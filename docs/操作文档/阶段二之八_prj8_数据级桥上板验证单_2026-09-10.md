## 〇′、第二根因修复（2026-09-17，必读，[[操作文档/调试记录_帧泵rd_empty_off-by-one_2026-09-17|完整调试记录]]）

15:07 版位流上板仍不通（ping/UDP 全失败、偶发 1/4 通过），**第二根因**由整链仿真定位：

**根因**：`frame_fifo_pump` 读侧 `rd_empty = (bin2gray(rd_bin_next) == wr_ptr_g_s2)` 误用
`rd_bin_next`（提前一拍判空）——读指针追到与写指针持平时，**每帧最后一个字节被误判为空而拒读**
→ 回显帧尾部截断 → PC 网卡按 FCS 丢弃 → ARP/ping/UDP 全丢。该缺陷存在于历代所有位流。

**修复**（C21）：`rd_empty = (bin2gray(rd_bin) == wr_ptr_g_s2)` —— 本泵"整帧先写满再读"，
读期间写指针稳定，用当前 `rd_bin` 判空安全，末字节允许读出。

**整链仿真验证**（`sim/tb_full_chain.v`，官方栈 + 双帧泵 + 打包/解包 + Aurora AXIS 模型）：
ARP 请求/回复 + UDP 回显 16B/29B/200B 共 **5 帧逐字节全对**，三级字节数 553=553=553 零丢失，
源端口回显（改动 B）同步验证通过。

**与板上现象吻合**：历代 ping 全不通（帧尾截断→FCS 错→丢弃）；"4 个 ping 收到 1 个"
（复位后首帧幸存、后续被截）；project_6 能通（TX 直连不经过帧泵，天然绕开）。

## 〇、首轮上板暴露的问题与本次修复（历史，已由 〇′ 补全另一半）

**首轮现象**：两灯亮（`channel_up=1`、Aurora 收到过数据）+ ping 不通。

**根因（闭环仿真已复现）**：`axis_word_unpack` 在**帧中间插了空拍**，而下游帧泵靠
`wr_en` 的下降沿判帧尾 —— 一帧被切成多段，回显帧残破，PC 网卡按 FCS 全部丢弃。

三个具体缺陷：
1. **"边收边吐"必然断流**：Aurora RX 有流水线延迟，而写侧（1 字/8 周期）与读侧
   （1 字节/周期）平均速率恰好相等 → 缓冲迟早被抽干。仿真：34 帧收回 **77 段**、`stall=40`。
   → 改为**整帧存储转发**（收全一帧再连续吐，帧内物理上不可能断流）。
2. **末拍跳过无效 lane 也留空拍**：按 lane 0..7 扫、遇 keep=0 就"不吐"，会在帧中间留 7 拍
   （9 字节帧被切成 8+1，与首轮现象吻合）。→ 改为 popcount 算有效字节数、从首个有效 lane
   **连续吐 N 个字节**。
3. 附带修掉一个仿真器坑：`lowidx8` 用 `for` 循环求"最低有效位"，**XSim 按升序求值**，
   返回的成了最高位 → 每帧最后一个字节跑到帧首。改成无循环的优先链。

**修复后闭环仿真**：34 帧（长度 1~1000 字节，覆盖全部 `帧长%8` 余数，含随机 `tvalid` 空洞）
→ **34 帧全对、逐字节一致、无断流、无溢出（stall=0）**。脚本 `sim/tb_pack_unpack.v`。

> ⚠️ 结论：**必须重新烧录 15:07 版位流**；旧版（13:17）已知有上述缺陷。

## 一、这次要证明什么

**判据只有一条：PC 发 UDP payload `P`，收到回显 `P′`，要求 `P′ == P`。**

为什么这一条就能证明 64B/66B 通了：
板上 PC→栈 方向是**直连 RGMII**（不走 Aurora），只有**板卡要发出去的帧**（ARP 应答 /
ICMP 应答 / UDP 回显）才被强制穿过 `帧泵 → 8→64 打包 → Aurora TX → GT 内环 → Aurora RX
→ 64→8 解包 → 帧泵 → RGMII TX`。

关键点：**Aurora 没起来时链路是硬门控的**（`aurora_rst = ~sys_rst_n | ~channel_up`
把帧泵读侧按在复位里），板卡对外**完全不说话**——所以不存在"绕过 Aurora 也能通"的旁路。
`P′ == P` 只可能来自"数据确实穿了 64B/66B 编解码往返"。

## 五、第一步：ping —— 先证链路，再看数据

```powershell
ping 192.168.1.10 -n 4
```

**为什么先 ping**：板卡的 ICMP 应答同样要穿过 Aurora 才能发出来。
所以 **ping 通 = Aurora TX/RX + 打包/解包 + 双帧泵全部工作正常**，
此时再做 UDP 数据比对就是"确认数据内容没有被改坏"。

- ping 不通 → 直接查 T23 灯和 ILA0（此时 UDP 一定也不通）；
- ping 通但 UDP 不通 → 看 ILA1 的 `pump_fwd_drop / pump_rev_drop` 是否非 0。

## 六、第二步：UDP 数据比对（硬判据）

```powershell
cd D:\FPGA\project_8
python scripts\udp_verify.py
```

脚本依次发 payload 长度 **26/27/28/29/30/31/32/33/40/63/100/200** 字节各一包，
逐字节比对，最后打印 `回显一致 N/12`。

**为什么用这么多长度**：以太网帧总长 = 头 + payload + FCS，未必是 8 的倍数。
打包模块对"帧尾不足 8 字节"的余字有专门逻辑（按 Aurora 约定**高位 lane 对齐** +
`tkeep = 8'hFF << (8-N)`），解包侧升序遍历跳过无效 lane。
12 种长度覆盖了 8 种 `帧长 % 8` 余数类别 —— 任一余数类别处理错，都会在这一步暴露。

期望输出末尾：`PASS: 所有 payload 原样返回 → 数据已穿越 Aurora 64b/66b 编解码往返`

> 若想加压：`python scripts\udp_verify.py 3`（每个长度发 3 包）。
> 注意帧泵是**握手限流**的：上一帧没排空时新帧会被丢弃（`*_drop` 计数），
> 脚本默认每包间隔 0.3 s，足够；不要用无间隔狂发来"压测"，那不是本阶段目标。

## 七、可选：ILA 抓波形（归档用）

### 7.0 先解决 "Run Trigger 不可用" 的报错

报错原文：`Use the Refresh Device command with a valid Probes (debug_nets.ltx) file
before executing the command: Run Trigger`

**原因**：位流里的 ILA 是有的，但 Vivado 不知道 `probe0` 每一位对应什么信号 ——
必须把生成位流时一并写出的 `probes.ltx` **关联到"设备"**，再 Refresh Device。

**一条命令解决**（推荐）：

```powershell
cd D:\FPGA\project_8
vivado -mode batch -source scripts\ila_load_probes.tcl -notrace
```

脚本会连上 hw_server、设好探针文件、Refresh Device，并打印 ILA 列表与完整位表。

**GUI 等价操作**（建立直觉，建议走一遍）：
1. Hardware Manager 里选中最上面的器件（`xcku060_0`）；
2. 左下 Properties 面板 → **Probes File** 选 `D:\FPGA\project_8\scripts\probes.ltx`
   （**Full Probes File** 一栏同样选它）；
3. 右键该器件 → **Refresh Device**；
4. 树里 `hw_ila_1`/`hw_ila_2` 展开即可看到 probe0，Run Trigger 可用。

> 也可以在 Program Device 对话框的 **Probes file** 栏直接指定 `probes.ltx` ——
> 这样烧录时就一并加载，省掉刷新步骤。

### 7.1 抓取建议

Hardware Manager → 选 ILA（用 cell 名区分：`u_ila_0` 在 user_clk 域，`u_ila_1` 在 eth_rxc 域）。

| ILA | 时钟域 | 触发条件 | 看什么 |
|---|---|---|---|
| ILA0 | user_clk | `rx_tvalid == 1` | `rx_tdata/rx_tkeep/rx_tlast`（Aurora 回来的 64bit 流）、`unpack_frames/bytes`、`unpack_ovf/stall` 应为 0、`channel_up=1`、`soft_err/hard_err=0` |
| ILA1 | eth_rxc | `stack_tx_en == 1` | `pump_fwd_wr` 递增、`pump_fwd_drop=0` |

> 探针位序说明：probe0 按"先列 = 低位"拼接（脚本注释里写了完整位表）。
> 如果波形看起来字段位序颠倒，就是 Vivado 用了"先列 = 高位"的映射，
> 按注释里的位表反着解析即可——**不影响判据**（判据是脚本比对，不依赖 ILA）。
