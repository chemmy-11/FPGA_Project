## ⚠️ 最重要的一页：设计点数字与两处口径订正

> W2 记录（`操作文档/阶段三_prj10_内存桥RTL与仿真记录_2026-09-29.md` §四）与设计说明 §5 里的
> **"单桥 3.11 µs/帧"是混合帧长（64–1466 B）的统计均值，不可作为设计点引用**。
> 设计点 = prj9 满 chunk **1466 B**（ui_clk = 300 MHz，帧周期 12.304 µs = 3691 拍）：

| 量（1466 B 设计点） | 替身模型（Lw≈2, Lr≈9 拍） | 真 MIG 上界假设（Lw=200, Lr=250 拍） |
|---|---|---|
| 单桥写服务 `T_w = L+3·ceil(L/64)+4+Lw` | **5.14 µs**（1541 拍） | **5.80 µs**（1739 拍） |
| 单桥读服务 `T_r = L+2·ceil(L/64)+4+Lr` | **5.08 µs**（1523 拍） | **5.88 µs**（1764 拍） |
| **两级桥（入口写 + 出口读）每帧 DDR 路径 = T_w + T_r（串行）** | **10.21 µs** | **11.68 µs** |
| → 相对 12.304 µs 帧周期的裕量 | **1.20×** | **1.05×** |
| 稳态吞吐上限 = 1/max(T_w,T_r)（**流水前提**） | 194.7k fps（2.39× 线速） | 170.1k fps（2.09× 线速） |

**两条必须改口径的结论**

1. **W2 记录的"端到端延迟 +6 µs"应改为"+10~12 µs"，且这是串行相加**（同一帧先写后读），不是并行。
   原记录拿"单桥 max"去加两级桥，等于把**吞吐口径**当**延迟口径**用。
2. **"2 倍余量"只在两级桥允许流水时成立**（帧 N 在出口桥读的同时、帧 N+1 在入口桥写）。
   若系统要求整帧穿完两级桥才放下一帧，裕量只剩 **1.05×**。
   破坏节拍的阈值：**流水时 L > 2152 拍（7.17 µs）；不流水时 Lw+Lr > 636 拍（2.12 µs）**。

**两个真缺陷的处理状态（本轮已修并复验）**

| | 状态 | 证据 |
|---|---|---|
| **D1** `out_inc/out_dec` 双 always 驱动 | **真综合判定为硬件致命 → 已修复 → 复验 0 Critical Warning** | 修前综合报 **6 条 CRITICAL WARNING**，含 `constant driver preserved, other driver is ignored`；修后 **0 条**。见 §3 |
| **D2** 超长帧导致写 FSM 永久卡死 | **已复现 → 已修复 → 回归 PASS** | 修前 `wst=6, w_pop=4095, w_len=8000` 永不恢复；修后 `wst=0, len_err=1, wr_frame=2` 且后一帧逐字节正确。见 §4 |

## 3. 真缺陷 D1：`out_inc / out_dec` 双 always 块驱动（多驱动竞争）

### 3.1 事实（[已核实]，源码行号）

用脚本对 `axi4_master_bridge.v` 做"同一 reg 被几个 always 块赋值"的全量扫描，输出：

REGS DRIVEN FROM MORE THAN ONE ALWAYS BLOCK:

即：

## 4. 真缺陷 D2：帧侧不强制帧长上限 → 字节 FIFO 与描述符静默失步

### 4.1 事实（[已核实]，源码行号）

- 验收条件只保证**一个 MAX_LEN 的余量**：
  `frame_mem_if.v:110` `BF_ROOM = BF_DEPTH - MAX_LEN = 4096-1538 = 2558`；
  `frame_mem_if.v:208` `byte_room_ok = (ub_wl <= BF_ROOM)`（⇒ 至少 1538 B 空位）。
- 但**帧长本身没有任何上界**：`frame_mem_if.v:231-239` `wcnt` 对每个 `wr_en` 拍都 +1（不管写没写进去）；
  `frame_mem_if.v:216` `ub_wr_en = wr_en & ~frm_drop_now & ~ub_full` **会被 `ub_full` 掐掉**；
  `frame_mem_if.v:244` `ud_len_r <= wcnt` 仍然记录**完整长度**。
- 桥看到超长描述符后走 `axi4_master_bridge.v:170` `w_bad_len` → `:281-288` `W_DRAIN`
  按 `w_len` 抽字节；字节根本不在 FIFO 里 → 抽不动 → **永久停在 W_DRAIN**，并且会吃掉后面帧的字节。

### 4.2 最小复现（新增文件）

### 4.3 定性（避免夸大）

- **触发前提是上游违约**：prj9 帧契约（chunk=1466 + 头）≤1538 B，正常路径不触发。
  所以 **D2 不推翻 W2 的 PASS**，它是"防守性缺失"。
- 但两个后果是真的：**(a) 写路径永久卡死**（不是丢一帧就恢复）；**(b) T3 赖以成立的差分链
  `pushed == committed + bridge_stall` 被打破**（实测 `pushed=2, committed=1, wr_stall=0`）。
- 第 3 帧**有**被计数（`buf_drop=1`），所以不是"完全静默"；静默的是**帧 2 的失步**。
### 4.4 修复与回归（Lead 已授权，本轮已改 rtl/）

**根因修法（frame_mem_if.v）——让"描述符长度"恒等于"真正进 FIFO 的字节数"**

原代码用 `wcnt`（上游**提供**的字节数）当描述符长度，而 `ub_wr_en` 会被 `ub_full` 掐掉（**真正入队**的字节数）。
二者一旦分叉，桥再怎么定义都是错的。修法：

```
wire push_now = wr_en & ~frm_drop_now & ~ub_full;   // 真正入队的那个字节
assign ub_wr_en = push_now;
reg [15:0] n_push, n_push_r;                         // 入队计数 + 锁存
assign ud_din = n_push_r;                            // 描述符 == 入队字节数
...
if (wr_first) n_push <= push_now ? 16'd1 : 16'd0;
else if (push_now) n_push <= n_push + 16'd1;         // 只数真正写进去的
if (wr_last) if (~frm_drop && n_push != 0) begin ud_push<=1; n_push_r<=n_push; ... end
```

**这样描述符与字节流在结构上不可能失步**（无论上游多长、无论 `ub_full` 何时掐），
W_DRAIN 永远能抽到它要的字节数。

**再加一道 liveness 保险（axi4_master_bridge.v）**：W_DRAIN 若连续 16 个 ui 拍抽不到字节，
就放弃、计数（新增 `stat_len_err`）、回 IDLE —— **"不可恢复态"从结构上被排除**。
同时 `w_bad_len`（len>MAX_LEN 或 0）也计入 `stat_len_err`，超长帧不再是"静默"的。

## 7. 延迟维度量化（回答 Lead 的两条追加问题）

### 7.1 拍数公式（[推算]，已用实测计数回归校验）

时钟：`ui_clk = 300 MHz`（3.3333 ns/拍）——**由 MIG 配置推得，仍待 W1 用生成报告定稿**。
记号：帧长 `L` 字节，`B = ceil(L/64)` 拍（512 bit = 64 B）。

**写路径**（`axi4_master_bridge.v:210-279`）：

```
T_w(L) = 1 (W_IDLE) + 1 (W_WAIT) + 2 (W_AW) + L (W_FILL，每拍 1 字节) + 3·B (每 beat 死区) + Lw
       = L + 3·B + 4 + Lw
```

- **AWLEN 是整帧一次**，不是每 64 B 一次：`:178` `m_axi_awlen = w_beats - 8'd1`，
  `w_beats` 在 `:225` 由**整帧长度**一次算出（`(wd_data+63)>>6`），`w_beat` 只在 `:254-258` 内部累加。
  **Lead 的读法 (3) 正确。**
- **每 beat 3 拍死区**（[已核实] 状态机逐拍展开）：
  `:243-245` `w_beat_full` 置起后仍要在 W_FILL 空转 1 拍 → `:247-248` W_PUSH 第 1 拍 `wvalid` 还是 0 →
  第 2 拍才握手。即 **64 B/67 拍**（`:249-260`）。
- **每帧串行暴露一次 Lw**：`:175` `wd_rd_en=(wst==W_IDLE)&&calib_ok&&!wd_empty`，唯一的回 IDLE 路径是
  `:263-278` 的 W_B（`m_axi_bvalid && m_axi_bready` 之后 `:277` `wst <= W_IDLE`）。
  → **下一帧的 AW 必须等本帧 BVALID，Lead 的判断 (3) 正确。**

**读路径**（`axi4_master_bridge.v:347-421`）：

```
T_r(L) = 1 (R_IDLE) + 2 (R_AR) + [2·B + L] (R_R + R_UNPACK，每拍 1 字节) + 1 (R_FIN) + Lr
       = L + 2·B + 4 + Lr
```

- `:320` `m_axi_arlen = r_beats - 8'd1`，`r_beats` 由 `:368` 整帧长度算出 → **整帧一次 AR**。
- 每帧串行暴露一次 Lr：`:317` `rc_rd_en=(rstate==R_IDLE)&&...`，唯一回 IDLE 路径是 `:412-420` R_FIN。
  → **Lead 的判断 (4) 正确。**

| 用例 | 帧数与长度 | 公式预测（写 / 读） | 实测（写 933×585 / 读 920×585） |

### 7.2 读写两个 FSM 是同一个 AXI 端口吗？

- **AXI 协议层：不是；两者可以同拍同时活动，RTL 里没有任何仲裁或互斥。** [已核实]
  - 两个独立 always 块：写 `:185`，读 `:332`。
  - 驱动**互不相交**的信号集合：写 = `awaddr/awlen/awsize/awburst`(`:177-181`)、`wdata/wstrb/wlast`(`:182-183`)、
    `awvalid`(`:82`)、`wvalid`(`:87`)、`bready`(`:91`)；读 = `araddr/arlen/arsize/arburst`(`:319-322`)、
    `arvalid`(`:96`)、`rready`(`:102`)。AXI4 的 AW/W/B 与 AR/R 是独立通道 → 天然可并行。
  - 共享的只有槽表 `full_bit/len_tab`(`:108-133`) 与 `stat_wm`，都是同域单拍读，无互锁。
- **物理层：是同一个 slave 端口。** 真 MIG 只暴露 **一组** `c0_ddr4_s_axi_*`（`ddr4_0.veo:80-116`）。
  → **W3 若真做"入口桥+出口桥"，两个桥必须经 AXI Interconnect 或自制仲裁接到这一个口上**，
  并给不同 ID；这是 W2 完全没有覆盖的架构项（TB 里只有 1 个桥、1 个模型）。

### 7.3 挂上真 MIG 后：哪些数字变、哪些不变

**不变（且占绝对主导）**——因为瓶颈是桥内部**逐字节串行**，与 DDR 无关：

- 字节装配 `+L` 拍（`axi4_master_bridge.v:197-204`，每拍 1 字节）与解包 `+L` 拍（`:400-409`）；
- 每 beat 死区 3 拍（写）/ 2 拍（读）；
- 槽表、5 个 CDC FIFO、命令/寄存器语义、4KB 规则（仍 0 违规）、`wm=wr=rd` 对账链。

**会变（每帧新增/放大）**：

| 量 | 替身实测 | 真 MIG 量级 | 每帧影响 |
|---|---|---|---|
| 写响应延迟 Lw | **2 拍**(`axi4_ram_model.v:124-131`) | 数十~数百拍（写缓冲/刷新） | 串行 +Lw（`axi4_master_bridge.v:175,277`） |
| 读首拍延迟 Lr | **9 拍**(`axi4_ram_model.v:17,164,174-177`) | 数十~数百拍 | 串行 +Lr（`axi4_master_bridge.v:317,420`） |
| `awready/arready/wready` 拉低时长 | 随机 1/8 拍(`:66-71`) | 成串，tRFC 量级 ~105 拍 | 只加在 W_AW/`W_PUSH`/`R_AR`/`R_R`，**功能不怕**（valid 保持正确） |
| DDR 总线读写互抢 | 不存在 | 读写转向惩罚 | 让 §7.4 的"两 FSM 并行"在 DRAM 层打折 |

**DDR4-2400 64 bit 的带宽上界算术**（[推算]，用于证明带宽不是约束）：

```
峰值     = 2400 MT/s × 8 B/transfer                = 19.2 GB/s
保守效率 = 512b 突发、单 outstanding，取 50–70%     = 9.6 – 13.4 GB/s
需求     = 81.3k fps × 1466 B × 2(写+读)           = 238 MB/s  = 峰值的 1.2%
单帧 DDR 占用 = 23 写 beat + 23 读 beat = 46 ui 拍 / 帧周期 3691 拍 = 1.25%
```

→ **DDR 带宽与 MIG 效率都不是约束**（40× 以上余量）。单帧里 DDR 只忙 ~46 拍，而桥要 1539 拍
——**桥比 DDR 慢 33 倍，DDR 98% 时间在空转**。这一条决定了下面所有结论。

### 7.4 设计点数值与判定阈值

设计点取 prj9 满 chunk：**L = 1466 B，B = 23**；帧周期 **12.304 µs = 3691 拍**。

| 量 | 替身（Lw=2, Lr=9） | Lead 假设（Lw=200, Lr=250） |
|---|---|---|
| 写服务 `T_w = 1539+Lw` | **1541 拍 = 5.137 µs** | **1739 拍 = 5.797 µs** |
| 读服务 `T_r = 1514+Lr` | **1523 拍 = 5.077 µs** | **1764 拍 = 5.880 µs** |
| 单帧穿一个桥（写+读，串行） | 3064 拍 = **10.21 µs** | 3503 拍 = **11.68 µs** |
| **稳态吞吐上限 = 1/max(Tw,Tr)** | 1541 拍 → **194.7k fps** | 1764 拍 → **170.1k fps** |
| **相对 prj9 线速 81.27k fps 的裕量** | **2.39×** | **2.09×** |
| 两级桥（入口写 + 出口读）每帧 DDR 路径 | 3064 拍 = 10.21 µs → 裕量 1.20× | 3503 拍 = 11.68 µs → **裕量 1.05×** |

**判定阈值（回答"L 大到多少就破坏节拍"）**：

- **流水成立**（帧 N 在出口桥读的同时，帧 N+1 在入口桥写）：
  `max(T_w,T_r) < 3691` → **L < 2152 拍 = 7.17 µs**。真 MIG 不可能达到 → **不会被延迟破坏节拍**。
- **不流水**（必须整帧穿完两级桥才允许下一帧）：
  `T_w + T_r = 3055 + Lw + Lr < 3691` → **Lw + Lr < 636 拍 = 2.12 µs**。
  Lead 的假设值 450 拍 → 余 186 拍（0.62 µs），**裕量只有 1.41×，且真值尚未实测**。

**结论**：**能跑，不需要先改成多帧流水/多 outstanding。** 但必须同时修正两处口径：

1. 文档 §四/§五的"单桥 3.1 µs/帧、两级桥 6.2 µs、端到端 +6 µs"
   → 应改为"设计点单桥写 5.14 µs / 读 5.08 µs（替身）、两级桥链每帧 **10.21 µs**（替身）
   / **11.68 µs**（含 Lw+Lr），端到端延迟增加 **~10–12 µs ≈ 1 个帧周期**"。
   3.11/3.07 µs 是**混合帧长均值**，不能当作设计点服务时间用（Lead 的 (1)(4) 问的就是这个）。
2. "2 倍余量"只在**流水**前提下成立；不流水时只有 **1.05×**。
   W3 必须明确"两级桥允许流水"，否则没有任何缓冲余量吃仲裁/刷新抖动。
3. 若想拿回余量，**最有效的杠杆不是 MIG，而是把 `w_data_r[w_bi*8 +: 8]` 的逐字节装配改成 4/8 字节并行**
   （`axi4_master_bridge.v:197-204`）——它能把 T_w 从 1539 拍压到 ~250 拍，与 MIG 延迟无关。

### 9.3 最小修复方案（只给方案，本轮未落地）

**Step 1 — 端口补齐（必做，低风险，零行为变化）**

| 方向 | 端口 | 驱动 |
|---|---|---|
| output | `m_axi_awid[3:0]` · `m_axi_arid[3:0]` | 常量（见 Step 2 的 ID 策略） |
| input | `m_axi_bid[3:0]` · `m_axi_rid[3:0]` | 单 outstanding 时**不参与状态机**（可选：加 `!= 期望ID` 的计数） |
| output | `m_axi_awlock[0:0]`=`1'b0` · `awcache[3:0]`=`0` · `awprot[2:0]`=`0` · `awqos[3:0]`=`0` | AXI4 语义：LOCK=0 普通访问；CACHE=0 device non-bufferable；PROT/QOS=0（与 Xilinx MIG example design 一致） |
| output | `m_axi_arlock`/`arcache`/`arprot`/`arqos` | 同上 |

- 落点：`axi4_master_bridge.v` 端口表 + `frame_mem_if.v` 透传 + `axi4_ram_model.v` 补同名端口（**TB 才能继续跑同一个用例集**）+ `mem_bridge_tb.sv` 例化。
- 工作量：**约 30 行 × 3 个 RTL/模型文件 + 2 处例化，1–2 小时**。
- 验收：`run_sim.bat` 仍须 `PASS (0 errors)` 且四个 STAT 行一字不差（全是常量，行为不应变）。
- **不能只加在 TB 上**——那样只是把缺口藏起来。

**Step 2 — ID 分配策略**

| 形态 | 分配 | 理由 |
|---|---|---|
| 单桥 + 单 MIG 口（W3 最小形态） | 读写都用 **`ID = 4'b0000`** | AXI4 只要求"同一 ID 的事务按序返回"。本桥写、读各只有 **1 个 outstanding**（`axi4_master_bridge.v:235-241` 单 AW、`:376-382` 单 AR）→ 单 ID **完全合法**；B 通道与 R 通道的 ID 空间互不影响，读写不必用不同 ID |
| **两级桥共用 1 个 MIG 口（prj10 计划形态）** | `ID = {bridge_sel[1:0], dir}`：桥0写=`4'b0000`、桥0读=`4'b0001`、桥1写=`4'b0010`、桥1读=`4'b0011` | 两个桥必须能区分自己的 BID/RID，否则 interconnect 只能退化成"独占串行"→ 直接踩 §7.4 的"不流水退化"（裕量 1.05×） |

> **ID 不解决仲裁**：两个桥仍需要 `axi_interconnect`/`smartconnect`（或自制 burst 级仲裁），
> 且必须保证**整帧 23 拍突发的原子性**，否则 §7.4 的结论要按"不流水"那一栏算。

**Step 3 — "端口补齐"和"多 outstanding"是不是同一个改动的两面？**

**不是。两者可分离，而且本阶段不需要做多 outstanding。**

| 维度 | 端口补齐（ID / 属性） | 多 outstanding |
|---|---|---|
| 性质 | 连线 + 合规（thin pass-through） | **FSM 结构性改造** |
| 行为变化 | 无（常量 + 忽略输入） | 大：AR 发出后不等 R；读数据按 ID 重排或每 slot 独立缓冲；命令队列加深；`rstate` 需拆分 |
| 依赖关系 | 无前置 | 需要 ID 已存在；但 AXI4 允许**同 ID 多 outstanding**（只要按序返回），所以严格说**不是硬依赖** |
| 对 W3 的必要性 | **必须做，否则物理上接不上** | **按 §7.3 不必要**：DDR 利用率仅 **1.25%**，瓶颈是逐字节装配（桥 1539 拍/帧 vs DDR 只忙 46 拍） |

**合起来的结论**：把"补齐端口"当作**独立小改动先做掉**（1–2 h，零行为变化，可当天回归验证）；
**多 outstanding 推迟**到"余量被实测证明不够"时再做。真要拿余量，优先级是
**① 字节并行装配（§7.4 结论 3：1539 → ~250 拍，与 MIG 无关）> ② 多 outstanding**。

## 10. 地址解码断言 + 反向验证 + SLOT_BASE 依据（Lead 追加要求，已做成可判据）

### 10.1 为什么必须收口（[已核实]）

`axi4_ram_model.v:113` 用 `mem[(waddr[19:0]+mi) % MEM_BYTES]`、`:182-213` 读同理 —— **只取低 20 位**。
`SLOT_BASE = 0x0010_0000` 恰好是 1 MB，而 `MEM_BYTES = 1 MB`，**基址被整位丢掉**，
槽 N 恒等于偏移 N×4096。于是"写错 SLOT_BASE / 槽步长写错 / 槽号 ≥256"这三种错误
**在 W2 的 TB 里全部不可见**（TB 从头到尾没有看过一眼 `m_axi_awaddr`/`m_axi_araddr`）。

### 10.2 断言（新增 `sim/addr_assert_tb.sv`）

在每个 `awvalid` / `arvalid` **上升沿**判三条（写读各一遍）：

```systemverilog
wire [31:0] aw_expect = EXPECT_BASE + {12'b0, ro_dbg_wr_slot[7:0], 12'b0};
if (m_awvalid && !awv_d) begin
    if (m_awaddr !== aw_expect)   viol_rel   <= viol_rel   + 32'd1;  // ① 基址+槽号*4096
    if (m_awaddr[11:0] !== 12'd0) viol_align <= viol_align + 32'd1;  // ② 4KB 对齐
    if (({20'b0,m_awaddr[11:0]} + (m_awlen+8'd1)*32'd64) > 32'd4096)
                                  viol_4k    <= viol_4k    + 32'd1;  // ③ 突发不跨 4KB
end
```

关键点：**槽号取自桥自己的 `ro_dbg_wr_slot`/`ro_dbg_rd_slot`**，所以 ① 是一条真正的
"槽表 ↔ 地址"关系断言，**不是恒真**（下面用反向验证证明）。

一键复现：

```
cd D:\FPGA\project_10\sim
xvlog -sv ..\rtl\async_fifo.v ..\rtl\axi4_master_bridge.v ..\rtl\frame_mem_if.v axi4_ram_model.v addr_assert_tb.sv
xelab -debug typical addr_assert_tb_good       -s addr_good ; xsim addr_good -runall
xelab -debug typical addr_assert_tb_bad        -s addr_bad  ; xsim addr_bad  -runall
xelab -debug typical addr_assert_tb_misaligned -s addr_mis  ; xsim addr_mis  -runall
```

### 10.3 反向验证：故意改错，断言必须变红（原始输出）

```
=== ADDR ASSERT (correct base) ===
  frames_committed=3  viol_rel=0 viol_align=0 viol_4k=0
  RESULT: PASS (addr == base+slot*4096, 4KB aligned, no 4KB cross)

=== ADDR ASSERT REVERSE #1 (EXPECT_BASE deliberately wrong: 0x0020_0000) ===
  frames_committed=3  viol_rel=6 viol_align=0 viol_4k=0
  RESULT: PASS -- check #1 went RED (6 violations): the assertion is NOT vacuous

=== ADDR ASSERT REVERSE #2 (RTL SLOT_BASE deliberately misaligned: 0x0010_0800) ===
  frames_committed=3  viol_rel=6 viol_align=6 viol_4k=0
  RESULT: PASS -- alignment check went RED (6 violations)
```

**结论**：三条断言在真错时**确实变红**（反向 #1 打红 ①，反向 #2 打红 ①②），
所以它们不是恒真式；同时正确设计下 3 帧 6 个突发全部 0 违规。
反向 #2 还顺带说明：**基址一旦不是 4KB 对齐，AXI 4KB 规则立刻被破坏** —— 这正是当年选 4KB 槽的隐含前提。

### 10.4 `SLOT_BASE = 0x0010_0000` 是拍脑袋还是有依据？

| 维度 | 事实（证据） | 判定 |
|---|---|---|
| 值本身 | `0x0010_0000` = 1 MB，4KB 对齐；两区 2×256×4KB = **2 MB** → 占 `0x0010_0000–0x002F_FFFF` | **人为约定值**，无官方依据 |
| 与 MIG 映射冲突？ | `ddr4_0.xci`：`C0_DDR4_MEMORY_MAP_BASEADDR=0x0000_0000`、`HIGHADDR=0xFFFFFFFF` → MIG 把整个 32 bit 空间都当 DDR 解码 | **不冲突**；2 MB 相对容量可忽略（容量口径由 W1 复核） |
| 与 MicroBlaze/BD 地址打架？ | `ddr4_0_microblaze_mcs.hwh` 的地址块是 **LMB 本地存储器**：`Mem 0x0000_0000–0x0000_FFFF`、`second 0x0001_0000–0x0001_7FFF`、`Reg 0x8000_0000`、`IO 0xC000_0000` —— **不是经 MIG AXI 的 DDR 地址**；MCS 在本设计里只做校准状态读出，**不做 DDR 主机** | **当前不打架** |
| 未来风险 | 若 W3 起把 MicroBlaze/BD（或 AXI DMA）接成 MIG 的 AXI 主机，其默认分配会落在 DDR 低区 `0x0` 起，与 `0x0–0xFFFFF` 及本槽区 `0x100000–0x2FFFFF` **相邻甚至重叠** | **这是明确的未来打架点**，须在 BD 地址编辑器里显式避让 |

> **一句结论**：`SLOT_BASE = 0x0010_0000` 是**人为约定值**，当前自洽、不与 MIG 的 0–4 GB 解码冲突，
> 也不与 MicroBlaze MCS 的 LMB 地址冲突；**"是否要为将来的 BD/AXI DMA 主机让路"待 W1 用 MIG 地址映射
> + prj4 BD 地址分配复核**。在此之前，§10.2 的断言已经把"桥自己产生的地址"锁死为
> `SLOT_BASE + 槽号×4096`，任何改动都会立刻变红。
