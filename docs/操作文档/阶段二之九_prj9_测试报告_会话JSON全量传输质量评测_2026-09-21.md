# 传输质量评测：本会话 JSON 全量过光链路（prj9）

## 一、测试设计

- **负载**：本会话记录快照（`session.v3.jsonl` 解压，10,293,111 B / 2808 行 JSONL）——即工程未来承载的 agent 间数据实况。
- **链路**：PC ⇋ RGMII ⇋ 以太网栈 ⇋ 帧泵A ⇋ pack ⇋ Aurora 10G ⇋ **光纤** ⇋ B 侧 unpack→pack 回显 ⇋ **光纤** ⇋ A.RX ⇋ 泵B ⇋ PC（数据渡光两次）。
- **分片**：1408B 帧（1360B 切片 + 6B 帧头 seq/len），7569 片。
- **工具**：`project_9/scripts/json_storm.py`（重组 + SHA256 全文比对 + 逐片 MD5 + RTT/吞吐统计）。

## 三、丢失定位（证据链）

1. **PC 侧排除**：同代码打 localhost 回显 772/772 = 0 丢失。
2. **泵A 排除**：ILA 计数器差分（4MB@1ms，PC 丢 14 片）：pfwd_wr +3087 全过、**pfwd_drop=0**、pk=pfwd_wr；而 prev_wr 恰差丢失数。
3. **结论**：0.4% 相邻对丢失发生在 **Aurora 渡纤段内部**（A.TX→纤→B 回显→纤→A.RX），与节奏无关（1/2/5ms 同率），呈随机分布的相邻对。
4. **首要嫌疑**：B 侧回显 pack_b 输入溢出（单帧在途策略）——其 o_overflow 计数器未挂 ILA，待下版位流验证。

## 四、容量与稳定性边界

- **突发**：gap=0 时隔帧丢弃（51%）——帧泵/回显的单帧在途策略是硬瓶颈；设计目标内（人节奏交互）无影响。
- **累计退化**：约 26MB 累计流量后泵A 冻结（计数器全停、ping 部分通、出现 seq 字段损坏的回显）——重烧即恢复，机制待查（疑与持续流量下某状态机退化有关）。
- **数据面**：全部测试**零损坏、零乱序**——光链路本身的数据完整性无可挑剔。

## 四B、补测（2026-09-21）：性能档、容量天花板与冻结触发

| 场景 | 到达 | 损坏 | 速率(单向) |
|---|---|---|---|
| 全量 10MB @gap=0.1ms（性能档）| **99.84%**（历史最佳，丢 12）| 0 | **19.3 Mbps**（4.25s 发完）|
| 4 进程并行 @0.1ms（容量探测）| 33.77%（送 70 Mbps 回 22.9）| 0 | 回程 22.9 Mbps |

- **PC 单流天花板 = 19.3 Mbps**：gap≤0.5ms 时速率收敛于此（sleep 精度 + 每帧一次 syscall + GIL），与链路无关。
- **系统串行容量 ≈ 23 Mbps**：并行送 70 Mbps 只回 22.9——全链 store-and-forward（帧泵×2+pack×3+B 回显）逐级整帧缓存，每帧独占全路径 ~230µs（与 RTT 吻合）。
- **冻结触发条件修正**：不只累计流量（~26MB），**瞬时过载**（大量帧冲突丢弃）也会触发硬冻结（ping 全灭，重烧恢复）。
- 性能档丢失 12 片 < 慢速档 32 片：Aurora 段丢失为随机底噪，与速率无关。

## 五、结论与下一步

**回答原始问题**：全量收发**基本可行**——小批量(100KB 级)已达 100% 完美往返；全量 10MB 级到达 99.6%，瓶颈不在光链路而在交换结构的**单帧在途策略**（两处：泵A 已证无辜存活、B 回显 pack 嫌疑最大）。

下一步（按优先级）：
1. 重编位流：echo_b_ovf / unpack_b 计数器 + Aurora CC/错误计数器入 ILA → 锁死 0.4% 丢失点；
2. 泵 v2：多帧队列（N 帧环形），消除单帧在途策略 → 突发场景到达率；
3. 累计退化（26MB 冻结）复现实验 + 根因；
4. 传输层重试/纠错（未来 agent 业务的可靠性应由上层协议保证）。
