# prj9 传输效率与瓶颈判定 · 实操单（v2 · 线速达标版）

> **性质**：本单 v1 = 归因判定；**v2 目标升级 = 传输效率达到以太网口上限**（千兆 GE，1466 B 净载荷口径 **≈953 Mbps**——这是物理可达上限的操作定义，不存在"1000 Mbps"这个数）。
> **判定报告必须回答的三问**（§八有模板）：
> ① 目前的传输实验是 Python 脚本限制速率吗？
> ② 实际场景中需要用什么协议传输？
> ③ prj9 的硬件设计部分是否限制了速率？
> **红线**：上板、烧录、插拔光纤归用户（AGENTS.md 红线 #2）；E1/E2/E3 为 PC 侧脚本 + 板上现有判决位流（build9v/w）即可跑；E4 需 Wireshark；E5 用 ILA 计数器（verdict_capture.ps1 幂等）。

### v2 修订记录（2026-09-29 第二次修订）

- **新增 §三 静态带宽预算**：读全部数据通路 RTL（udp_tx/udp_rx/frame_fifo_pump/axis_word_pack/eth_ctrl/顶层）逐级核算每帧服务时间——**这是三问中③的书面答案基础，未上板即可定案大半**。
- **修正 v1 的 A4 错误**：`--chunk 1472` 会造成 IP 分片（UDP payload 上限 1472 已含脚本 6 B 头）→ 板端栈无分片重组 → **全部丢弃**。正确值 **1466**。
- **判读树重写**：v1 三分支（≥100 / ≈23 / 40–80）基于"瓶颈未知"预设；静态核算后预判：瓶颈阶梯 = PC sleep (19.3) → Python 发送循环 (~400–700) → **帧泵B/栈TX 零裕量级 (~950–957)**，实验按阶梯验证而非摸索。
- **新增 §四 硬件静态风险清单**（含过载冻结的候选机制）与 §八 三问回答模板。

## 一、现状与目标

| 指标 | 实测值 | 出处 |
|---|---|---|
| 单流有效吞吐（性能档 10MB） | **19.3 Mbps**（4.25 s 发完，561 µs/帧） | 09-21 评测 |
| 受控并行回程（容量档，4 进程） | **约 22.9 Mbps**（送 70 回 22.9） | 09-21 评测 |
| 帧规格（现行） | 载荷 1360 B + 6 B 头 = 线上 1426 B | `json_storm.py` §L151 |
| **千兆口净载荷上限（目标）** | **953 Mbps** @1466 B 净载荷（1538 B 线上/帧，12.304 µs 帧周期，81.3k fps） | §三核算 |
| 链路层线速 | Aurora 10 Gbps ×2 通道 | 已实测 |

**差距表述**：19.3 → 953 差 **49 倍**。v2 的任务 = 把这 49 倍逐层拆开，每层用实验钉死，最终在报告里同时给出：**达到多少（实测）+ 剩余差距归谁（PC/协议/硬件）**。

## 二、归因定案（v1 已完成，结论保留）

### 2.1 19.3 Mbps = PC 侧 `time.sleep()` 睡出来的

代码与算术（`json_storm.py` 发送主循环每帧一次 `time.sleep`）：561 µs/帧 ≈ Windows 高精度定时器 ~500 µs 分辨率 + 循环开销。4 独立进程各自 ~17.5 Mbps（进程间无 GIL，卡点相同）→ 公共因子只有 sleep。**主循环在等定时器，不是在等 FPGA。**

### 2.2 22.9 Mbps = 开环伪容量（测量下界）

回程无独立发送源，测量同时受 PC 收包能力与板卡冲突丢弃污染。设计报告 v0.5 §3.3.2 已修正口径：**"送 70 回 22.9"是测量方法的下界，不是互连结构的极限**。

### 2.3 v1 遗留的候选②"帧泵单帧在途"——静态核算已定案（见 §三）

v1 把"帧泵单帧在途"列为待实验判别的候选瓶颈。v2 读 RTL 定量核算后**降级为非当前瓶颈**：单帧在途的服务时间 ≈ 9.8 µs（泵A）/ 12.2 µs（泵B），对应上限 1.19 Gbps / 959 Mbps——**它确实限制速率，但限制点在千兆线速上，不在 23 Mbps 上**。也就是说 49 倍差距里，硬件只"负责"最后 ~1%。

## 三、静态带宽预算（第一性原理核算 · 未上板可定案）★ v2 核心新增

**方法**：一帧从 PC 应用层到回显再回到 PC，逐级数清楚"每帧占用该级多久"（服务时间），全链路稳态帧周期 = max(各级服务时间)。时钟取 gmii = 125 MHz（千兆 GMII）、Aurora user_clk ≈ 156 MHz（10G 64b/66b，工程注释值 ~151.5M，对结论不敏感）。

**帧规格（chunk = 1466 = 1472 − 6）**：

```text
UDP payload = 6(脚本头) + 1466(净载荷) = 1472 B   ← MTU 1500 内，不分片
IP 包    = 20 + 8 + 1472   = 1500 B
以太帧   = 14 + 1500 + 4(FCS) = 1518 B
线上     = 8(前导/SFD) + 1518 + 12(IFG) = 1538 B   → 帧周期 12.304 µs，81.3k fps
板内 GMII 搬运(不含 IFG) = 1520 B/帧               ← 栈TX/泵A/泵B 的搬运量
净载荷上限 = 1466/1538 × 1000 Mbps = 953 Mbps      ← 「以太网口上限」的操作定义
```

**逐级服务时间表**（RTL 依据标注到文件）：

| # | 级 | 时钟 | 每帧拍数 | 服务时间 | 等效上限 | 裕量 vs 12.304 µs |
|---|---|---|---|---|---|---|
| 1 | GE 链路含 IFG（目标定义） | 线路 | 1538 B | 12.304 µs | 953 Mbps | 0（即目标） |
| 2 | RGMII RX + `gmii_to_rgmii` + `udp_rx` 解析 | 125M | 逐拍流水 | 跟随线速 | — | ✓（解析逐字节，无整帧缓存） |
| 3 | `async_fifo_2048x8b`（payload 缓存） | 125M | 1520 写/1520 读并行 | 透明 | — | ⚠️ 深 2048 = 1.35 帧，**积 2 帧即溢出且 full 悬空**（顶层 L436 `.full()` 空接，无计数） |
| 4 | **栈 TX `udp_tx.v`**（校验和4+前导8+Eth14+IP/UDP28+数据1466+CRC4+转移~6） | 125M | 1530 | **12.24 µs** | 957 Mbps | **+0.06 µs（0.5%）⚠️ 零裕量级** |
| 5 | 帧泵A（`frame_fifo_pump`，写125M/读~156M） | 双域 | 1520@156M + 4相握手~0.1µs | 9.83 µs | ~1.19 Gbps | +2.5 µs ✓ |
| 6 | `axis_word_pack`（16深队列，流式）+ Aurora A TX | 156M | ~190 拍流水 | 1.22 µs | ~9.6 Gbps | ✓✓ |
| 7 | B 回显 unpack→pack + 光 ×2 + unpack（A 侧收） | 156M | 流水 | ~3.7 µs | — | ✓✓ |
| 8 | **帧泵B（写~156M/读125M）** | 双域 | 1520@125M + 握手~0.05µs | **12.21 µs** | **~959 Mbps** | **+0.09 µs（0.7%）⚠️⚠️ 全链路节拍器** |
| 9 | RGMII TX → PHY | 125M | 1520 | 12.16 µs | 961 Mbps | ⚠️ 帧间仅 ~10 拍，**无标准 IFG（96 拍）**，PHY 容忍性待 E4 验证 |
| 10 | PC 接收（Python `recvfrom` 单线程） | — | — | 估 12–30 µs/帧 | 估 400–800 Mbps | 待 E4 排除 |
| 11 | PC 发送（Python `sendto` 循环，gap=0） | — | — | 估 16–30 µs/帧 | 估 400–700 Mbps | 待 E1/E2 实测 |

**三条静态定论（三问的书面答案基础）**：

1. **全链路静态上限 ≈ 957–959 Mbps**（= 帧泵B 与栈TX 两级零裕量级的较小者），恰好压在千兆口净载荷上限 953 Mbps 之上 **0.4–0.6%**。**prj9 硬件"刚好"设计在线速上：不是慢 49 倍的结构，是零裕量的线速结构。**
2. **推论（可实验证伪）**：
   - 发送端**受控节奏**（帧周期 > 12.3 µs，即 ≤950 Mbps）→ 全链路各级均有裕量 → **100% 无损通过**（E3 验证）。
   - 发送端**背靠背打满**（12.304 µs 帧周期）→ 泵B 服务 12.21 µs + 到达抖动 → **零星整帧丢弃**（量级预估 0.5–2%），`pump_rev_drop` 计数与 PC 丢失数算术闭合（E2 验证）。
3. **19.3 / 22.9 与硬件无关**：49 倍差距 = PC sleep（×31）→ Python 循环（×1.4–2.4，待测）→ 硬件零裕量（最后 ~1%）。

**为什么泵B 是节拍器而不是泵A**：两泵结构相同（单帧在途 + 忙时整帧丢弃，`frame_fifo_pump.v` 头注释自述"Human-paced traffic; stress mode is future work"），差别只在读侧时钟——泵A 读侧 ~156 MHz（9.73 µs 泵完一帧），泵B 读侧 125 MHz（12.16 µs 泵完一帧，把字节喂回 GMII）。**回程方向比去程慢 25%，这是纯时钟域结构决定的**。

## 四、硬件静态风险清单（上板判读对照表）★ v2 新增

| # | 风险点 | RTL 依据 | 触发条件 | 观测手段 |
|---|---|---|---|---|
| R1 | 泵A/泵B 忙时整帧丢弃（hs_busy 门控） | `frame_fifo_pump.v` L88 `wr_valid = wr_en && !wr_full && !hs_busy && !frm_dropping` | 帧到达时上一帧未排空 | `wr_drop_cnt`（泵A=`dbg_pfwd_drop`，泵B=`dbg_prev_drop`） |
| R2 | 栈 TX 帧间无 IFG | `udp_tx.v` 状态机 st_crc→st_idle→(3拍边沿检测+trig)→st_check_sum(4拍)，帧间仅 ~10 拍 vs IEEE 要求 96 拍 | 全速回显（任何速率都有，低速下 PHY 已容忍，线速未知） | E4 Wireshark 帧到达间隔 + 回帧计数 |
| R3 | `async_fifo_2048x8b` 溢出不可见 | 顶层 L436 `.full()` 空接；深 2048 < 2×1466 | TX 被 ARP/ICMP 占线时第 2 个 UDP 帧到达 | 无直接计数 → **实验时静默 ARP/不 ping/关无关流量**；间接：`dbg_pfwd_wr` 与 `dbg_pk_frames` 差额 |
| R4 | **`udp_tx` 长度锁存仅 idle 态**——TX 忙时到达的 `rec_pkt_done` 边沿丢失 | `udp_tx.v` L120 `pos_start_en && cur_state==st_idle`；且 FIFO 无帧边界，错位后新旧帧粘连 | 背靠背下 rec_pkt_done 落在 TX 发送窗口内 | **过载硬冻结/数据损坏的第一候选机制**；E2 冻结时抓 `dbg_pfwd_stuck_cnt`（泵A看门狗）+ 对账 `pfwd_wr` vs `pk_frames` 定位是栈内错位还是泵丢帧 |
| R5 | `time.sleep` 不能做 µs 级 pacing | Windows 高精度定时器 ~500 µs 分辨率（§2.1 同因） | 任何用 sleep 控制帧节奏的尝试 | §六改造：忙等/批量校正，不用 sleep |

> R4 与"过载只降速不冻结"路线的关系：R4 若坐实，修复方向是给 `udp_tx` 加"忙时锁存 pending start"或把 FIFO 换成带帧边界的帧队列——后者正是 **D 线 D2 队列后端（DDR 化）的接口语义**，一条线修两个问题。

## 五、实验矩阵（E1→E5 阶梯逼近线速）★ v2 重写

> 设计原则：每级实验只引入**一个变量**，且**先静态预算（§三）→ 再实验验证**。板端用现有判决位流（build9v/w，三域 ILA + 六段差分链），无需重新构建。

### E1 · 单进程 gap=0：Python 发送循环上限（~10 分钟）

```powershell
$env:PYTHONUTF8 = 1
cd D:\FPGA\project_9
# 基线复现（应得 ~19.3 Mbps，确认环境无回归）
python scripts\json_storm.py testdata\session_full.jsonl --gap-ms 0.1 --limit-bytes 1048576
# E1：去掉 pacing（脚本已支持，gap_s=0 即跳过 sleep）+ 吃满 MTU（chunk 修正为 1466！）
python scripts\json_storm.py testdata\session_full.jsonl --gap-ms 0 --chunk 1466 --limit-bytes 10485760 --out out\recv_e1.bin
```

**为什么先做**：零改造成本，直接测出 Python `sendto` 循环天花板。
**判读**：结果 = min(Python 循环速率, 线速)。预期 400–700 Mbps（每帧 struct.pack+切片+dict+syscall 约 16–30 µs）。
- ≥900 Mbps：Python 不是瓶颈，直接进 E3。
- 400–700 Mbps：记录为"PC 单进程上限"，进 E2。
- 完整性必须 100%+SHA（此速率低于线速，板端 drop 应=0；若有丢 → R1/R3/R4 任一被提前触发，按 §四对照）。

### E2 · 4 进程 gap=0：背靠背线速冲击（~10 分钟）

```powershell
python scripts\json_storm.py testdata\session_full.jsonl --gap-ms 0 --chunk 1466 --parallel 4 --limit-bytes 10485760 --out out\recv_e2.bin
```

**为什么**：4 进程 × 各自端口 → 到达率冲过 81.3k fps → NIC/线速背压 → **板端以千兆线速受击**。这是对 §三定论 2-b 的直接验证，也是 R4（冻结候选）的触发场景。
**判读**（关键数字全要）：
- 发送速率（应 ≈953–957 Mbps，被 NIC 背压）；
- 到达率（预期 98–99.5%，丢 0.5–2%）；
- 板端对账：`dbg_prev_drop`（泵B 丢弃数）+ `dbg_pfwd_drop`（泵A）应与 PC 丢失数**算术闭合**；
- `dbg_pfwd_stuck_cnt` = 0（不冻结）；若 >0 → R4 机制坐实，冻结复现即抓（看门狗已就位）。
- **若 100% 到达**：静态预算的"零裕量丢帧"预判被证伪 → 说明到达抖动被上游流水平滑了，更好；三问答案不变。

### E3 · 受控节奏：目标 ≥900 Mbps 且 100%+SHA（需 §六 A6 改造，~半天）

```powershell
python scripts\json_storm.py testdata\session_full.jsonl --pace-us 12.5 --chunk 1466 --limit-bytes 10485760 --out out\recv_e3.bin
```

**为什么**：§三定论 2-a——帧周期 12.5 µs > 泵B 服务 12.21 µs，让每级都留裕量，**这是"不改 RTL 拿到无损线速"的唯一路径**，也是给实际场景的推荐工作点。
**判读**：速率 ≥900 Mbps 且 100%+SHA、`dbg_prev_drop`=0 → **达标判据 E-E3 过**；三问①的最终证据（pacing 开 → 900+，pacing 关+单进程 → 400–700，pacing 关+sleep → 19.3，三层对比 = 瓶颈归 PC 侧的完整证据链）。

### E4 · Wireshark 独立回程测量（排除 Python 接收瓶颈，~15 分钟）

```powershell
# 抓包过滤：udp.port==1234（回显方向 src=192.168.1.10）
# 统计：Statistics → I/O Graphs（速率曲线）/ Capture Summary（帧数）/ 帧到达时间差
```

**为什么**：json_storm 的接收是发送进程内的 Python 线程（recvfrom + dict），千兆回程 81k fps 时它自己可能丢/慢——**表 10 号嫌疑必须独立测量排除**，否则 E1–E3 的"到达率"被接收端污染。Wireshark 走内核 Npcap 缓冲，不受 Python 限制。
**判读**：Wireshark 帧数 ≥ Python 收到数 → 差额 = PC 接收端丢失（答案归 PC，三问①再加一层证据）；Wireshark 帧到达间隔分布 → 顺带验证 R2（板端无 IFG 的帧 PHY 是否放行、到达是否背靠背）。

### E5 · 全链路计数器对账（判决定稿，跑完 E1–E3 后统一做）

用 `verdict_capture.ps1` 抓六段差分链，与 PC 侧收/发数对总账：

```text
PC发送 N ─→ pfwd_wr ─→ pfwd_rd ─→ pk_frames ─→ echo_b_rx ─→ echo_b_tx ─→ unpack_frames ─→ prev_wr ─→ PC收到 M
           (+pfwd_drop)                                    (+echo_b_ovf_cnt)              (+prev_drop)
闭合条件: N = Σ各级计数 + Σ各级drop = M + 总丢弃
```

**为什么**：速率数字回答"多快"，对账回答"丢在哪一级"。判定报告的数据完整性章节直接引用这张对账表。

## 六、PC 端改造规格（A 组 · 本期做）

| # | 动作 | 规格 | 预期 |
|---|---|---|---|
| A1 | `--gap-ms 0` 去 pacing | 已支持（E1 即测） | 19.3 → 400–700 |
| A2 | 发送循环瘦身 | 预构造全部分片包（pack+切片移出循环），循环体只剩 sendto + 计时 | 每帧省 5–10 µs |
| A3 | 发送 socket 设 `SO_SNDBUF`（现仅接收设了 8 MB） | 4 MB | 减少 sendto 阻塞抖动 |
| A4 | **chunk 1360 → 1466**（v1 写 1472 是错的） | 1466 = 1472 − 6 脚本头；**1472 会 IP 分片 → 板端无分片重组 → 全丢** | +7.8% 载荷效率 |
| A5 | 多进程 `--parallel N` | 已实现 | E2 用 |
| A6 | **新增 `--pace-us`：忙等节奏器**（E3 的钥匙） | 不用 sleep（R5）；每帧发送前 `perf_counter()` 忙等到目标时刻（12.5 µs/帧），或每 8 帧批量校正一次摊薄 CPU；单独 `--parallel` 时各进程按 N 倍周期独立节拍 | 精确控制到 ≥ 泵B 服务时间，实现"有裕量的线速" |
| A7 | 接收端独立进程（可选） | 把 rx 线程拆为独立进程，与发送循环脱离 GIL 争用 | E4 已用 Wireshask 独立验证时，此项为锦上添花 |

## 八、判定报告三问回答模板 ★ v2 新增（用户点名要求）

> 每问一表：结论 + 证据（实验编号）+ 讲给导师的一句话。跑完实验填数字即成文。

### 问题①：目前的传输实验是 Python 脚本限制速率吗？

| 层 | 实测速率 | 证据 | 结论 |
|---|---|---|---|
| 带 sleep（性能档现状） | 19.3 Mbps | 09-21 评测 + §2.1 算术（561 µs/帧 ≈ 定时器分辨率） | **是，sleep 是第一层限制** |
| 去 sleep 单进程 | ___ Mbps（E1 填） | E1 | Python 循环（syscall+解释器）是第二层限制 |
| 4 进程背靠背 | 发送 ___ / 到达 ___ Mbps（E2 填） | E2 + 板端 drop 对账 | PC 侧天花板突破后，限制移交板端零裕量级 |
| 受控节奏 | ___ Mbps（E3 填） | E3 + drop=0 | pacing 由脚本控制 → **速率已由设计决定，不再由脚本"意外"决定** |

**一句话结论（预填，实验后修正）**：是——19.3 Mbps 完全由 PC 侧脚本造成（sleep ×31 倍 + 循环开销 ×1.5–2.4）；硬件实际能跑 ~950 Mbps。

### 问题②：实际场景中需要用什么协议传输？

**定案（无需实验，架构文档已有依据）**：
- **传输层 = UDP**（payload ≤1472 B/帧，业务净载荷 ≤1466 B + 6 B 应用头）：prj 栈只有 ARP/ICMP/UDP（无 TCP）；Aurora 板间干线由 FPGA 封 64b/66b 自定义帧（决策 #10/#11），端点接入一律千兆网口（#13）。
- **可靠性 = 应用层**：`json_reliable.py` 选择性重传滑窗已验证（交付 100%/0 重传）——"FPGA 快路径 + 传输层可靠性"的架构叙事（#12）。
- **节奏 = 发送端 pacing 或板端队列**：E3 证明前者（≤950 Mbps 无损）；背靠背满速需板端帧队列 = D2 交付物。**TCP 不引入**（栈改造大、拥塞控制反而压制 FPGA 快路径优势；如导师要求，答辩口径 = "UDP+ARQ 等价实现可靠传输，且可定制重传策略适配 fabric"）。
- **帧长 = 1466 B 冻结**（§九契约），不做 jumbo。

### 问题③：prj9 的硬件设计部分是否限制了速率？

| 级 | 静态上限（§三） | 是否当前瓶颈 | 证据 |
|---|---|---|---|
| RGMII RX / 栈 RX 解析 | 线速跟随 | 否 | RTL 逐拍流水 |
| async_fifo | 透明（风险 R3） | 否（避混流即可） | §四 |
| 栈 TX | 957 Mbps | 零裕量级，与泵B 同档 | udp_tx.v 拍数核算 + E2 |
| 帧泵A | ~1.19 Gbps | 否（裕量 20%） | §三表 #5 |
| Aurora ×2 + B 回显 | ~9.6 Gbps | 否 | 流水核算 |
| **帧泵B** | **~959 Mbps** | **全链路节拍器（零裕量级）** | §三表 #8 + E2 drop 对账 |
| PC 接收 | 待测 | 候选 | E4 |

**一句话结论（预填，实验后修正）**：限制，但限制点就在千兆口上限上——帧泵B（回程 125 MHz 逐字节泵出）把全链路卡在 ≈959 Mbps，与千兆口净载荷上限 953 Mbps 只差 0.6%；受控节奏下无损达标，背靠背满速需帧队列化（= D 线 D2 的交付物，改造方向已在 §四 R4 注明）。
