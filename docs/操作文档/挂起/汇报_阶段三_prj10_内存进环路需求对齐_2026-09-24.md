### 1.3 导师 09-24 的新要求（原话）

> 现在需要把内存的读写功能加进去，也就是实现以太网数据先写到内存，再从内存读出来。目前比较关键的是多读几个数据，这样数据存的地址会不一样。
> 具体操作步骤：1. 以太网发送的数据先写到内存中；2. 内存再选定其中某一个地址（每次可以选不一样的地址），把数据读出来；3. 通过光回环，再存到内存里；4. 最后从内存读出来，通过以太网发回去。
> 核心目的就是把内存的读写，特别是随机读写的这个功能放进整个环路。

**我的转写**：在现有「以太网 ↔ 光回环」通路的光口**两侧**，各插入一级 DDR4 内存（**写 + 按地址读**），使数据面从"流式直通"变为"**按地址存储转发**"。

## 二、需求理解

### 2.1 要的不是"更大的 FIFO"，而是"内存语义"

现有 `frame_fifo_pump` 是 BRAM 做的 FIFO：地址对用户不可见，读出顺序恒等于写入顺序。导师强调"**多读几个数据、地址不一样**"，本质是要证明**读出顺序可以不同于写入顺序，而每一帧的内容仍与其所在地址严格对应**。

| 维度 | 现在（帧泵 = FIFO 语义） | 导师要求（内存语义） |
|---|---|---|
| 地址 | 硬件自行递增，对外不可见 | **地址是显式、可指定的一等参数** |
| 读出顺序 | 必然 = 写入顺序 | **可指定，可不同于写入顺序** |
| 数据归属 | "第 N 个出来的那份" | "**存在地址 X 的那份**" |
| 后续价值 | 只能做单一队列 | 多队列 / 优先级 / 拥塞迁移 / 描述符环的地基 |

### 2.2 加入两级内存后的数据流（本期形态）

```text
 PC
  │ 千兆网线 · UDP/JSON 帧
  ▼
 [GE1 RGMII / YT8531] → [以太网栈 ARP/ICMP/UDP] → 回显帧
  │ 8b
  ▼
 [泵A frame_fifo_pump]   帧感知 CDC · BRAM 2048B 单帧中转
  │ 8b @user_clk
  ▼
 ④【内存桥① 写】槽号 = 写帧计数器 · 地址 = ING_BASE + slot×SLOT   ← 新增
  ▼
 ⑤[(DDR4 4GB · MIG)  INGRESS 槽区]                              ← 新增
  ▼
 ⑥【内存桥① 读】槽号 = 读地址选择器（可指定）                     ← 新增
  │ 8b
  ▼
 [pack 8→64] → [Aurora A · GT X1Y11] → 笼A(Y11) ══ LC 跳线 ══ 笼B(Y9)
  ▼
 [Aurora B · GT X1Y9] → 回显（整帧存储转发）
  ▼
 笼B(Y9) ══ LC 跳线 ══ 笼A(Y11) → [Aurora A RX] → [unpack 64→8]
  │ 8b @user_clk
  ▼
 ⑱【内存桥② 写】同①结构                                    ← 新增
 ⑲[(DDR4) EGRESS 槽区]                                      ← 新增
 ⑳【内存桥② 读】槽号 = 读地址选择器                           ← 新增
  │ 8b
  ▼
 [泵B frame_fifo_pump] → [RGMII TX] → PC
```

**关键点**：现有以太网栈、泵、pack/unpack、Aurora 全部**零改动**，只在 `泵A→pack` 与 `unpack→泵B` 两处各插一级"写 + 读"内存。

> 完整拓扑（含时钟域 / 接口契约 / 内存地址映射）见 [[架构_cross_内存进环路拓扑_2026-09-24]]。

### 2.3 「多读几个数据、地址不一样」——两种读法，**请导师确认**

| 读法 | 含义 | 能证明什么 |
|---|---|---|
| **读法一**：写侧分槽 | 多帧各写不同地址，读出仍按写入顺序 | 只证明"地址空间被用上了"，本质仍是 FIFO |
| **读法二**：读侧挑地址 | 读侧每次指定不同地址，**读出顺序可不同于写入顺序** | 才叫「**随机读写**」——内存 ≠ FIFO 的决定性证据 |

**我的理解**：导师要的是**读法二**（"内存再选定其中某一个地址，每次可以选不一样的地址"）。若如此，验收判据必须包含"**乱序读出仍逐帧正确**"。

### 2.4 导师需求的意图理解（我的推断 · **请导师确认**）

> 以下是学生对"为什么是这四步"的推断，**不是导师原话**。写出来是为了让需求方向对齐，请导师判断是否与本意一致。

**推断一：这套验证逻辑对单板与多板同样成立。**

四步把内存放在了**光段的两端**：

```text
单板（现在）： 以太网 → 内存 → [光段: 笼A→纤→笼B→纤→笼A] → 内存 → 以太网
多板（将来）： 以太网 → 内存 → [光段: 板①A ←─纤─→ 板②A]   → 内存 → 以太网
```

同一套数据面逻辑，**只换接线**——单板双笼回环是把"未来的板间干线"就地折回自接。所以单板实验的结论可以直接外推到多板。

**边界（必须说清）**：它能外推的是"**内存进出 + 光段收发 + 64b/66b 编解码往返**"；**不能**外推跨板链路建立（两条 `channel_up` 独立）、转发决策与查表、多路径寻址——那些属于后续阶段。

**推断二：第 2 步的"选地址"是控制面的第一个切入点，也是队列调度的种子。**

- N 个队列 = 内存中的 N 个地址段；**调度器 = 决定"这次从哪个地址段读"**；拥塞迁移 = 改变地址段映射/权重。
- 所以"每次可以选不一样的地址"不只是寻址技巧，而是**多队列调度的雏形**（对应开题报告 §4.3「队列组（每端口独立队列）→ 调度器」）。
- **推论（可执行）**：若目标包含"为软核控制打基础"，**读地址就应做成软件可写的寄存器**（上位机命令字或 MicroBlaze 寄存器），而不是硬连线 LFSR——后者只证明"内存不是 FIFO"，与控制面无关。

## 四、★核心分歧：内存读写由谁执行？

这是本次最需要导师拍板的一件事，因为**它决定工程量、决定与原阶段三/四计划的关系**。

### 4.0 分岔口**只有一处**（先说清楚再谈选项）

```text
     ┌──────────── 共同部分（占大头，选哪条路都不浪费）────────────┐
     │ 以太网栈 / 帧泵 / pack / unpack      （prj9     ✅ 已有）    │
     │ MIG/DDR4 校准与上板                  （prj4     待做）       │
     │ DDR4 引脚约束（已双来源交叉验证 107/107）                     │
     │ 地址规划 / 槽结构 / 判据设计 / 主机侧校验脚本                 │
     │ MicroBlaze 作控制面（下参数、读计数器）                       │
     └──────────────────────────┬──────────────────────────────────┘
                                │
                    ★ 分岔口：数据怎么进出 DDR ★
                                │
              ┌─────────────────┴─────────────────┐
              │                                   │
      路线 A：自研 RTL AXI4 主机            路线 B：AXI DMA + MicroBlaze
      （数据面自主，AXIS → AXI4 主机）      （软件配搬运，学长那套骨架）
```

> 分岔口**不在**"要不要内存"，也**不在**"要不要软核"——只在"**数据怎么进出 DDR**"这一层。

### 路线 A：纯 RTL 数据面（自研 AXI4 主机）

- 内存桥是纯 RTL 模块，自己产生地址、发 AXI4 突发；**MicroBlaze 只做控制面**（下发读地址 / 模式 / 阈值，读回计数器）；
- **优点**：数据面不依赖软核，延迟确定；与现有纯 RTL 以太网栈 + Aurora 风格一致，"只增不改"；已有 `mig_verify_top.v` 证明这条路可行；与开题报告"板内双平面：数据面纯硬件 + MicroBlaze 控制面"的定案一致；
- **缺点**：偏离阶段三原文的"MicroBlaze + C 代码"；AXI4 主机需自己写（但有范例）。

### 路线 B：MicroBlaze + MIG + AXI DMA（原阶段三/四计划）

- 按 Block Design 挂 MicroBlaze，用 C 代码配置 AXI DMA，在 DDR4 与前端之间搬运；
- **优点**：与任务分工原文一致；复用 Xilinx 驱动 API；"软硬件协同"在答辩上是加分项；描述符环天然支持随机地址与多队列；
- **缺点**：把原定**阶段四**的 AXI DMA 提前引入，一步跨两个大变量；现有以太网栈是 **8bit GMII 字节流 + 帧泵**、不是 AXIS 接口，接 DMA 需要额外适配；MicroBlaze 参与数据面会带来带宽与延迟的不确定性；现有顶层是纯 RTL，混入 Block Design 较繁琐。

### 路线 C（我的建议）：先 A 跑通判据，再演进到 B

- **第一步用路线 A**：把"内存进环路 + 随机读写"这条**功能判据**先拿到手（工程量可控、风险最低）；
- **再演进到 B**：多队列 / 描述符环阶段再上 MicroBlaze + AXI DMA，那时 MicroBlaze 的控制面作用才真正体现——**这也正好落在原阶段四的位置上**。

| | 路线 A | 路线 B | 路线 C（建议） |
|---|---|---|---|
| 数据面执行者 | 纯 RTL | MicroBlaze + DMA | 先 RTL，后 DMA |
| 与原阶段三 | 有偏差（需说明） | 一致 | 先偏差后回归 |
| 工程量 | 小 | 大 | 分两步 |
| 风险 | 低 | 中高（两个新变量） | 低 |
| 随机地址 | 需自研地址生成器 | 描述符环天然支持 | 先自研，后描述符 |
