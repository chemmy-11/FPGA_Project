## 1. 课题定位与需求

### 1.0 双主线定位（本节是全局最重要的一节）

本课题同时服务两个目标，**它们共用同一张数据通路，但边界必须清晰**：

| | 学位主线 | 应用载体 |
|---|---|---|
| 名称 | 面向边缘多节点协作的 FPGA 高速互联网络平台设计与实现（开题报告 v2） | 实验室本地 AI Infra 系统（本报告） |
| 载体 | **KU060 ×2 组双链路交换网络（第三块板可选扩展）** | 服务器 LLM 服务 + PC 编排 + 树莓派 Agent |
| 贡献点 | **互连层**：fabric 转发引擎、队列缓存、拥塞感知调度（优先级/反压/多路径）、多节点验证 | 提供真实业务负载与长期运行观测 |
| 验收 | 论文第五章实验全部产出 | 本报告 G1–G6 |

**一张通路，两种负载**（这是两套叙事的物理统一性）：

| 负载类型 | AI Infra 侧的形态 | FL 侧的形态 | 对互连层的要求 |
|---|---|---|---|
| 小包高频流 | LLM token 流（SSE）、Agent 心跳/状态 | FL 控制消息 | 低延迟、低抖动、优先级隔离 |
| 大包批量流 | 会话记录回传、工具结果 | 梯度上传、模型广播 | 带宽、队列（吸收突发）、反压 |

**红线**：答辩时的创新点表述必须落在 FPGA 互连层（转发/队列/调度/多节点）；nginx、Ollama、编排容器属于工程载体，写入论文时不作为贡献点，只作为验证平台的组成部分。

### 1.2 设计目标（可验收）

| 编号 | 目标 | 验收判据 |
|---|---|---|
| G1 | **可用**：使用者通过统一入口获得流式回答 | 端到端可用；首 token 正常返回、长回答不被超时切断 |
| G2 | **不被打死**：任何单一使用者/Agent 无法独占或压垮 GPU | 超限请求得到明确反馈，而非静默排队至超时 |
| G3 | **可观测**：每次调用可归因 | 可回答「谁在用 / 用了多少 token / 慢在入口还是推理」 |
| G4 | **可协作（预留）**：为多 Agent 并发 tool call 预留入口与通道 | Agent 入口与优先级标记就位，不阻塞后续接入 |
| G5 | **可演进**：换模型 / 加卡 / 加节点不改调用方 | 调用方只依赖统一入口地址 |
| G6 | **不冻结**：过载只降速，不宕机 | 持续过载与瞬时冲击下 `ping` 不归零、无需重烧恢复（F0 的验收口径） |

> **G6 的意义**：过载在真实 AI 负载中是常态而非异常（fan-in 汇聚、批量回传、多 Agent 同时 tool call）。一个会硬冻结的平台不能承担「交换核心」的定位，因此 G6 与其余各条同为**可用性级目标**。

### 1.3 明确不做（本期范围外）

- ❌ 监控大盘、消息队列集群、多实例负载均衡、多模型路由、跨机房
- ❌ 多 Agent 协作推理本身（论文中多 Agent 是**验证场景**，不是被实现的智能体系统）
- ❌ 面向公网的服务暴露（仅内网）
- ❌ 完整联邦学习系统（FL 只做梯度传输基准实验：Pi5 上浅层 ResNet + CIFAR-10，梯度经 FPGA 通路回传，测单轮通信延迟）
- ❌ **线速转发**。目标负载（token 流）比千兆端点低三个数量级；**在带宽维度上与交换机竞争既无必要也赢不了**（§3.3.2）。差异化在延迟确定性、硬件级可观测性与可编程调度
- ❌ **（v0.4 新增）SFP+ 口承载以太网**。端点全部经千兆网口接入后，`prj7` 的 1000BASE-X 前端**不需要复活**，SFP+ 通道专用于板间 Aurora 干线
- ❌ **（v0.4 新增）WAN/多跳扩展的工程实现**。第三块板的多跳拓扑属"展望"，不进本期验收

## 2. 总体架构与拓扑

### 2.1 今天真实存在的连接（2026-09-21 实测事实）✅

```text
  PC（192.168.1.102，Windows，Python 发包脚本）
   │  网线直连 · 千兆铜口 GE1（RGMII / YT8531 / rgmii_rx_fix2 IDELAY 1250ps）
   ▼
  KU060-①（xcku060-ffva1156-2-i）—— 唯一在做实验的板
   ├ 以太网栈 UDP（判据：ping 20/20 全<1ms · udp_verify 12/12 · 压力 36/36 逐字节一致）
   ├ 帧泵 store-and-forward（pack 队列 16 深，0.4% 丢失根因已修复）
   └ Aurora 64b/66b @10G 通道 A（X1Y11）── SFP+ 笼 A(Y11) ══ LC 跳线 ══ 笼 B(Y9) ── 通道 B（X1Y9）
        数据在同一块板内出光、渡纤、再回来（判据：全量 10MB 100% + SHA256 一致，历史首次）

  KU060-②：已到位，尚未参与任何实验（无位流、无连线）
  服务器（5090）：在普通内网，与上图无耦合 → LLM 服务（软件轨 S1）不依赖 FPGA，可立即开工
  树莓派：✅ 在位可用，但尚未接入任何通路
  GE2：引脚已在 KU_IO.xdc，从未 bring-up
  SFP+ 模块：✅ 4 只 10G 模块 + 4 条 LC 跳线已在手（事实 D）→ 双链路可直接组网
```

**读法**：目前唯一穿过 FPGA 的真实业务数据是 PC 发出的 UDP/JSON，且**全部在同一块板的两个光笼之间往返**。**「真光链路」证明的是光路与 64b/66b 编解码正确，不是跨板互连**——跨板组网是本版 L1 判据。

### 2.3 接入拓扑的四级递进（每级都是前一级的超集，可回退）

| 阶段 | 拓扑 | 判据 | 前置 | 论文去向 |
|---|---|---|---|---|
| **P1 单板双笼**（现状 ✅） | 一块板的 A/B 笼外部跳线 | 数据渡光两次 100%+SHA | 无 | 5.2 链路验证 |
| **P2 单板双端点**（最便宜的"交换"） | ①GE1=PC，①GE2=服务器；FPGA 成为 PC↔服务器唯一通路 | 服务器↔PC 双向 ping + udp_verify 穿板通过；**LLM 流量确实经过 FPGA** | **GE2 bring-up** | 5.5 端到端 |
| **P3 双板双链路**（L1+L3，多路径主场） | 两板各用 A/B 两笼组成**两条平行 10G 链路**；②GE1=树莓派 | 两条 `channel_up` 常亮；跨板双向转发通过；双链路按流哈希分流；单链断开 <10ms 重路由 | **无（4 只模块 + 2 根跳线已在手）** | 5.2 / 5.4 / 5.5 |
| **P4 三节点多跳**（可选扩展） | 两板各上联 ③ 号板，形成三节点 fabric | 跨两跳转发判据；多节点调度 | **第三块 KU060** | 5.4 规模讨论 |

> **原则一：编排层持路由开关。** FPGA 通路异常时，流量降级回普通内网——**FPGA 是增强路径，不是系统的生存依赖**。
> **原则二：端点侧零改动。** 端点始终是标准以太网设备，fabric 内层承载的仍是完整以太网帧（§3.3.6）——这是「可演进」G5 的唯一实现方式。
> **原则三（v0.4 新增）：不引入新协议栈。** 服务器与 PC 都走千兆网口 → 复用已 ✅ 验证的「以太网栈 + Aurora 桥」通路（事实 C）。**任何需要新造前端（SFP 承载以太网、万兆以太网栈、PCIe 网卡）的方案一律不做**——它们不产生论文贡献，只产生工期风险。

| 层 | 组件 | 职责 | 状态 |
|---|---|---|---|
| 入口层 | nginx（服务器） | 统一入口、TLS、鉴权、分池限流、流式透传、访问日志收口 | 🔧 |
| 推理层 | Ollama + 27B 级 Q4（5090） | 本地推理，数据不出内网；按显存预算控制并发 | 🔧 / ⏳ |

### 2.5 三条正交切分（设计核心）

**切分一：控制面 / 数据面**

| | 控制面 | 数据面 |
|---|---|---|
| 做什么 | 决策：任务分类、路由、节点选择、能力注册、**fabric 权重与阈值** | 搬运：token 流、Agent 间数据、结果回传 |
| 放哪 | **PC（Docker）+ MicroBlaze（板级）** | **节点直连，经 nginx 收口；节点间走 FPGA fabric** |
| 特征 | 请求量小、可降级 | 量大、延迟敏感 |

> **原则**：**控制面可以挂，数据面必须活。** PC 不可用时退化为规则路由或直连推理；MicroBlaze 不可用时数据面按上次配置继续转发。

**切分二：南北向 / 东西向**

- **南北向**（人 → 服务）：走 nginx，需要鉴权、限流、审计
- **东西向**（Agent ↔ Agent、Agent ↔ 推理）：基线走普通内网；fabric 就位后按流量类别切换，需要带宽、确定性、优先级

**切分三：基线 / 增强**

- **基线 = 普通内网**
- **增强 = FPGA fabric**：按端点逐个迁入，迁入失败回退基线，**系统永不为 FPGA 陪葬**

### 2.6 两个控制面的分工

| | MicroBlaze（板级，Vitis） | PC 编排（系统级，Docker） |
|---|---|---|
| 管什么 | 单板内：链路初始化/状态监控、**队列参数、转发权重、看门狗、帧计数** | 跨节点：任务拆分、路由决策、能力注册、重试、**fabric 全局权重下发** |
| 接口 | AXI4-Lite 配置各 IP；UART 调试输出 | 以太网（经 GE1/GE2）下发参数至 MicroBlaze |
| 失效影响 | 数据面按上次配置转发；看门狗抓冻结 | 系统退化为直连推理（数据面不受影响） |
| 论文去向 | 第四章 4.3 控制子系统 | 第三章 3.4 协调层 |

> **定位**：MicroBlaze 不只是「调试打印」——它是**把纯硬件队列变成可配置对象**的唯一路径（水位阈值、优先级权重、多路径权重都要经它下发）。这也是队列后端走 DDR4 的真正理由（§3.3.5）。

### 2.7 隐私边界（trust boundary）

- **一票否决规则**：判断任务能否使用第三方 API，**先看数据能不能出实验室**，再看模型能力，最后看成本。
- **敏感数据永远在本地 27B 侧闭环**；第三方仅承接不敏感任务。

## 3. 分层设计

### 3.1 入口层（nginx）🔧

| 职责 | 说明 |
|---|---|
| 统一入口 | 对外仅暴露一个地址与端口，隐藏后端 |
| TLS 终止 | 证书只在 nginx，后端走 HTTP |
| 鉴权 | API Key / 简单令牌校验 |
| **分池限流** | 按调用方类别分池：human 低并发保响应，agent 高并发可排队 |
| **流式透传** | 关闭 proxy_buffering、放大 proxy_read_timeout，否则流式退化为一次性返回或长回答被切断 |
| 访问日志收口 | 记录 $request_time 与 $upstream_response_time，区分「卡在入口」与「卡在推理」 |

**配置骨架（示例值，需按实测标定）**

```nginx
upstream llm {
    server 127.0.0.1:11434;      # Ollama；将来加卡/加实例在此追加
    keepalive 16;
}

limit_conn_zone $server_name zone=human_slots:1m;
limit_conn_zone $server_name zone=agent_slots:1m;

log_format llm '$remote_addr "$request" $status rt=$request_time urt=$upstream_response_time';
access_log /var/log/nginx/llm.log llm;

location /human/ {
    limit_conn human_slots 2;          # 人：低并发、保响应
    proxy_pass http://llm/;
    proxy_http_version 1.1;
    proxy_buffering off;               # 流式必须关
    proxy_read_timeout 600s;
}

location /agent/ {
    limit_conn agent_slots 8;          # Agent：高并发、允许排队
    proxy_pass http://llm/;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_read_timeout 600s;
}
```

> **设计说明**：流式响应期间连接一直持有，因此 `limit_conn` 即可实现「同时只有 N 个请求在生成」。
> **nginx 负责门口放行，真正的排队与调度交给推理服务。**

### 3.2 推理层（Ollama + 27B 级 Q4 / 单卡 5090）🔧 / ⏳

**显存预算（32GB）**

| 项 | 占用 | 说明 |
|---|---|---|
| 模型权重 Q4 | 约 16 GB | 27B 半精度约 54 GB，单卡装不下，**必须量化** ⏳ |
| KV cache + 运行开销 | 余下约十几 GB | 与上下文长度成正比，**决定并发路数** |
| 系统 / 容器开销 | 1–2 GB | 预留，避免踩满 |

**关键取舍**

| 决策 | 取舍 | 依据 |
|---|---|---|
| 量化而非 FP16 | 精度略降，换「能跑」 | 54 GB > 32 GB，无选择余地 |
| 27B-Q4 而非 8B-FP16 | 质量优先，速度次之 | 使用人数少、无高并发压力 |
| 并发度 | 单请求速度 ↔ 总吞吐 | 面向人优化延迟，面向 Agent 优化吞吐 ⏳ |
| 上下文上限 | 上下文长度 ↔ 并发路数 | KV cache 预算切分 ⏳ |

> **选型口径**：27B 级 Q4 是 32GB 显存下的质量上限，具体型号以部署时实测为准（吞吐/显存/中文能力三项判据），不锁死在某一版本。

**速度估算（不跑基准的判断法）**：单流解码上限 ≈ 显存带宽 ÷ 模型字节数 = 1.79 TB/s ÷ 16 GB ≈ 110 tok/s，实际打对折 → **几十 tok/s 量级** ⏳

**服务参数（建议起点）**

```bash
OLLAMA_NUM_PARALLEL=1     # 串行：单请求最快；调大则按槽位切分上下文预算
OLLAMA_MAX_QUEUE=...      # 排队上限，防止无限堆积
# num_ctx 需按显存预算设定，避免超长请求挤没并发额度
```

> ⚠️ **陷阱**：开并行度会按槽位切分上下文预算（配 32k 开 4 路 → 每路只剩 8k）。**必须同步调整 num_ctx**。

#### 3.3.2 实测性能基线与瓶颈判定（v0.2 归因已修正）

**实测数字（均为 2026-09-21 实测）**

| 指标 | 实测值 | 口径说明 |
|---|---|---|
| 单流有效吞吐（性能档，10MB） | **19.3 Mbps** | PC 单流天花板（Python 发包侧受限） |
| 受控并行回程（容量档） | **约 22.9 Mbps**（送 70 回 22.9） | 4 进程并行、独立端口 |
| 数据完整性（修复后） | 100% + SHA256 一致 | 载荷 = 本会话真实记录 10.3MB / 7569 片 |
| 损坏 / 乱序 | 0 / 0 | 全程 |
| 链路层线速 | 10 Gbps ×2 通道 | 链路不是瓶颈 |

**瓶颈判定**：v0.2 曾把 ~23 Mbps 写成「store-and-forward 帧泵全链串行瓶颈」。**该归因与代码事实不符**：

```text
帧长 1408 B（1360 B 载荷 + 6 B 头） · 帧泵写侧 8 bit @ eth_rxc 125 MHz · pack 输出 64 bit @ user_clk ≥151.5 MHz

单帧在链路上的传输时间      = 1408 B ÷ 8 B/cycle ÷ 151.5 MHz ≈ 1.16 µs
实测每帧占用全路径时间      = 1 ÷ 23 Mbps ÷ 1408 B × 8  ≈ 488 µs
                                  → 相差约 400 倍
```

**四项候选瓶颈**：

| 候选瓶颈 | 机制 | 可预测后果 | 判别方法 |
|---|---|---|---|
| ① PC 侧发包 | Python 每帧一次 syscall + sleep 精度 + GIL | 20 Mbps 量级**上界** | 换 C/DPDK 或板卡自发流对照 |
| ② 帧泵「单帧在途」 | `frame_fifo_pump.v` 仅 `S_IDLE`/`S_PUMP` 两态，整帧原子周转 | 吞吐 ≈ 1/RTT_泵；与 payload 大小弱相关 | DDR 多帧队列（D2/D3）后复测 |
| ③ 多级 store-and-forward 串联 | 帧泵×2 + pack×3 + B 回显，逐级整帧缓存 | 每级 2–4 µs，合计远小于 488 µs | 三域 ILA 逐级打时间戳 |
| ④ **受控对照实验缺项（真正结论）** | 「送 70 回 22.9」是**开环冲击**：回程无独立发送源，测量值同时受 PC 收包能力与板卡冲突丢弃影响 | **22.9 不是 fabric 容量** | 需**闭环受控**对照：固定窗口 + 流控 |

> **诚实结论**：**23 Mbps 是测量方法给出的下界，不是互连结构的极限。** 在拿到受控对照之前，任何以「吞吐不足」为由的架构投入（尤其 3–6 周的 DDR4）都缺乏依据。

**判别实验（v0.5 起由 D 线承载）**：v0.4 原计划用 BRAM 多帧队列（旧 F2）做廉价判别；09-26 定案 DDR 先行后，判别改在 **D3（DDR 队列落地后用同一套 `json_storm.py` 复测容量档）**完成。**候选①（PC 侧）不依赖任何 FPGA 改动，先行廉价排除**（改发送端实现 / 多进程对照，约 1–2 天）。

```text
若仍 ~23 Mbps   → 瓶颈在 PC 侧（①），fabric 结构无辜
若跳到 100 Mbps+ → 瓶颈是单帧在途（②），D 线顺带解决
若介于两者       → 定位到 ③，逐级时间戳（F4）继续分解
```

> **定案后的读法**：判别结果**不再决定 DDR 做不做**（已定案做），只决定论文「吞吐」叙事怎么写——若 ① 成立，DDR 的论文叙事就只写深队列 / 可配置 / 突发吸收，不写吞吐（§3.3.5 的立项依据本就如此）。

**每跳延迟预算（v0.4 新增，开题报告的可行性依据）**

| 环节 | 估算延迟 | 说明 |
|---|---|---|
| GE RX → 以太网栈 | 1–2 µs | 整帧接收 + 最小解析 |
| 帧泵 → pack 8→64 | <1 µs | 与帧长相关 |
| Aurora TX + 纤 + RX | ~0.3 µs | 线速 + 编解码开销（10G，1408B ≈ 1.16 µs 传输时间内的固定部分） |
| 对端解包 → 转发决策 | 1–2 µs | 查表 + 仲裁（纯逻辑） |
| 出队 → GE TX | 1–2 µs | 与帧长相关 |
| **单跳合计（不含排队）** | **约 5–8 µs** | ⏳ 待 F1 实测标定 |
| 对照：商用千兆交换机 | 5–10 µs | 同数量级 |

> **这条对照必须诚实写进论文**：FPGA 的**转发延迟不比商用交换机低一个数量级**。因此本课题的差异化**不能建立在「更快」上**，只能建立在三项通用交换机给不出的能力上：
> ① **纳秒/微秒级逐跳时间戳**（延迟可分解，而非只有端口级统计）；
> ② **可编程的优先级与水位反压策略**（通用交换机是固定硬件队列，改不了策略）；
> ③ **与上层协作语义耦合的调度**（按 Agent 任务的 `prio`/`flow_hash` 调度，而非只看五元组）。
> **这三项正是 §3.3.3 对照实验要测的东西**，也是答辩时最该主动讲清的一条边界。

#### 3.3.3 负载-容量核算

| 负载 | 典型体量 | 当前 23 Mbps 下表现 | 结论 |
|---|---|---|---|
| LLM token 流（SSE 分片） | ≤5 KB/s/路（几十 tok/s × <100B/事件） | 余量 >100× | **已够** —— 价值在延迟/抖动/隔离，**不在带宽** |
| Agent 消息 / tool call | KB 级/次 | 毫秒级 | 已够；并发 fan-out 时的队头阻塞才是真问题（→ 优先级） |
| 会话记录 / 工具结果回传 | 10 MB | 约 3.6 s（json_reliable 已实测） | 已够 |
| FL 梯度（演示级浅层 ResNet） | 约 40 MB/轮 | 约 14 s/轮 | 勉强可用；D 线（D2/D3）提升后预期 ~3 s 量级，以实测为准，作论文对比点 |
| 模型权重分发（27B-Q4） | 16 GB | 数小时 | **不作为 FPGA 通路需求**，走内网拷贝/人工介质 |

> **结论**：目标负载的带宽需求比千兆端点低**三个数量级**。因此在带宽维度上，FPGA 通路**既无必要也不可能赢过普通交换机**——差异化只能建立在 **延迟确定性、硬件级可观测性、可编程调度** 三项上。

**论文对照实验口径（与开题报告 §5.4 一致）**：

| 维度 | 基线组 | FPGA 组 | 预期可证伪的假说 |
|---|---|---|---|
| 主指标 | token 流 **P99 延迟与抖动**（非吞吐） | 同左 | 微突发下 FPGA 组 P99 更优、抖动更小 |
| 机制指标 | 无逐跳分解能力 | **逐跳延迟分解**（硬件时间戳） | 能把延迟归因到具体跳/队列 |
| 干扰场景 | 大批量（10MB 回传）与 token 流并发 | 同左 | FPGA 优先级隔离消除队头阻塞 |
| 多路径 | 单链路无分流 | 双链路按 `flow_hash` 分流 + 拥塞迁移 | 双链路负载偏差 <10%；单链断开 <10ms 恢复 |
| **假说 H1** | — | — | **在大批量传输干扰下，token 流 P99 延迟上界改善 ≥50%**（数字以实测为准，不预先承诺） |
| **假说 H2** | — | — | 双链路下聚合吞吐 ≥ 单链路的 1.7 倍（理论 2×，扣除调度开销） |

#### 3.3.5 队列后端决策（#13 / D2 已定案：DDR 先行，2026-09-26）

**决策矩阵（留档，答辩叙事用）**

| 维度 | BRAM 帧泵 v2（回退） | DDR4 队列缓存（✅ 主线） |
|---|---|---|
| 工程量 | 小（1–2 周，复用现有帧泵框架） | 中—大（3–6 周，含 MIG 时序收敛风险） |
| 队列深度 | N 帧环形（BRAM 预算内，几十帧 × KB 级） | GB 级 |
| 附加延迟 | 无 | DDR 控制器约 100ns 级（对短帧敏感，D3 实测定 D4 取舍） |
| **吞吐贡献** | **消除单帧在途——吞吐瓶颈主嫌疑** | **对吞吐无直接贡献** |
| 论文价值 | 快速解锁 L1/L2 与调度原型 | **可配置队列基础设施**：描述符环 + DMA + MicroBlaze 可下发水位/权重（对齐 4.2/4.3） |
| 主要风险 | 深度受限，多端点 incast 下可能不足 | MIG 时序、Aurora↔MIG 跨时钟域（→ 风险 #13） |

**定案记录（2026-09-26）**：导师定案 **DDR 先行**。v0.4 的「三步走」与三条触发条件**作废留档**；BRAM v2 的角色改为**回退方案**（D2 时序不过即切）与**可选廉价对照**。接口「队列后端可替换」原则保留——这是 3–6 周投入的下限保险。

**DDR 先行的正确立项依据（答辩口径）**：① 开题报告 **4.2（DDR4 缓存与 DMA）与 4.3（MicroBlaze 控制子系统）是两个独立章节**，D 线同时产出两者；② GB 级深队列与多队列（按端口/优先级）是 L2/L3 拥塞感知调度的**基础设施**，BRAM 深度给不了；③ **不是吞吐**——§3.3.2 已论证（判别实验由 D3 承载，只影响叙事不影响决策）。

**D 线五步**（判据在 §8.1 展开）：D1 MIG 解冻校准复验 → D2 队列后端 DDR 化（描述符环 + CDC + 水位可观测）→ D3 容量判别复测 + 短帧延迟量化 → D4 缓存/直通双模式 → D5 AXI DMA 集成（对齐开题 4.2 的 DMA 部分）。

#### 3.3.6 fabric 包头设计（两级头部）

对齐开题报告的四层协同帧格式（源/目的 ID、序列号、帧类型 + CRC），明确**两级结构**——这是多跳免解析的关键：

```text
┌──────────────────── fabric 头（仅板间链路存在，入板生成 / 末板剥离）────────────────────┐
│ ver(4) │ msg_type(4) │ prio(3) │ flow_hash(13) │ src_port(4) │ dst_port(4) │ flags(4) │
│ hop_cnt(4) │ seq(16) │ tstamp_in(32) │ queue_occ(8) │ rsvd │ crc16 │
├──────────────────────────────────────────────────────────────────────────────────────────┤
│                        内层：完整以太网帧（目的MAC…payload…FCS）——端点侧零改动              │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

| 字段 | 位宽 | 用途 |
|---|---|---|
| ver | 4 | 协议演进 |
| msg_type | 4 | tool_call 请求 / 结果 / 状态同步 / 心跳 / 梯度段 |
| **prio** | 3 | 结果包优先于状态同步；调度器唯一需要读的字段之一 |
| **flow_hash** | 13 | **入板计算一次（内层以太网五元组哈希）**；后续所有跳直接复用 → 中间板**无需解析内层** |
| src_port / dst_port | 各 4 | 端口编址（0=GE1 · 1=GE2 · 2=SFP+A · 3=SFP+B） |
| flags | 4 | 首片/末片/拥塞标记/反压请求 |
| hop_cnt | 4 | 防环 + TTL |
| seq | 16 | 分段重组 + 幂等（与 `json_reliable` 滑窗**共用编号空间**） |
| tstamp_in | 32 | 入队时刻（微秒粒度）→ 逐跳延迟分解的基准 |
| queue_occ | 8 | 逐跳水位回传（拥塞感知的输入） |
| crc16 | 16 | 头完整性（内层以太网 FCS 保留，负责载荷完整性） |

> **为什么入板打标**：千兆端口的五元组解析每板只需在**入端口**做一次；中间板与出板只读 `flow_hash`/`prio`/`dst_port` 即可转发。这使转发流水线做到**与帧长无关的浅逻辑**，是能把 fabric 从「两端点一条隧道」升级为「多跳网络」的结构前提。

```text
现状：PC 192.168.1.102/24（静态）↔ 板卡 192.168.1.10（MAC 00:11:22:33:44:55）

目标：把「PC ↔ 服务器」的流量纳入 FPGA 通路，需要一个两端点都可达的网段
  · 方案甲（推荐）：沿用 192.168.1.0/24

  · 方案乙：FPGA 仅做旁路观测（不承担转发），保留 PC/服务器原有内网直连
      → 代价：FPGA 不在数据路径上，"AI Infra 交换核心"的叙事不成立（仅作过渡态）
```

**三条纪律**

1. **FPGA 单向不通 = 该链路不可用**：PC 与服务器之间一旦改由 FPGA 承载，**必须保留一条可回退的基线路径**（临时插网线 / 换交换机），否则 F0 冻结时两端点直接失联——这违反"FPGA 是增强路径"的红线。
2. **PC 日常上网不共享此网段**：控制机同时要上内网/公网 → 用第二个网卡或 WiFi；**不要在同一网卡上混跑 192.168.1.x 与办公网**。
3. **接入判据（每新增一个端点跑一遍）**：

```powershell
ping <端点IP> -n 20                  # 0% 丢包、全 <1ms（通路）
$env:PYTHONUTF8 = 1

```

## 5. 关键流程与降级路径

### 5.1 人在线问答（P0 目标流程）🔧

```text
使用者 → nginx（鉴权 / 限流 / 流式）→ Ollama 推理 → 流式返回
                    │
                    └→ 访问日志（rt / urt）→ 批量入库 → 观测台
```

> **v0.4 补注**：服务器接入 GE2 后，PC 侧发起的所有 LLM 调用将**物理穿过 FPGA**——这条流程本身就成为 §3.3.3 对照实验的负载源。

**关键点**：超时链路必须一致——客户端超时 ≥ nginx proxy_read_timeout ≥ 推理耗时上限。

### 5.2 Agent 并发 tool call（集成期目标流程）🔧

```text
任务 → task queue（ack）→ orchestrator
                              │ 并发发起 N 个 tool call
                              ▼
             路由开关：基线内网（保底） / FPGA fabric（增强）
                                          │ 优先级 / 反压 / 多路径
                        │                        │
                     边缘节点 A               边缘节点 B
                        │                        │
                        └────── 结果汇聚 ────────┘   ← 扇入：最后一个到达者决定整体耗时
                                  │
                                  ▼
                         汇总 → 生成答复（必要时调 LLM）
```

**并发意味着三件事**：① 总耗时由**最慢的那次**决定（长尾优先于均值）；② 微突发可能瞬间打满端口缓冲；③ 多源同时回同一个目的形成 incast。**这正是 fabric 队列深化与拥塞感知调度要解决的问题，也是论文的核心实验场景。**

### 5.3 降级路径矩阵（必须实现）🔧

| 故障 | 检测方式 | 降级动作 | 影响 |
|---|---|---|---|
| 第三方 API 不可用 / 限流 429 | 错误码 + 指数退避计数 | **回退本地 27B**；必要时拒绝新任务 | 质量降级，可用性保持 |
| GPU 满载 / 队列超限 | 队列长度阈值 | 拒绝并明确返回「当前繁忙」；human 池优先 | 部分请求失败，不雪崩 |
| 边缘节点掉线 | 心跳超时 | 从注册表摘除；任务改派或本地完成 | 协作能力下降 |
| 控制面 PC 不可用 | 注册表心跳 + 健康检查 | **退化为规则路由或直连推理** | 编排降级，数据面不受影响 |
| **FPGA 通路异常（冻结/失联）** | 心跳探针 + 看门狗计数 | **路由开关切回基线内网**；板侧重烧恢复 | 该路径流量绕行，系统不停 |
| **板间光纤断 / `channel_up` 掉** | 链路状态硬门控 | 该跳流量停（判据无旁路原则）；**双链路时另一条可承接（<10ms 重路由）** | 跨板能力降级 |
| **（v0.4）PC↔服务器唯一通路中断** | 端点侧连通性探针 | **物理回退：临时直连网线 / 接交换机**——**必须演练一次** | 两端点失联，直到人工回退 |
| 显存不足 / 溢出到 CPU | ollama ps 显示 CPU/GPU 混合 | 降低 num_ctx 或减少并行度 | 速度下降，避免断崖 |
| 磁盘写满 | 磁盘水位阈值 | 触发轮转 / 清理；降级为采样记录 | 观测精度下降 |

> **原则**：**外部依赖必须有一条不走它的路。** 表里那条"PC↔服务器唯一通路中断"是本版新引入的**真实可用性风险**——把 FPGA 放进关键路径换来真实负载，代价就是这条降级必须演练过（§3.3.9 纪律 1）。

## 6. 容量与资源预算

### 6.1 显存与并发（核心约束）⏳

```text
可用显存 ≈ 32GB − 权重(约16GB) − 系统开销(1~2GB) ≈ 13~15GB
单路 KV cache ∝ 上下文长度
最大并发路数 ≈ 可用显存 ÷ 单路 KV 占用
   · 8k 上下文：约十来路
   · 32k 上下文：仅剩几路
```

> **结论**：**上下文长度与并发路数在抢同一块显存。**

### 6.2 互连层：实测基线 → 判别实验 → 目标设定

```text
实测基线（09-21）：单流 19.3 Mbps（PC 侧天花板）· 受控并行回程 22.9 Mbps · 无损 100%+SHA
判别实验（D3）：  DDR 队列落地后复测 → 才能得到「结构容量」这个数字（候选① PC 侧先行廉价排除）
提升路径：        消除单帧在途（D2 多帧并发）→ 缓存/直通双模式（D4）→ 双链路分流（L3）→ 多端点叠加
目标设定方法：    对「接入端口线速的有效载荷率」设目标（千兆接入 → 数百 Mbps 级），
                  数字以 D3 完成后实测为准，不预先承诺
链路能力：        Aurora 10G ✅（0E0）×2 通道 —— 不是瓶颈，无需投入
```

### 6.3 负载-容量对照（决策用速查）

见 §3.3.3 表。一句话版：**流式负载现在就够；批量负载等 D3 判别；16GB 级分发永不走此通路；带宽不是本课题的战场。**


### 7.3 启动顺序与健康检查 🔧

1. 服务器：Ollama 就绪（模型加载完成）→ nginx 启动 → 自检 /human/ 通路
2. PC：队列 → registry → orchestrator → router
3. 边缘：Agent 容器 → 向 registry 上报心跳
4. **板卡（两台都要）**：位流重烧（易失）→ 链路判据（T23）→ 通路判据（ping）→ 数据判据（udp_verify）
5. 每层提供健康端点；nginx 侧用 upstream 健康检查摘除异常实例

### 7.4 FPGA 板运维四事实（工程已固化）✅

- **位流断电即失**：上电先一键重烧 + 判据（`board_test_*.ps1`）；**双板时两台都要烧**，且判据要覆盖"跨板"这条新路径
- **PC 侧脚本环境**：`PYTHONUTF8=1` 必须；发包前关闭占用 1234 端口的程序
- **过载红线**：容量档过载会触发硬冻结（根因待查，**F0 关键路径**）——F0 闭环前只在已知安全负载内运行
- **判据无旁路**：数据通路必须被链路状态硬门控（`channel_up` 参与复位），否则判据通过不等于真的穿过了链路

### 7.5 磁盘保护（易被忽略）🔧

- 应用日志：logrotate 按天切割 + 保留上限
- 容器日志：max-size / max-file
- 事件库：分区表或按周期归档；设置水位告警
- **自查**：模拟磁盘打满，验证降级路径生效

## 10. 指标口径与观测规范

> **口径先定，再取数。** 口径错，数据越精确越误导。

| 指标 | 定义 | 数据来源 |
|---|---|---|
| 排队时长 queue_ms | 请求到达 nginx 至被转发给推理服务 | nginx 日志 + 服务日志 |
| TTFT | 请求发出至首个 token 返回 | 客户端 / 服务端埋点 |
| 端到端耗时 | 请求发出至最后一个 token | 客户端计时 |
| 吞吐 TPS | 生成 token 数 ÷ 生成耗时 | 服务端输出计数 |
| 并发路数 | 同时在生成的请求数 | 服务端 |
| 拒绝率 | 因限流 / 满载被拒 ÷ 总请求 | nginx 状态码统计 |
| 重试率 | 重试次数 ÷ 首次请求数 | 编排层 |
| 显存峰值 | 采样周期内的最大值 | 系统 / GPU 采样 |
| 采样新鲜度 | 当前时间 − 最新采样时间 | 观测库自检 |
| **fabric 好包率** | 1 − 丢失帧数 ÷ 发送帧数 | 帧计数差分链 |
| **fabric 结构容量** | 在**发送端非瓶颈**的受控条件下测得的有效载荷率 | **D3 判别实验**（现有 19.3/22.9 Mbps 标注为「PC 侧下界」；候选① PC 侧先行排除） |
| **每跳延迟** | `tstamp` 入队与出队时刻差（逐跳） | fabric 头时间戳差分（F4 后） |
| **队列水位峰值** | 采样周期内队列占用最大值 | ILA / MicroBlaze 上报 |
| **token 流 P99 延迟 / 抖动** | 分位延迟与标准差（含干扰场景） | 客户端埋点 + I2 实验设计 |
| **多路径负载偏差** | max(链路负载) − min(链路负载) ÷ 均值 | 双链路帧计数（I4） |
| **故障切换时间** | 断开一条链路至流量在另一条上恢复 | 帧计数时间戳（I4） |
| **冻结恢复次数** | 单位实验时长内需重烧恢复的次数（目标 = 0） | 实验日志（G6 判据） |

**验收门禁通则**

1. 每个阶段先定义判据，再动手；
2. **告警路径必须用极低阈值自测一次**——静默失效比报错更危险；
3. 数字只讲能当场验证的；历史快照须明确标注为快照；
4. **凡引用吞吐数字，必须注明口径与发送端条件**（防止 §3.3.2 那类误读复发）。
