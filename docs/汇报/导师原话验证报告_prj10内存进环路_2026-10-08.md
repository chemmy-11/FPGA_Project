## 〇、一页结论

> **导师 2026-09-24 原话所要求的「把内存读写、特别是随机读写放进整个环路」，已在本板实现并通过上板验证。**

| 原话分解 | 对应硬件 | 上板证据 |
|---|---|---|
| ① 以太网发送的数据**先写到内存** | RJ45 → 以太网栈 → 泵A → 桥① → DDR4 槽区 0x0010_0000 | 板内写计数增量 16 = 发送 16；写槽规则 = 帧计数 mod 256（可复现） |

| ③ **经光回环再存到内存** | 桥① 读出 → pack → Aurora 10G → 光纤往返 → unpack → 桥② → DDR4 0x0020_0000 | 二级内存计数与桥① 读计数一致（每帧穿光一次） |
| ④ **从内存读出经以太网发回** | 桥② 读出 → 泵B → RGMII TX → PC | 收帧 16/16，逐字节一致，字节差异 0 |

| **J3** 每帧内容与其槽位严格对应 | ✅ **16/16** 逐步一致（槽 7 内确为第 1002 帧，等等） |

## 一、导师原话（逐字）

> **导师原话（2026-09-24，见实施单 §1.1 需求转写）**：
> 「以太网发送的数据先写到内存 → 内存里选定某个地址（**每次可选不一样**）读出来 → 经光回环再存到内存 → 最后从内存读出经以太网发回；**核心是把内存读写、特别是随机读写放进整个环路**。」

**需求定界**（实施单 §1.1 原文）：在「以太网 ↔ 光回环」通路的光口**两侧**各插一级 DDR4（写 + 按地址读），数据面从流式直通变为**按地址存储转发**。

| 维度 | 改造前（帧泵 = FIFO 语义） | 导师要求（内存语义） |
|---|---|---|
| 地址 | 硬件自行递增，对外不可见 | **地址是显式、可指定的一等参数** |
| 读出顺序 | 必然等于写入顺序 | **可不同于写入顺序** |
| 数据归属 | 第 N 个出来的那份 | **存在地址 X 的那份** |

**「随机读写」判定式**：读出顺序 ≠ 写入顺序，且每帧内容与其槽位严格对应。**这是内存 ≠ 更深的 FIFO 的决定性证据。**

## 三、验证链路（数据面拓扑）

`~
   PC ──UDP 数据帧──> 192.168.1.10:1234
     │
     ▼
RJ45 → 以太网栈（官方）──回显帧──> 泵A → 桥① ──写──> DDR4 槽区 0x0010_0000
                                       │                     ▲
                                       │ 按槽号读出           │ 写槽 = 帧计数 mod 256
                                       ▼                     │
                           axis_word_pack → Aurora 10G TX ───┘
                                       │
                                  光纤往返（光回环）
                                       ▼
                           Aurora RX → axis_word_unpack → 桥② → DDR4 0x0020_0000
                                       │
                                       ▼
                                  泵B → RGMII TX ──> PC（本地数据口 1236）

   PC ──UDP 命令── 广播 192.168.1.255:1235
        SET_MODE(RND) / READ_SLOT(槽号) / GET_WATERMARK / GET_SLOT_MAP
        应答 P10R 从网口末级直接注入（绕开两级内存桥，避免 ACK 被写进槽里取不出来）
`~

**关键设计**：命令走**广播 IP** ⇒ 被官方栈按「目的 IP ≠ 板 IP」丢弃 ⇒ **零数据面污染**；应答在 **RGMII TX 末级**注入 ⇒ 不受 RND 模式（桥① 不自动读）影响。

## 四、判据的非恒真证明（负向对照）

| 负向轮 | 构造 | 期望 | 实测 |
|---|---|---|---|
| A | 读取计划中**故意删掉 1 个槽**（命令数 = N−1） | 判据报**恰好缺 1 帧**并指出是哪个 seq | ✅ 报缺 1 帧（seq=1258），u_rd_frame 增量 15 |
| B | **重复读同一个槽**（命令数 = N+1） | 集合仍相等（缺 0 多 0）；第二次读同槽观测到「空」 | ✅ 命令 17 / 实取 16 / 额外 0；「空」1 次 |

> **B 的语义**：本设计的读是**一次性取走（破坏性读）**——读完即退休该槽，第二次读同槽返回定长空应答。**这是设计语义，不是丢包**。因此**不能**用「同槽连读两次内容一致」当通过标准。

## 五、本轮同时发现并修复的两处真实缺陷

J5 首次烧录后判据 FAIL，最终定位到**两个真实缺陷**（各有独立记录）：

| # | 缺陷 | 现象 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | **应答帧是以太网 runt 帧** | 板内一切正常（ILA 实测 resp_busy 高 68 拍、FCS 经独立参考校验），**PC 一个包都收不到、网卡错误计数 0** | 帧长 58 字节 < 以太网最小帧 64 字节 ⇒ 网卡硬件静默丢弃 | 按 RFC 894 追加 6 字节填充（不计入 IP/UDP 长度，仅参与 FCS）；**单元 TB 补上最小帧长护栏**，并用旧 RTL 做负向对照（FAIL 45 例）证明护栏有牙 |
| 2 | **写槽游标死锁（RND 模式）** | 命令通道正常、写侧报全成功，读侧却 0 帧；ILA 实测接受计数 334 vs 提交计数 278（**发散 56 帧**） | 写槽号取自「提交计数」，拒收时提交计数不动 ⇒ 游标停在未读满槽上**永久卡死**（RND 无自动读，无人解锁）；上位机按发散的计数推算槽号 ⇒ **不可恢复** | 新增独立槽游标 `wr_slot_ptr`（每帧无论提交或被拒都 +1），槽号分配与提交计数解耦；`stat_wm` 语义不变（W2 判据逐字不变）。**专项回归 `deadlock_regress.py`：灌满 256 槽不读后桥仍存活、读回 16/16，帧量守恒 256+44=300** |

> 详见 [[调试记录/阶段三_prj10_W5命令通道上板缺陷_runt帧_2026-10-08]] 与 [[调试记录/阶段三_prj10_W5写槽游标死锁_2026-10-08]]。

**另外排除的三个假故障**（记录在案，避免误判）：

| 现象 | 定性 | 依据 |
|---|---|---|
| 每次重跑第一轮必丢 14/16 帧 | **PC 侧 ARP 老化**（测试工具问题） | 清 ARP 条目后稳定复现；数据帧是单播，解析窗口内 Windows 直接丢帧。已在引擎加 UDP 单播预热（**不能用 ping**：RND 模式下 ICMP 回包被写进内存取不出来） |
| 负向 B 的 `value16` 整体错位一拍 | **测试工具配对缺陷** | 重复读命令用 `expect_resp=False` 发出、应答滞留，被下一条命令误配。已在发命令前加滞留应答排空 |
| 时序根因的两次常量对照实验无效 | **方法论坑** | 命令 FIFO 被综合成 LUTRAM 宏，**宏对常量传播不透明**——写常量进 RAM ≠ 读出可折叠。验证读路径是否根因必须做**结构性移除**（见时序第三轮记录） |

## 七、复现步骤

`~powershell
# 0) 前提：PC 网卡 192.168.1.102/24，板卡 192.168.1.10，光纤回环已接
# 1) 位流闸门（SHA256 不符就停，不要烧）
Get-FileHash D:\FPGA\prj\project_10\prj_loop\out\aurora_mem_bridge.bit -Algorithm SHA256
# 期望 6ACFF5150AE6794E8BF07C52375ADDA53A6B937192D06E8EDD2A5C6C5A2EA62B

# 2) 烧录 + 体检
cd D:\FPGA\prj\project_10\prj_loop
vivado -mode batch -source scripts\program_loop.tcl -notrace
# 判据: PROGRAM_OK / startup status HIGH / 4 ILA + 1 MIG / 四个时钟在跑

# 3) 数据面回归（SEQ 模式）
ping 192.168.1.10 -n 20                       # 20/20 0% loss
python scripts\udp_verify_ddr.py              # DDR_VERIFY: PASS

# 4) 导师原话验证（终端截图这一屏）
python scripts\mentor_verify.py               # N=16 含负向 A/B

# 5) 死锁修复专项回归（可选，会灌满槽；跑完建议重烧复位）
python scripts\deadlock_regress.py --n 300
`~

> ⚠️ **RND 模式的固有副作用（必读，已用工具自愈）**：RND 下桥① 不自动读 ⇒ **板子无法主动发任何帧给 PC**（ARP 应答也要经「内存→泵B」）⇒ PC 邻居表老化成 `Unreachable`（`Get-NetNeighbor 192.168.1.10` 可见）⇒ **单播数据帧被直接丢弃**，而**广播命令不需要 ARP**、通道一直正常 —— 表现为「命令通、数据丢 14/16」，极易误判为板卡故障或 WLAN 抢路由（**两者都不是**）。
> **工具已自愈**：`j3_random_read.py` 每轮开测前先 `SET_MODE(SEQ)`（板子即可应答 ARP）→ UDP 单播探测刷新邻居表 → 再切 `RND` 正式开测；收尾恢复 `SEQ`。
> 实测（WLAN 全程连接）：连续 4 轮 **全部 PASS**（增量 16/16）。
> 若想彻底免掉 ARP（可选，需管理员）：
> `New-NetNeighbor -InterfaceAlias '以太网' -IPAddress 192.168.1.10 -LinkLayerAddress 00-11-22-33-44-55 -State Permanent`

## 八、结论与后续

**结论**：导师原话的四个环节**全部在真板上取到证据**，判据 J3 / J3′ 全过，负向对照证明判据非恒真。**「内存 ≠ 更深的 FIFO」已由实测确立**：读出顺序与写入顺序不同（逆序对 52），且每帧内容与其槽位严格对应。

**后续（W5 → W6）**：

1. 多轮稳定性复跑（本轮已跑出多次 PASS，但需在干净网络环境下做长稳）；
2. 两级内存的光口两侧对账用 ILA 固化进上板验证单（方法已在 W4/J4 建立）；
3. 写槽满时的 PC 侧策略（补读/降速）——游标死锁已修，但槽满拒收仍是设计行为，上位机应可见；
4. 导师关注的后继路线 B（软核 + C 控制读写位置）接口预留已在契约 §六.4。
