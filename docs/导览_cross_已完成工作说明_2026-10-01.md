## 一、已完成的工作

### 1.1 最小系统跑通（08-11）

- **为什么做这一步**：这块芯片内部**没有**处理器，后续的控制逻辑需要一个"软核"来承担；同时需要把"从画图到板卡跑起来"的完整流程先走通一遍。
- **实现路径**：① 用图形化方式搭一个最小系统（软核 + 本地存储 + 串口 + 总线互连 + 时钟与复位模块）；② 写引脚约束；③ 生成配置文件并烧录；④ 上位机导入硬件规格，把程序下载进去；⑤ 串口查看输出。
- **结果**：串口正常打印，整套流程一次走通。此后这条流程成为本项目的标准开发流程。
- **期间的问题**：第一次烧录后启动状态异常。排查顺序是——先怀疑启动模式引脚，再用一个极简的点灯程序排除调试链路，最后对比两版配置文件的头部信息，发现是**器件型号写成了带 "CIV" 后缀的版本，而实物不带**。改正后一次通过。
- **留下的原则**：硬件参数以**实测**为准，教程与视频只能当参考。

### 1.2 光口物理层自检（08-27）

- **为什么做这一步**：在写协议之前，先确认 4 个光口的**硬件本身**是好的。否则后面一旦不通，无法判断是协议写错还是硬件有问题。
- **实现路径**：① 建独立工程，加入官方的误码测试工具（它自带测试码流产生与检查，几乎不用写代码）；② 配置到实际使用的通道组与 156.25 MHz 参考时钟，并为 10G 速率选择对应的时钟源；③ 用官方例程生成工程，避免自己写高速接口；④ 补上光模块的控制信号——**这是唯一需要改代码的地方**；⑤ 写约束（只约束控制脚，高速差分对由工具自动放置）；⑥ 上板：插光模块，用一根光纤把同一模块的收发短接（或两个模块交叉互连）；⑦ 在界面里灌入已知码流，读误码与信号质量图。
- **判据与结果**：时钟锁定 + **误码为 0** + 信号质量图张开并归档。
- **意义**：这一层确认之后，后续光链路出问题可以直接排除硬件因素，**排障范围砍掉一半**。

### 1.3 光链路协议层（08-31）

- **为什么做这一步**：物理层通了只说明"线是好的"，还需要一个协议层把数据可靠地送上去并判断链路状态。
- **实现路径**：① 配置 Aurora 协议核——线速率 10 Gbps、单通道双向、通道位置 X1Y11、参考时钟 T6/T5；② 生成官方例程，并按本板做适配（指示灯、时钟、复位、光模块控制脚）；③ 先做**芯片内部串行环回**（数据不出芯片，直接绕回自己），以排除光模块这个变量；④ 上板后用片内逻辑分析仪观察链路状态信号与误码计数。
- **判据与结果**：链路建立信号与通道信号均为 1、误码计数为 0。
- **沉淀（后来直接复用）**：同一组高速通道内**只能有一个共享时钟资源**。放第二个协议核时，第一个实例把参考时钟与时钟模块引出来，兄弟实例使用不带这些资源的版本——否则综合阶段会直接报冲突。这条在做双光口时用上了。

### 1.4 以太网口通信（09-04）

- **为什么做这一步**：这是"上位机 ↔ 板卡"的唯一数据入口，后续所有实验都要跑在它之上。
- **实现路径**：① 以官方以太网回环例程为基础移植，保留地址解析、ping、UDP 三个协议；② 针对本板网口芯片的采样时序做处理——本板网口芯片已通过引脚配置在芯片内部完成了收发延时，因此 FPGA 侧不需要再补延时链；③ 上板按三层依次验证：**指示灯 → ping → 数据逐字节比对**。
- **判据与结果**：指示灯亮、ping 通、UDP 回显**逐字节一致**；抓包可见完整的"地址解析请求 / 地址解析应答 / 上位机 UDP / 板卡 UDP"四包链。
- **沉淀**：确立了"三层递进"的验证写法的雏形——只报前两层不算通过。

### 1.5 数据经光链路往返（09-18）

- **为什么做这一步**：让上位机发的数据真的穿过光链路往返一次再回来。这是"**板卡能当中继**"的第一个完整证明。
- **实现路径**：① 把以太网部分与光链路部分拼在一起；② 加两个转换模块，把网口侧的 8 位宽数据与光口侧要求的 64 位宽互相转换；③ 加双向"帧搬运"模块——两侧时钟频率不同（网口 125 MHz、光口 151.5 MHz），必须把**整帧**从一侧搬到另一侧，且保证帧不被截断；④ 上板验证。
- **结果**：ping 与数据比对全部通过。
- **期间修复三个问题**（同一轮集中暴露，逐一定位）：
  1. **每帧尾部丢 1 字节**：搬运模块判断"读空"时用了**提前一拍**的指针值，导致每帧最后一个字节被误判为空而没读出来 → 帧被截断 → 网卡按校验丢弃。改成用当前指针判断。
  2. **接收端对帧中断过于敏感**：数据流中间出现短暂空档就被当成帧结束 → 改为"收满整帧再转发"。
  3. **网口接收相位**：针对本板网口芯片的采样时序做修正。
- **定位方法（值得记）**：先做**整链闭环仿真**——把官方协议栈、双搬运模块、打包解包、光链路模型全部串起来，灌入真实的地址解析请求与 UDP 帧，逐字节比对。仿真稳定复现"第二帧起恒少 1 字节"，据此一眼看出是判断信号用错了拍。**没有一上来就上板反复试。**

### 1.6 真光链路（09-21）— 目前的主力验证平台

- **为什么做这一步**：不再用芯片内部环回，而是**真的插两个 10G 光模块、用光纤跳线连起来**，让数据**两次经过光**（出去一次、回来一次）——这才接近真实组网形态。
- **实现路径**：① 在上一版基础上增加第二个光链路核（处理同一组内共享时钟资源的问题）；② 对端实现**整帧原样回显**；③ 构建"判决用"的配置文件——在三个时钟区域各挂一个片内逻辑分析仪，并在数据通路每一级埋计数器（为逐级对账做准备）；④ 上板跑判据。
- **判据与结果**：指示灯常亮、ping 20/20 无丢包（全 <1 ms）、数据比对 12/12、压力测试 36/36、复测无异常；时序收敛无违例。
- **期间的问题（本项目最典型的一次定位）**：运行到约第 26 帧时，**整条回显路径永久卡死**——重烧才能恢复，且必然复现。定位链条：
  1. 换一种回显实现方式，卡死点**分毫不差** → 说明不是回显实现的问题；
  2. 用片内逻辑分析仪做"尸检"：光链路段的计数器完全平衡（25 / 25 / 25）、误码为 0 → **证明光纤这一段是无辜的**；
  3. 用排除法收敛：帧到达了、发送端正在发、而搬运模块既不写入也不丢弃也不完成 → 唯一自洽的解释是**它的"满"信号被永久置位**；
  4. 读代码找到公式错误：**把二进制计数值与格雷码指针逐位比较**——在累计计数跨过缓存深度回绕之后，这个比较会给出错误结果，且读侧空闲时永远不解除。
- **修复与验证**：改为标准的格雷码满判断；同时补上"忙时到达的整帧不进缓存"的帧原子性、以及两侧复位对称化。**修复前先在仿真里复现了同样现象**（40 帧慢节奏有 16 帧无声消失），仿真通过后才上板——修复后板级判据全部通过。
- **沉淀**：走完了"**板上必现 → 仿真复现 → 修复 → 回归**"的完整流程；并总结出"计数器全对账 + 零触发"是定位卡死类问题的有效组合——**先证明哪一段无辜，再逼出唯一解**。

### 1.7 传输质量评测与丢失定位（09-21）

- **为什么做这一步**：不只看"通不通"，还要看"传 10 MB 一个字节都不能错"。
- **实现路径**：① 写评测脚本——把真实数据切片、每片加序号头，接收端按序号重组并做整体校验；② 分三档跑：慢速（求正确）、单流（求速度）、多进程（求容量）；③ 第一轮发现慢速下仍有 **0.4% 的相邻帧丢失**；④ 换上"判决用"配置文件，用逐级计数器对账定位；⑤ 定位到打包输出环节：该处缓存队列只有 **2 级深**，溢出时把**帧结束标志**一起吞掉了，导致两帧被合并成一帧；⑥ 把队列加深到 **16 级**，重新出配置文件复测。
- **判据与结果**：**10 MB 全量 100%，校验完全一致**（历史首次）；带选择性重传的业务传输层交付率 100%、0 重传。
- **关键认识**：**"通"和"对"是两件事**——0.4% 的丢失在 ping 测试里完全看不出来，只有逐字节校验才会暴露。

### 1.8 传输效率核算（09-29）

- **为什么做这一步**：性能档实测只有 **19.3 Mbps**，比千兆口低了约 49 倍，很容易被误读成"板卡很慢"。
- **实现路径**：① **逐级核算**——读一遍数据通路每一级的设计，算出"一帧在该级要占用多久"，取最大值即为全链路上限；② 得出全链路上限约 **957–959 Mbps**，恰好压在千兆口净载荷上限（约 953 Mbps）之上——说明硬件是**贴着线速设计**的、几乎没有余量；③ 反查上位机：脚本每帧调用了一次系统睡眠，而 Windows 定时器精度只有约 0.5 毫秒，导致每帧被硬拖到 561 微秒；④ 结论：**19.3 Mbps 是上位机脚本睡出来的，与板卡无关**。
- **副产品**：确定**单帧净载荷 1466 字节**——写更大值会触发网络分片，而板端不做重组，整包会被丢弃；并据此规划了五级效率实验（E1–E5），用于逐层确认瓶颈到底在哪一级。
- **意义**：这是"答辩要讲得出原理"的典型——一个难看的数字背后，是一张能逐级拆开、每一级都有依据的预算表。

## 二、正在推进：DDR 两步走

### 2.1 这件事要解决什么

本期核心目标 = **把内存读写放进数据环路**：数据先写入内存，再按选定地址读出。这样内存就成了环路里的一个可寻址环节，而不是只能一路直通。

整件事的分岔口**只有一处**——不在"要不要内存"，也不在"要不要软核"，而只在：**数据怎么进出 DDR**。围绕这一个点，导师给出了两步走的定案（2026-09-30）：

> 建议先走路线 A，先实现功能，然后再加上软核，这种路线 B。

### 2.2 路线 A —— 自写硬件模块直连内存（本期交付）

- **做法**：数据进出内存这一段，用**自己写的纯硬件模块**直接连到 DDR 控制器；"读哪一个地址"做成**软件可写的寄存器**，由上位机下发。也就是说，随机读写的能力不受限制，而控制通路用的是现成的。
- **已完成的部分**：
  - 设计了三层硬件逻辑——一层负责两侧时钟不同的数据缓冲，一层是内存读写主控（主动发起读写、管理地址与数据宽度转换），一层是与帧数据对接的接口；
  - 写了一个**行为级的简化内存模型**（不等真实内存控制器就位），把逻辑先验起来；
  - 用**六个用例**覆盖主要场景：内存校准完成前不应有任何读写活动、写入后逐字节读出一致、乱序读取、非法地址的定长应答、长序列绕回、缓存满时不覆盖未读数据。
- **目前的进展**：六个用例全部通过。
- **期间发现并修复的两个问题**：
  1. **一处逻辑被两个模块同时驱动**——这类问题**仿真器完全不报错**，但**实际综合会把其中一路丢弃**（保留常量、丢掉逻辑），上板后表现为计数器恒为 0。这类缺陷只能靠真综合来判，**光跑仿真查不出来**。
  2. **超长数据帧会把写入流程永久卡住**——已修复并加上长度保护。
- **边界（必须写清楚）**：目前**未建工程、未上板**；仿真所用的简化内存模型会"立即应答"，因此它**只验证了功能逻辑**，真实内存的时序特性（读写往返延迟、突发长度约束）还须接上真实控制器后实测。

### 2.3 路线 B —— 软核 + C 代码控制（后继，不推翻 A）

- **做法**：在路线 A 之上，增加软核处理器与 C 代码来控制读写位置。软核**只下发参数、读取状态，不进入数据通路**——数据仍然走硬件那条快路径。
- **定位**：**B 是后继，不是替代**。它只换数据面的一层、加一个控制面；路线 A 的桥、引脚、时序与判据**全部保留**。它的启动条件是：**路线 A 的功能判据全部通过之后**。
- **为什么不需要返工**：三条接口在路线 A 阶段就按"可替换"的形态预留了——把控制入口从"上位机下发"换成"软核下发"时，寄存器语义不变，只换上层。这也是导师定案"先功能、后机制"能省成本的原因：两步的**共同部分占大头**。

### 2.4 共同前置 —— 内存控制器校准复验

- 板载 DDR4 容量 4 GB。**内存上电后必须先完成一次校准**（控制器自动训练读写时序），校准通过之前不能进行任何读写。
- 该项目前**只差一次上板**：对应的配置文件和探针文件都已在库，离线核查也做完了（时序收敛、引脚与布线结果逐条一致、控制器工作时钟已确认），**校准过程本身无法用仿真替代**——它训练的是芯片与内存颗粒之间的物理时序。
- 校准一旦通过，除了支撑路线 A/B，也顺带为后续"把队列缓存放到 DDR 上去"（让缓存深度从几帧提升到 GB 级）铺好路。
