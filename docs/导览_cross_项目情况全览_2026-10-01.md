# FPGA 高速互联平台 · 项目情况全览

> 本文客观记录项目**已经完成了什么、大致怎么做的、结果怎么确认、现在到哪一步**，供组内了解情况。
> 不含操作步骤，也不含术语教学。

---

## 一、项目概况

### 1.1 课题内容

在 FPGA 上实现一个高速数据交换平台，为实验室的多机协作推理提供机器之间的互联。一条数据的完整路径是：

**计算机 → 千兆网口 → 板卡内部处理 → 10G 光链路 → 对端（或光回环）→ 原路返回 → 计算机**

选择 FPGA 而不是通用服务器做这件事，原因有三：时延可算可复现（不受操作系统调度影响）、协议可以按需裁剪、数据来的多快就处理多快。

### 1.2 硬件平台

| 项 | 情况 |
|---|---|
| 板卡 | 正点原子 KU060 开发板，主芯片 Xilinx Kintex UltraScale **XCKU060**（型号 `xcku060-ffva1156-2-i`） |
| 处理器 | 芯片内**没有**硬核处理器，需要用 FPGA 逻辑搭一个软核来代替 |
| 板载时钟 | 100 MHz 差分晶振（系统主时钟）；156.25 MHz（光口专用参考时钟） |
| 光口 | 4 个，位置记为 A / B / C / D，最高 10 Gbps |
| 网口 | 2 个千兆网口 |
| 板载内存 | DDR4 4 GB |
| 其他 | JTAG 烧录口、串口、若干指示灯；板上共 4 根光纤接口，现有 2 个 10G 光模块与 2 条光纤跳线 |

### 1.3 数据通路

```
   计算机                  FPGA 板卡                        光链路
 ┌─────────┐  千兆网口  ┌───────────────────────┐  10G 光  ┌──────────┐
 │ 上位机   │ ────────► │ 网口收发 → 帧缓存搬运  │ ───────► │ 对端板卡  │
 │ 脚本     │           │        → 位宽转换      │  光纤    │ 或光回环  │
 │          │ ◄──────── │        → 光链路收发    │ ◄─────── │          │
 └─────────┘           └───────────────────────┘          └──────────┘
```

### 1.4 本期范围

**单板闭环 + 把内存读写纳入数据环路**（已与导师定案）。板间组网作为并行的后续方向推进，本期不做。

## 二、已完成的工作

### 2.1 最小系统跑通（08-11）

- **内容**：在板上运行一个软核处理器，通过串口输出信息，同时把整套开发流程走通。
- **实现路径**：图形化搭建处理器最小系统（处理器 + 本地存储 + 串口 + 总线）→ 约束引脚 → 生成配置文件 → 烧录板卡 → 上位机导入硬件规格并下载程序 → 串口查看输出。
- **结果**：串口输出正常。
- **过程中的问题**：最初烧录后启动状态异常。排查后确认是**器件型号选错**——用了带 "CIV" 后缀的型号，而实物不带。改正后一次通过。

### 2.2 光口物理层自检（08-27）

- **内容**：在开发协议之前，先确认光口的硬件本身是好的。
- **实现路径**：建专用工程 → 配置官方的误码测试工具 → 生成官方例程 → 补上光模块的控制信号 → 约束 → 上板插光模块、用光纤跳线连接 → 灌入已知码流，观察误码与信号质量图。
- **结果**：时钟锁定、**误码为 0**、信号质量图已归档。
- **意义**：这一层确认后，后续光链路出问题可直接排除硬件因素。

### 2.3 光链路协议层（08-31）

- **内容**：在板上建立一条 10G 光链路，并能判断链路是否正常。
- **实现路径**：配置 Aurora 协议核 → 生成官方例程 → 约束 → 先做**芯片内部环回**（数据不出芯片）以排除光模块因素 → 上板后用片内逻辑分析仪观察链路状态信号。
- **结果**：链路建立、误码为 0。
- **沉淀**：同一组高速通道内**只能有一个共享时钟资源**，放第二个协议核时需要用不带头时钟的版本——这条后来做双光口时用上了。

### 2.4 以太网口通信（09-04）

- **内容**：板卡能回应 ping，能与上位机收发 UDP 数据。
- **实现路径**：以官方以太网例程为基础移植 → 针对本板网口芯片的采样时序加入相位修正 → 上板按 **指示灯 → ping → 数据逐字节比对** 三层依次验证。
- **结果**：ping 正常，UDP 回显**逐字节一致**。

### 2.5 数据经光链路往返（09-18）

- **内容**：上位机发的数据，经板卡穿过光链路往返一次后原样回到上位机。这是"板卡可作中继"的第一个完整证明。
- **实现路径**：把以太网部分与光链路部分拼接 → 加入**数据位宽转换**（网口侧 8 位宽、光口侧 64 位宽）→ 加入**整帧跨时钟域搬运**（两侧时钟频率不同）→ 上板验证。
- **结果**：ping 与数据比对全部通过。
- **期间修复三个问题**：接收端对帧中断过于敏感（改为收满整帧再转发）、搬运模块判断空满时用错了信号（导致帧尾丢 1 字节）、网口接收相位。

### 2.6 真光链路（09-21）— 目前的主力验证平台

- **内容**：不再用芯片内部环回，而是**插两个 10G 光模块、用光纤跳线连起来**，数据**两次经过光**（出去一次、回来一次）。
- **实现路径**：增加第二个光链路核（处理好共享时钟资源）→ 对端实现**整帧原样回显** → 构建判决用的配置文件（在三个时钟区域各挂一个片内逻辑分析仪，并在通路各级埋计数器）→ 上板。
- **结果**：判据全部通过——指示灯常亮、ping 无丢包、数据逐字节比对一致、压力测试一致、复测无异常。
- **过程中的问题**：运行约 25 帧后链路整体失效。根因是**缓存"满"的判断**在跨时钟计数回绕时出错，导致被误判为永久满。按标准做法重写满判断后解决。这条走的是"板上必现 → 仿真复现 → 修复 → 回归"的完整流程。

### 2.7 传输质量评测与丢失定位（09-21）

- **内容**：不只看"通不通"，还要看"传 10 MB 一个字节都不能错"。
- **实现路径**：写评测脚本（把数据切片、加序号、接收端重组并校验）→ 分慢速 / 单流 / 多进程三档测试 → 发现慢速下有 **0.4% 的相邻帧丢失** → 用计数器逐级相减，定位到打包输出环节 → 该环节的缓存队列只有 2 级深，溢出时把**帧结束标志**吞掉了，导致两帧被并成一帧 → 加深到 16 级 → 复测。
- **结果**：**10 MB 全量 100%，校验完全一致**；带重传机制的业务传输层交付率 100%。

### 2.8 传输效率核算（09-29）

- **内容**：回答"为什么传输速率只有 19.3 Mbps"。
- **实现路径**：逐级核算每帧在各环节的耗时 → 得出全链路上限约 **957–959 Mbps**（恰好压在千兆口净载荷上限之上）→ 反查上位机脚本，发现每帧调用了一次系统睡眠，而 Windows 定时器精度只有约 0.5 毫秒 → 定位为**上位机脚本限速**，与板卡无关。
- **结果**：明确板卡实际接近千兆上限；同时确定**单帧净载荷 1466 字节**——写更大值会触发网络分片，而板端不做重组，整包会被丢弃。
- **副产品**：据此规划了五级效率实验（E1–E5），用于逐层确认瓶颈归属。

### 2.9 内存读写进环路（09-29 起，进行中）

- **内容**：把内存读写纳入数据环路——数据先写入内存，再按选定地址读出。**即导师定案的路线 A**（后续路线 B 见 §4.1）。
- **实现路径**：设计三层硬件逻辑（跨时钟缓存 + 内存读写主控 + 帧接口）→ 先用**行为级内存模型**做仿真（不等真实内存控制器）→ 六个用例覆盖主要场景 → 仿真通过后再接真实内存控制器。
- **目前结果**：仿真六个用例全部通过。
- **期间发现两个缺陷**：一处逻辑被两个模块同时驱动（**仿真器不报错，但实际综合会丢弃其中一路**，会导致计数器恒为 0），一处是超长数据帧会卡死，均已修复。

## 三、结果是怎么确认的

项目对"做成了"有固定口径，避免自说自话：

1. **三层递进**：指示灯（链路建立）→ ping（通路可用）→ **逐字节比对 + 校验和**（数据正确）。只报前两层不算通过。
2. **计数器逐级对账**：在数据通路每一级埋计数器，跑完流量后逐级相减，**差额落在哪一级，问题就在哪一级**。2.7 的 0.4% 丢失就是这样定位的。
3. **数据通路被链路状态硬门控**：链路没建立时板卡对外静默，因此"判据通过"等价于"数据真的走过了整条链路"。
4. **证据留档**：每次判决使用的配置文件与探针文件配套保存，测试产物带时间戳归档，保证事后可复查。
5. **信息来源优先级**：官方例程 > 已上板验证的自家工程 > 板卡手册 > 其他资料。

## 四、当前进展与后续

### 4.1 正在推进：DDR 相关（导师定案的两步走）

本期核心目标 = **把内存读写放进数据环路**（数据先写入内存，再按选定地址读出）。整件事的分岔口只有一处：**数据怎么进出 DDR**。

**导师定案（2026-09-30）**：

> 建议先走路线 A，先实现功能，然后再加上软核，这种路线 B。

**路线 A —— 自写硬件模块直连内存（本期交付）**

- **内容**：数据进出内存这一段，用自己写的纯硬件模块直接连到 DDR 控制器；"读哪一个地址"做成软件可写的寄存器，由上位机下发。
- **已完成**：三层硬件逻辑（跨时钟缓存 / 内存读写主控 / 帧接口）+ 简化内存模型的仿真，六个用例全部通过。
- **下一步**：接真实 DDR 控制器（须先完成校准）→ 换掉简化模型 → 上板联调。
- **边界**：目前未建工程、未上板；仿真所用的简化内存模型会立即应答，**真实内存的时序特性还须实测**。

**路线 B —— 软核 + C 代码控制（后继，不推翻 A）**

- **内容**：在路线 A 之上增加软核处理器与 C 代码来控制读写位置；软核只下发参数、读取状态，**不进入数据通路**。
- **定位**：**B 是后继不是替代**——它只换数据面的一层、加一个控制面，A 的桥、引脚、时序与判据全部保留；启动条件是 A 的功能判据全部通过。
- **接口预留**：三条接口已按"可替换"设计，保证两步走不返工。

**共同前置 —— 内存控制器校准复验**

- 板载 DDR4 上电后必须先完成校准才能读写；该过程**无法用仿真替代**。
- 状态：对应配置文件已在库，**只差一次上板**。
- 说明：它同时是后续"把队列缓存改到 DDR"的前提。

**另有一条非 DDR 的并行线**：传输效率五级实验（E1–E5），上位机脚本侧已就绪，等板卡，用于逐层确认"哪一段限制了速率"。

### 4.2 已知的两个待修问题

1. **过载时的硬冻结**：背靠背高速发送时板卡可能卡死（需重新烧录恢复）。**机制已用仿真复现**——接收端正在发送时新到达的帧开始信号会被丢弃，而缓存不记录帧边界，导致后续帧**用新帧的长度去读旧帧的数据**，字节流永久错位。修复方案已设计，但**暂不实施**：改动会使现有全部判据的基准失效，需要重新出配置文件并整体重测。
2. **一条约束实际未生效**：某个约束文件里有一条路径豁免命令，因为**在行尾写了注释符号**导致命令报错失败（该语言的注释只能独占一行）。影响很小（时序仍然收敛），但**新工程会继承这个写法，需一并修正**。

### 4.3 后续安排

板卡回到手上之后：跑传输效率实验 → 内存控制器校准复验 → 内存读写进环路联调 → 双板组网 → 跨板双向转发。
跨板转发被评估为当前**最大的技术风险**。
