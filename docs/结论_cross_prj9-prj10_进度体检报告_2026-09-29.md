# prj9 / prj10 进度体检报告（2026-09-29）

> **体检方法（第一性原理）**：一条数据通路的健康 = ①每一级**可观测**（有计数器/判据，溢出可见）②判据**可复现**（位流在库、脚本幂等、口径唯一）③风险**有主**（每条已知风险有触发条件、观测手段与归属阶段）。规划的健康 = 每个里程碑**编号唯一可寻址**、决策**已拍板或明确标注待拍板**、机制**无未定义行为**。按此逐项对照 prj9（工程实体）与 prj10（规划文档）。
> **证据源**：进度三件套 + 系统设计报告 v0.5 + prj10 三篇文档；工程实体核查（离线解析 `project_9.xpr` / `mig_ddr4_cal.xpr`、位流/脚本/目录清点、git 状态与远端同步比对、`json_storm.py` 参数实测）。**未做任何 Vivado 构建操作，未改动任何工程文件。**

### 1.2 漏洞与缺口（按severity）

| # | 级 | 缺口 | 现状与影响 |
|---|---|---|---|
| V1 | 🔴 | **E1–E5 实验全部未执行** | 实操单 v2 今日（09-29）才定稿。实测确认：`json_storm.py` **无 `--pace-us` 参数**（A6 未实现，E3 的钥匙）、`--chunk` 默认仍 1360（须显式传 1466）、发送 socket 未设 `SO_SNDBUF`（A3）。线速达标目标（≥900 Mbps 且 100%+SHA）目前是纯静态推算，无一实验背书 |
| V2 | 🔴 | **过载硬冻结根因未修** | R4（`udp_tx.v` L120 长度锁存仅 idle 态，TX 忙时 rec_pkt_done 边沿丢失→帧错位）只是**第一候选**，未坐实。E2 是触发场景；缓解措施（单独排期 + 冻结即抓 `dbg_pfwd_stuck_cnt` + 重烧恢复）已写进风险表，但"过载只降速不冻结"的路线目标未达成。**追线速（E2/E3）前这是第一道坎** |
| V3 | 🟡 | R3 观测盲区 | `async_fifo_2048x8b` 深 2048 < 2×1466，`.full()` 空接无计数——混流（ARP/ICMP 占线时第 2 帧）溢出**不可见**。实验纪律（不 ping/清 ARP）可规避，但盲区本身留在 RTL 里，D2 之前的所有实验都背着它 |
| V4 | 🟡 | R2 无标准 IFG | 栈 TX 帧间仅 ~10 拍（IEEE 要求 96 拍）。低速已验证 PHY 容忍，**线速下未验证**（E4/Wireshark 承载）——若 PHY 不容忍，E3 达标判据会被此卡住 |
| V5 | ⚪ | 判决位流只剩最后一颗 | build9v（修复前）已被 build9w 覆盖，`out/` 仅存 09-21 21:03 一颗。语义上 w ⊃ v（修复+全探针），**无功能损失**，但文档口径"build9v/w 两颗"与实体一颗不符，引用时注意 |
| V6 | ⚪ | 仿真资产未入工程 fileset | `sim/pump_tb.v` / `pump_tb_stress.v`（帧泵格雷满判修复的仿真复现资产）不在 xpr 仿真集里（解析显示 testbench 0 个），复现靠散装 xsim 日志。小项，建议后续把 testbench 挂进 sim_1 |

**判定**：prj9 没有"失管"项——V1–V4 全部在实操单 v2 风险表/实验矩阵里有归属；问题是**执行度为零**（今日才具备执行条件）+ V2 是硬风险。按实操单既定顺序（E1 单进程 → E2 背靠背单独排期 → E3 受控节奏）执行即可，**不要跳过 E1 直接 E2**（冻板重烧虽可恢复但浪费判据窗口）。

### 2.2 漏洞与缺口

|---|---|---|---|
| P1 | 🔴 | **D 命名空间三重冲突** | 同一字母 D 在三套编号里含义互斥：① 路线图 #14 / 设计报告 v0.5 §8.1 / 待办 / agent.md 的 **D1–D5**（D2 = 队列后端 DDR 化·描述符环）；② 09-28 路线建议汇报 §六的 **D0–D6**（D2 = 内存桥 RTL·槽式）；③ 09-24 架构草案 §5 的**决策点 D1–D7**。实例："D2"在三处指三个不同交付物；实操单 v2 §九"D2 需求输入"用的是 ① 口径，与 ② 的 D2 不是同一件事。跨文档引用/答辩讲述时必然张冠李戴 |
| P2 | 🔴 | **Q1–Q5 未拍板，且追踪文档完全缺席 prj10** | 路线 A 只是建议（09-28 汇报明确"待导师拍板 §五"），但短期待办主线区/挂起区均无 prj10 条目，README 工程索引无 prj10 行——**prj10 目前只活在三篇文档里，不在追踪系统里**。若导师改判 B，D 线叙述返工；若确认 A，实施单（`操作文档/阶段三_prj10_…`）尚未创建。另：路线图决策记录止步 #14（09-26），**09-24 导师"内存进环路+随机读写"布置没有对应决策记录**（应为 #15） |
| P3 | 🟡 | **两线衔接关系未定案** | #14 D 线（队列容量线：描述符环、多帧并发、GB 级）与 prj10（功能验证线：槽式随机读写）都动 DDR、都被叫"D 线"。09-28 汇报 §3.4 只说"不是同一件事、B/DMA 时机留在②"，但 prj10 D0–D6 完成后 #14 的 D2–D5 如何衔接（槽式桥是否升级为描述符环、F1 组网合流点"队列版帧泵"指哪个）无文档定案 |
| P4 | 🟡 | **控制面注入通道未设计** | J3 乱序读判据需要"上位机下发乱序槽号序列"，载体（UDP 命令字 vs MicroBlaze AXI-Lite 寄存器）= 悬置的 Q3。两条路都意味着**新增工程量**（命令解析器，或软核+BD 集成），但 D0–D6 里程碑没有单列此项；且"以太网栈零改动（只增不改）"的承诺只对数据面成立，需在实施单里明确边界，否则范围蔓延 |
| P5 | 🟡 | **槽资源管理机制缺失** | 槽区 256×4KB=1MB ×2（架构草案 §4），而 J4 要求全量 10MB SHA 一致 → **10 倍槽回绕**，需要"写等读"的槽空闲管理（否则覆盖未读帧）；随机读模式下读未写槽 = **未定义行为**，需要槽有效握手协议（PC 如何知道哪些槽已写？）。草案 §4 槽结构未覆盖这两点——这是"随机读写"能否自证清白的关键机制 |
| P6 | ⚪ | prj10 自身的静态预算未核算 | 实操单 v2 的服务时间表没有 DDR 段。两级桥各加"写+读"，4KB 突发 @ui_clk≈300MHz 量级约 0.5–1 µs/帧，**大概率**不破坏 959 Mbps 节拍，但这是 prj10 实施单应尽的核算义务（与 prj9 同方法论） |
| P7 | ⚪ | 槽规格两套口径并列 | 汇报 §二用学长工程"16 槽×64KB"作存量证据，§三用的是本期"4KB 对齐槽"——同文档两套槽参数，转实施单时须钉死本期规格（4KB×256），避免误抄 |
| P8 | ⚪ | 板②位流前置未列 | F1 双板组网判据不含"板②建工程/产出位流"步骤（KU060-② 已到位、无位流无连线，设计报告 §3.2.2 已登记）。属 F1 的隐含前置，列入实施清单可防"当天才发现没位流" |

**判定**：prj10 的规划**质量**不成问题，问题在**治理**——P1/P2 是结构性缺口（编号系统与追踪系统都没接住它），P5 是机制级缺口（会在 D2 仿真阶段暴露，最好现在补进架构草案）。三者都可以在"导师拍板后转实施单"这一步一并解决，成本最低。
