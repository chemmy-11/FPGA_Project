# prj9 过载冻结 R4 机制 · 离线仿真复现（2026-10-01）

> **性质**：板不在手期间的离线推进。**只读 prj9 RTL，未改动任何设计文件**（rtl/ xdc/ prj/ 零改动）；
> 新增物仅限 `project_9/sim/r4_start_lost/`（TB + 一键脚本 + 运行产物）。
> **口径**：本文结论 = **仿真证实**（功能级，可复现）；**未上板**。R4 对 09-21 过载冻结的**贡献度**仍待 E2 实测标定。

---

## 〇、一句话结论

**R4 成立**：`udp_tx` 对 start 的消费**只在 `st_idle`**，而长度寄存器也**只在 idle 锁存** —— 于是 **TX 忙时到达的 `rec_pkt_done` 被整帧丢弃**，
其字节留在**无帧边界**的 FIFO 里；下一个被接受的 start 会**用新帧长度去读旧帧字节**，造成**字节流永久错位**。
仿真四步逐字节复现（实得 `d0 d1 d2…`，期望 `e0 e1 e2…`），终态残留 50 B。

## 一、RTL 证据链（全部逐行核对，文件 `project_9/rtl/udp/udp_tx.v`）

| # | 位置 | 代码 | 含义 |
|---|---|---|---|
| 1 | L94 | `assign pos_start_en = (~start_en_d2) & start_en_d1;` | start 被整形成**单拍脉冲**（无队列、无 pending） |
| 2 | **L120** | `if(pos_start_en && cur_state==st_idle) begin tx_data_num<=tx_byte_num; total_num<=…; udp_num<=…; end` | **长度三件套只在 idle 锁存** —— 忙态脉冲来了也不更新 |
| 3 | L137 | `trig_tx_en <= pos_start_en;` | 触发信号**无条件**打一拍（看似"记住了"） |
| 4 | **L247** | `st_idle: if(trig_tx_en) begin skip_en<=1'b1; … ip_head[0]<={8'h45,8'h00,total_num}; …` | **但消费点只在 `st_idle`** —— 忙态的那一拍 `trig_tx_en` 无人接收、无锁存 |
| 5 | 顶层 L96 | `assign tx_start_en = rec_pkt_done;` | start 源 = `udp_rx` 的**单拍完成脉冲**（不是电平、不是握手） |
| 6 | 顶层 L436 | `async_fifo_2048x8b: .rd_en(tx_req), .dout(tx_data), .full(), .empty()` | 上游是**无帧边界的字节 FIFO**，且 full/empty 悬空（R3）；IP 配置 `Performance_Options="Standard_FIFO"` + 各 flag 全关（见 §二）|

**因果链**：忙态脉冲 → L120 不锁存长度、L247 不消费触发 → **整帧 start 丢失** → 该帧字节留在 FIFO（读指针不动）
→ 下一次 start（idle 时）用**新长度**从**旧首字节**开始读 → **错位**，错位量 = 新旧帧长之差，**逐帧累积**。

## 二、TB 设计（`project_9/sim/r4_start_lost/r4_tx_start_tb.sv`）

**思路**：只例化 `udp_tx` 单模块，用行为级上游忠实模拟真实激励条件。

> **上游 FIFO 语义的证据（2026-10-01 补，IP 级）**：本 TB 首版把 FIFO 建成组合读（FWFT）导致载荷首字节丢失；
> 改为"标准 FIFO 1 拍读延迟"的正确性由 IP 配置**独立坐实**——`project_9/ip/async_fifo_2048x8b/async_fifo_2048x8b.xci`
> 的 `component_parameters`：
> ```
> Performance_Options   = "Standard_FIFO"                  <- 决定性: 非 First_Word_Fall_Through ⇒ 1 拍读延迟
> Fifo_Implementation   = "Independent_Clocks_Block_RAM"
> Input_Depth/Width     = 2048 / 8      Output_Depth/Width = 2048 / 8
> Use_Embedded_Registers = "false"                         <- 无额外输出寄存器 ⇒ 延迟恰好 1 拍
> Almost_Full_Flag=false · Almost_Empty_Flag=false · Overflow_Flag=false · Underflow_Flag=false
> Valid_Flag=false · Data_Count=false                      <- 全部关闭 ⇒ 独立佐证 R3「无任何可观测性」
> ```
> ⇒ 模型语义有**双向证据**（RTL 注释 L334-337 的"提前请求" + IP 的 Standard_FIFO），不是凭直觉。

| TB 元件 | 模拟对象 | 关键建模点 |
|---|---|---|
| `fifo` + `rd_data_r` | `async_fifo_2048x8b` | **标准 FIFO（非 FWFT）1 拍读延迟**——依据 `udp_tx` L334-337 注释"提前读请求数据,等待数据有效时发送"（`tx_req` 在 st_ip_head 末尾提前一拍拉起，下一拍 `tx_data` 才有效） |
| `push()` + `wr_ptr` | `udp_rx` 写侧 | 只写字节，**不写帧边界**（与真实一致） |
| `start_frame(len)` | `rec_pkt_done` + `rec_byte_num` | **单拍脉冲** + 当拍给出长度 |
| GMII 逐字节捕获 | 线上帧 | 逐字节抓 `gmii_txd`，按帧切分，载荷偏移 = 8+14+28 = **50** |

**四步激励**：

| 步 | 动作 | 目的 |
|---|---|---|
| 1 | A(100B, 图案 A0) → start | 基线：空闲态 start 应被正常接受 |
| 2 | B(100B, 图案 B0) → start | 对照：连续两帧在**空闲**投递时全部对齐 |
| 3 | C(200B) start 后**等 60 拍**（此时 `gmii_tx_en=1` 确在忙）→ 投 D(50B) 并脉冲 start | **核心场景**：忙态 start |
| 4 | 空闲后投 E(30B,E0) → start | **错位证明**：若字节流已错位，发出的将是 D 的字节 |

## 三、判读输出（一键复现：`run_sim.ps1`）

```
==== R4 忙态 start 丢失复现 (prj9 udp_tx) ====
[step1] A(100B,A0) 发出后 nframes=1  wr=100 rd=100
    frame[0] len=154  payload[0..5]=a0 a1 a2 a3 a4 a5          <- 对齐
[step2] B(100B,B0) 发出后 nframes=2  wr=200 rd=200
    frame[1] len=154  payload[0..5]=b0 b1 b2 b3 b4 b5          <- 对齐(空闲态 start 被接受)
[step3] 忙态注入: gmii_tx_en=1 (1=确在忙)  -> 投 D(50B,D0) 并脉冲 start
[step3] 忙态 start 之后  nframes=3  (若=3 则 D 的 start 被丢弃)   <- 【证据1】帧数不增
[step3] FIFO: wr=450 rd=400  残留=50 B (D 的 50B 未消费)          <- 【证据2】字节留存
    frame[2] len=254  payload[0..5]=c0 c1 c2 c3 c4 c5          <- C 帧本身正确
[step4] E(30B,E0) 发出后 nframes=4  wr=480 rd=430
    frame[3] len=84  payload[0..5]=d0 d1 d2 d3 d4 d5           <- 【证据3】长度是 E 的(84=50+30+4)
        期望(正确设计)=e0..  实得(错误)=d0 d1 d2                <-    内容却是 D 的
>> 判决: 字节流错位【成立】—— 新帧(E0/len=30)发出了旧帧(D0)的字节
[终态] nframes=4  wr=480 rd=430  未消费=50 B                     <- 【证据4】永久偏移 50B
```

**四条硬证据**：

1. **忙态 start 被丢弃**：step3 后 `nframes` 保持 3 —— D 的 start 没有产生任何帧。
2. **字节留存**：`wr=450 / rd=400` —— D 的 50 B 原封不动留在 FIFO。
3. **错位**：step4 发出的帧 **长度 = E 的 30 B**（`len=84=50+30+4`），**内容 = D 的字节**（`d0 d1 d2…`）——「新帧长度 + 旧帧字节」。
4. **永久性**：终态 `wr-rd=50` —— 偏移不会自愈，此后**每一帧**都会带着前一帧的数据。

> **TB 自身的一次纠错（值得记录）**：首版把上游 FIFO 建成**组合读（FWFT）**，结果载荷首字节恒缺一字节（`00 a1 a2…`）。
> 查 `udp_tx` L334-337 注释才确认真实 IP 是**标准 FIFO**（提前一拍请求、下一拍数据有效）。改对模型后 `a0 a1 a2…` 逐字节正确。
> ⇒ 再次印证：**上游模型的一拍之差会让"结论"整体偏一位**；模型语义必须有 RTL 依据，不能凭直觉。

## 四、后果分析：它解释了什么、没解释什么

### 4.1 与既有观测的自洽性（**推论，非证实**）

| 既有观测 | R4 能否解释 |
|---|---|
| 低速（`--gap-ms 0.1`，561 µs/帧）**100% + SHA 一致** | ✅ 自洽：TX 早已空闲，start 必定落在 idle → 永不丢失 → 永不偏移 |
| `gap=0` 极限档大幅劣化、累计约 26 MB 后泵A冻结 | ⚠️ **可能是多因之一**：R4 提供"错位 + FIFO 只增不减"的机制，但 09-21 的冻结是否由此主导**未证实** |
| 静态预算：栈 TX 服务 **12.24 µs** vs 线速帧周期 **12.304 µs**（裕量仅 **0.06 µs ≈ 8 拍**） | ✅ 直接命中：线速/过载下 `rec_pkt_done` 极易落进 TX 忙窗（GMII 12.24 µs **之外还要算 FSM 尾部**：st_crc 4 拍 + 边沿检测 + st_check_sum 4~5 拍），**忙窗实际长于线速帧周期** |

⇒ **"零星整帧丢弃"的静态预判（实操单 §三 定论 2-b）现在有了机制归属**：不只泵A/泵B 忙时丢弃（R1），
**栈 TX 也有一条独立的丢帧路径**（而且是"丢 + 错位"双重后果，比单纯丢弃更坏）。

### 4.2 明确**不**声称的

- ❌ 不声称"R4 就是 26 MB 冻结的根因"——从"错位"到"泵A 楔死"之间还缺一环（FIFO 溢出不可见 R3 → 读指针与数据失步 → 下游异常）。该环需 E2 上板以 `dbg_pfwd_stuck_cnt` + `pfwd_wr` vs `pk_frames` 对账坐实。
- ❌ 不声称"线速下每帧都丢"——精确丢失率取决于到达抖动分布，属 E2/E3 实测标定范围。
- ❌ 不声称已修复。**本轮不改 RTL**（理由见 §五）。

## 五、修复方向（**已设计，未施行**）

### 案 A · 忙时锁存 pending start（最小改动，~10 行）

**思路**：把"start 是单拍脉冲"改成"start 是可锁存请求"，且**长度必须与请求同拍锁存**（否则仍会错位）。

```verilog
// 新增: pending 请求 + 配套长度（与 pos_start_en 同拍采样, 保证配对）
reg        pend_start;
reg [15:0] pend_len;
always @(posedge clk or negedge rst_n) begin
    if(!rst_n) begin pend_start <= 1'b0; pend_len <= 16'd0; end
    else if(pos_start_en && cur_state != st_idle) begin   // 忙态才需要挂起
        pend_start <= 1'b1;  pend_len <= tx_byte_num;
    end
    else if(pend_start && cur_state == st_idle) pend_start <= 1'b0;  // 服务即清
end
// 长度锁存改为: 服务时取 (pend_start ? pend_len : tx_byte_num)
```

**代价**：改动 `udp_tx` = 改 prj9 数据面 → **必须重出位流**；且需新增判据（忙态补发不丢帧、不错位）。

### 案 B · 帧边界队列（结构解，= D2 语义）

把"无帧边界的字节 FIFO + 单拍 start"换成**带帧边界的队列**（描述符环 + 帧长字段），
从结构上消灭"长度与字节流解耦"这一整类缺陷。**这正是决策 #14 D 线 D2（队列后端 DDR 化）的接口语义** ——
实操单 §四 R4 行早已注明"一条线修两个问题"。

### 为什么本轮**不施行**任何一案

| 理由 | 说明 |
|---|---|
| ① E1–E5 判据基线 | E1–E5 明确使用**现有判决位流**（build9v/w，三域 ILA + 六段差分计数器）。改 RTL → 重出位流 → **全部既有判据基线作废** |
| ② prj10 W3 场次3 沿用 prj9 rtl | W3 开发文档明确"源：**prj9 全部 rtl** + project_10 三层 rtl"。此刻改 prj9 rtl = **动到正在开工的 prj10 的输入** |
| ③ 时机 | 更优顺序 = **先 E2 实测标定 R4 贡献度** → 再决定案 A（小补丁）还是案 B（随 D2） |

## 六、与其他线的关系

| 线 | 关系 |
|---|---|
| **E2（背靠背冲击）** | 本文把 E2 判读从"抓现场"升级为"**带已知机制去验证**"：若出现丢帧，应同时看 ① 栈侧帧计数 ② `dbg_pfwd_drop`/`dbg_prev_drop`（泵侧）③ `dbg_pfwd_stuck_cnt`（冻结）。**若板端丢帧数 > 泵侧计数之和，差额即栈 TX 侧（R4）贡献** |

| **prj10 W3** | 本文**零改动** prj9 rtl，W3 场次3 的输入源不受影响 |
| **R1/R3** | 三条独立丢帧/失真路径：R1 泵忙丢弃、R3 FIFO 溢出不可见、**R4 栈 start 丢失+错位**。E5 对账时三者都在差额里，判读表需分开归因 |
