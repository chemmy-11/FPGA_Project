## 二、两次冻结（可复现）+ 计数器对账 ★本轮最重要的发现

### 2.1 冻结现象
两次运行结束、抓快照时都 **ping 100% 丢包**（板子不响应）；**重烧位流即恢复**（已做两次）——与"过载硬冻结、重烧恢复"的既有认知一致。

### 2.2 板端计数器（冻结瞬间立即触发快照；脚本 `scripts/freeze_snap.tcl`）

| 计数器 | E1 后 | E3 后 |
|---|---|---|
| `dbg_pfwd_wr`（进泵A） | 3557 | 3647 |
| `dbg_pfwd_rd`（出泵A） | 3557 | 3647 |
| `dbg_pk_frames`（打包） | 3557 | 3647 |
| `dbg_up_frames`（A 解包） | 3557 | 3647 |
| `dbg_prev_wr`（进泵B，回程） | 3557 | 3647 |
| `dbg_echo_b_rx` / `echo_b_tx`（B 回显） | 3557 / 3557 | 3647 / 3647 |
| `dbg_pfwd_stuck_cnt`（泵A看门狗） | **0** | **0** |
| `dbg_pk_ovf_cnt` / `hard_err_cnt` / `ch_up_evt` | 0 / 0 / 0 | 0 / 0 / 0 |
| `ch_up` / `lane_up` | 1 / 1 | 1 / 1 |
| **PC 实际收到** | 3511 | 3621 |

### 2.3 对账结论（三句话）

1. **FPGA 内部一处没丢**：六个计数器**完全相同**（3557 / 3647）→ 从"进泵A"到"B 回显出"之间**零丢失、零溢出、零误码**。
2. **PC 侧也没怎么丢**：板子回显 3647，PC 收到 3621 → 差 26 帧（0.7%，含收尾在途与 PC 收包）。
3. **丢失全部发生在"泵A之前"**：发送 7022，但只有 3557/3647（约 51%）真正进了泵A → **约一半的帧根本没进 FPGA 数据面**。
   而这一段**恰恰是唯一没有计数器覆盖的地方**（已知观测盲区：以太网 RX 侧 `async_fifo_2048x8b` 的 `.full()` 在顶层空接、无溢出计数）。

### 2.4 触发条件的新认识（**修正既有假设**）

- 既有说法：过载冻结由**背靠背冲击**（4 进程 / gap=0）触发，故 E2 单独排期。
- 本次实测：**E1（0.07 s 洪泛）与 E3（106 s 有节奏、401 Mbps）都冻结**，且都在**处理到约 3.6k 帧**时停下。
- ⇒ 更像**"累计帧量/字节量"触发**（≈3.6k 帧 ≈ 5.6 MB 线上量），而**不是速率触发**——把 401 Mbps 也叫"过载"是不准确的。
- ⇒ 与 09-21 记录的"约 26 MB 累计后泵A冻结"（旧观测）**量级不同**，需在后续实验里把触发阈值钉死（脚本已可复现）。

### 2.5 与"泵A看门狗"的关系（重要）
`dbg_pfwd_stuck_cnt = 0` → 09-29 装的那个看门狗**没有触发**，因为 **泵A自己没有卡**（它只是"再也没收到完整帧"）。
⇒ **现有观测手段对这类冻结是盲的**：必须给**以太网 RX 侧**（进泵A之前）加溢出/帧计数，否则永远只能看到"链内全好、链外全丢"。

## 三、下一步建议（按性价比）

1. **给 RX 侧加观测**（最高优先，成本最低）：把那颗 2048 B 异步 FIFO 的 `full`/`overflow` 引出来计数（现存顶层 `.full()` 空接），并加"进泵A 帧数"与"PC 发送帧数"的差分判决——**这是把"51% 丢在哪"钉死的唯一办法**。
2. **修 R4**（离线已复现的 `udp_tx` 长度锁存缺陷）：本次冻结的形态（链内全好、板子整体不应答）与"发送请求在忙态被丢 → 帧边界错位 → 此后永久错帧"的机制相符，值得作为第一候选去验证。
3. **换发包器（B2）**：E3 的 401 Mbps 是 Python 的上限，不是硬件的；要回答"硬件到底能到多少"，必须用 C 发包器把发送侧顶过 900 Mbps。
4. **冻结复现脚本化**：本次的 `freeze_snap.tcl`（立即触发快照）应固化为"冻结现场取证"标准动作（原来只能靠重烧后凭记忆描述）。
