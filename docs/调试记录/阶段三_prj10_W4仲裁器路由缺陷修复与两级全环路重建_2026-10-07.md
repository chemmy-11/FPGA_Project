# prj10 W4 · 仲裁器路由缺陷修复 + 两级全环路重建（2026-10-07）

> **一句话**：W4 第七轮构建其实已成功出流（WNS=+0.035，位流在库），但**上板前代码审查发现位流带着一个必死锁的 AXI ID 路由缺陷**——修复 + 联合仿真验证 + 重建位流，避免了一次板上白跑。本记录按"发现 → 定位 → 修复 → 验证 → 重建"五段留痕。

---

## 一、发现：缺陷在哪、怎么发现的

**背景**：W4 RTL 于 10-06 深夜落地（git 68a88ba），第七轮构建（build_w4g.log）综合 0 CW / 实现 WNS=+0.035 / 位流+探针已产出、EXIT=0——**构建本身成功了**，待办里的恢复点①（判读构建结果）由此关闭。接管 W4 后的下一步本该是"烧板跑 J4"。

**审查路径**（未上板、未抓波形，纯读 RTL）：

1. 读 `axi_arb_2to1.v` 响应路由：B 通道按 `m_axi_bid[0]` 路由（:123-127），R 通道按 `m_axi_rid[0]` 路由（:168-174）——**路由依据是响应 ID 的 bit0**；
2. 读 `axi4_master_bridge.v`：`awid=4'h0 / arid=4'h1` 是**硬编码常量**（:210-211）——两座桥（u_mem / u_mem2）例化**同一个模块**，驱动**完全相同**的 ID；
3. 读仲裁器头注释：自述假设"主0 ID=4'h0，主1 ID=4'h1，透传即可"——**该假设与桥的实际端口行为不符**，是设计意图与实现之间的脱节。

**死锁机制链**（MIG 按协议回声 ID——W3 前置清单已核实本 MIG 的 r_channel 把 ID 搬进读事务缓冲再驱动 rid）：

```
两桥 awid 恒 0 → MIG 回 bid 恒 0 → 仲裁器 bid[0]==0 → 所有写响应送桥①
                                          → 桥② 写 FSM 等不到 B → 桥② 首帧后挂死
两桥 arid 恒 1 → MIG 回 rid 恒 1 → 仲裁器 rid[0]==1 → 所有读响应送桥②
                                          → 桥① 读 FSM 等不到首拍 → 去程数据永不到 pack
→ 数据面全停（T23/T22 可能照常亮，ping 可能过，UDP 回显必挂）
```

**为什么单元仿真没抓到**（两个掩盖叠加）：

- `arb_tb.sv:84/104` 给两主**手工喂了不同 ID**（`awid[m]=m`），与真实桥的常量 ID 行为不符；
- T4 读方向数据回传直接置 0 跳过（`m_axi_rvalid(1'b0)`），R 路由从未被真正测过。

**为什么 W3 位流没这个问题**：W3 只有一座桥直连 MIG，没有仲裁器——路由缺陷是 W4 引入仲裁器时才产生的。

## 二、修复：10 行 RTL，语义与 ID 解耦

`axi_arb_2to1.v`（修复后）：

```verilog
// 写响应: 按授权锁存路由(W4 修复: 不依赖 bid —— 两桥 ID 恒同, 见文件头)
wire wresp_to_s01 = wbusy & (wgrant == 1'b1);
assign s00_axi_bvalid = m_axi_bvalid & ~wresp_to_s01;
assign s01_axi_bvalid = m_axi_bvalid &  wresp_to_s01;
assign m_axi_bready   = wresp_to_s01 ? s01_axi_bready : s00_axi_bready;

// 读数据: 按授权锁存路由回授权主(理由同 B 通道)
wire rresp_to_s01 = rbusy & (rgrant == 1'b1);
assign s00_axi_rvalid = m_axi_rvalid & ~rresp_to_s01;
assign s01_axi_rvalid = m_axi_rvalid &  rresp_to_s01;
assign m_axi_rready   = rresp_to_s01 ? s01_axi_rready : s00_axi_rready;
```

**为什么按 grant 而不是给桥加 ID 参数**：事务进行中（wbusy/rbusy=1）grant 锁存不变，响应必然属于授权主——路由由**授权历史唯一决定**，与响应 ID 彻底解耦；将来两桥 ID 再怎么变（W5 命令通道、D2 描述符环都会动这层）路由都不会再错。两桥 ID 相同本身**不违反 AXI**（不同主设备本就允许各自 ID 空间），错的只是"用 ID bit 区分主"的路由假设。

## 三、验证：负向对照 + 联合仿真 + 双回归

### 3.1 新增联合仿真 `sim/w4_joint_tb.sv`（本次修复的主要防线增量）

W4 之前只有单桥 TB（mem_bridge_tb）与仲裁器单元 TB——**两桥+仲裁器+共享从机**的系统级组合从未被仿真，这正是缺陷漏网的结构性原因。新 TB 拓扑 = 真实顶层的数据面核（两座 frame_mem_if + axi_arb_2to1 + 2MB axi4_ram_model），判据五组：

| 组 | 判据 | 结果 |
|---|---|---|
| 负向对照 | `DEFECT_ROUTING=1` 例化修复前路由副本（`axi_arb_2to1_defect.v`，逐行复制第七轮位流所含逻辑，仅存于 sim/） | **FAIL (deadlock)**——`A_ost=1` 静默窗触发死锁看门狗，判据**非恒真** ✅ |
| P1/P2 | 交错推+读 12+12 帧（fork/join 双桥并发回收），逐字节一致 | PASS |
| P3 | 对账闭合（两桥各自 wr=rd=wm=12）+ 协议（4k=0/proto=0）+ 双桥并发见证（J-B 锁存监视器） | PASS |
| P4 | 持续体量 96+96 帧仍逐字节一致 | PASS |
| P5 | 流水模式（读请求自生成，镜像真实顶层）对账闭合 | PASS（两桥 wr=rd=wm=148，错误计数全 0） |

**一键复现**：`sim\run_w4_joint.bat`（先负向后正向，两段判决行都在 `w4_joint_run.log`）。

**TB bring-up 两笔账（写在这里防复发）**：初版 TB 的读请求生成器在推帧阶段就自由跑、而字节采集假设 TB 门控——数据错位大面积红；改为显式 `issue_rd*` 脉冲 + fork/join 并发轮后只剩 5 个自伤错误，根因是**采集缓冲在发读请求之后才清零**（迟到 29/3 字节，`got` 值与 `patA(fid, 迟到量)` 精确吻合）+ **J-B 见证在两读都完成后采样**（必然 0）——先武装采集再发请求、见证改常驻锁存后 0 错误。

## 五、位流重建（第八轮）判读与时序修复

**第一段（build_w4h.log）**：综合 0 error / 0 critical warning；ILA 插入与实现推进到 opt_design 的 **MIG PHY 缝合阶段偶发失败**（`couldn't read file .../unimacro_vhdl.tcl: No error`——文件完好，句柄竞争类偶发，W3 集成执行单 §六 #7 已登记的同款坑）。**处置**：不重综，`build_debug_resume.tcl` 续跑（复用 synth_1 产物）。

**第二段（build_w4h_resume.log）**：续跑完成位流，但**时序判据未过**——

