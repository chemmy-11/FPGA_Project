## 二、根因重定（第一性原理 · 对上一轮结论的三处修正）

上一轮（[[调试记录/阶段三_prj10_W5命令通道与随机读_时序收敛阻断_2026-10-07]]）把根因写成“RND 逻辑从未时序收敛”，并据此设计“**只给 RND 加一拍决策态、SEQ 路径零改动**”的修法。本轮按第一性原理重新取证，**三处都要修正**：

### 2.1 修正一：超预算的不是“RND 逻辑”，而是**整条读命令解码锥**

最差 25 条路径**全部同源**（不是几百条各异）：

~~~
源: u_mem/u_rd_cmd/rd_bin_reg[0]_replica/C          <- 命令 FIFO 的读指针
  → u_rd_cmd/ram_reg_0_3_0_8/RAMB/O                 <- FWFT 组合读出! (async_fifo.v: assign rd_data = ram[rd_bin])
  → uc_dout = {cmd_rnd, cmd_slot}
  → in_range 比较 (LUT4 + CARRY8)
  → eff_slot 选择 (LUT 链)
  → full_bit / len_tab 的 256:1 查表 (RAMD32 + MUXF8 + LUT 树)
  → stat_ill_rd / r_len / r_beats / rd_wr_data 的 CE / D
数据路径 4.226ns（logic 1.328 / route 2.898），预算 3.333ns
~~~

关键点：`cmd_rnd` 不是“被算出来的数”，它是这条锥的**选择信号**。只要命令 FIFO 里装的是动态命令，**SEQ 模式下这条锥同样活着**——所以“只修 RND、SEQ 不动”在设计上就不成立。

### 2.2 修正二：W4 通过 ≠ 这条锥是好的，而是它**只剩零余量**

W4 时代 `cfg_mode` 硬接 `1'b0` → 命令 FIFO 只写常量 → `cmd_rnd` 被常量折叠 → `eff_slot` 退化成**寄存器** `rd_seq_slot`，于是：

- 前缀（FWFT 组合读出 + 比较 + 选择）整段消失；
- 只剩「寄存器索引 → len_tab → +63 → >>6 → r_beats」这一段。

而这一段在 W4 的最差路径清单里就已经是**贴着零余量**的（W4 记录 §五 原文列出的最差路径之一即 `u_mem2/u_bridge/rd_seq_slot_reg[0]_rep__3/C → u_mem2/u_bridge/r_beats_reg[1]/D`），W4 fix4 终版是 **+0.008ns / 0 失败端点**。

> 推论（本轮修复的第二个依据）：**只切“比较+选择”这一刀还不够**——那段“查表 + 加法器”本身就是固有瓶颈，必须一并摘掉。

### 2.3 修正三：SEQ 指针扫描的守卫本身也挂着 FIFO 输出

旧代码：`if (!cmd_rnd && !full_bit[rd_seq_slot] && (stat_outstanding != 9'd0)) rd_seq_slot <= rd_seq_slot + 1;`
`cmd_rnd` 来自 FWFT 组合读出 → 指针扫描的 CE 也挂在同一根慢线上。cut-1 把它改成只依赖寄存器（`!full_bit[rd_seq_slot] && outstanding!=0`）：扫描语义（“前进直到落在 FULL 槽”）不变，但**指针自走不再被 RND 命令冻结**，这与 W2 §6.3 注释声明的意图一致；回归已证六用例计数逐字不变（§六）。

## 三、cut-1：三处改动与实测效果

全部落在 `prj/project_10/rtl/axi4_master_bridge.v`（两个桥共享同一份代码，一次改动两处生效）。

| # | 改动 | 切掉了什么 |
|---|---|---|
| 1 | **命令预取寄存**：R_IDLE 里把命令从 FIFO 弹进 `pre_rnd/pre_slot/pre_seq` 寄存器，判决挪到下一拍 `R_PRE` | 切掉「FWFT 组合 RAM 读出」这段前缀——判决拍的所有输入变成寄存器 |
| 2 | **新状态 `R_PRE`**：范围比较 + 槽选择 + 查表在**寄存器输入**上做 | 查表锥的索引不再是 `rd_bin → RAM → 比较 → 选择` 的串联结果 |
| 3 | **`len_beats_tab[256]×8b` 预算表**：写侧提交时顺带算好 `(len+63)>>6`，读侧直接查 | **摘掉读路径上的 `+63 → >>6` 加法器**（W4 里那段就是零余量瓶颈），`r_len`（16b 查表）与 `r_beats`（8b 查表）变成**并行两次查表** |

**语义保持**：SEQ 仍是“最老未读槽”、RND 仍是“命令槽 + 越界 clamp + 退休/空槽定长空应答”，`ill_rd/noframe/退休` 全部照旧，唯一差别是**判决晚一拍**（口令间隔是人手级 1ms，无感）。

**实测**：

~~~
cut-1 终判: WNS -0.494 / WHS +0.004 / TNS -399.489 / 失败端点 3464（全在 mmcm_clkout0 = ui_clk）
改善: WNS +0.63ns, TNS +0.67ns, 失败端点 5011 -> 3464
~~~

**cut-1 后剩下的锥**（新最差路径，与旧锥已不同源）：

~~~
-0.494  u_mem/u_bridge/stat_wm_reg[2]/Q  → u_mem/u_bridge/r_len_reg[5]/D
-0.462  u_mem/u_bridge/stat_wm_reg[15]/Q → u_mem/u_bridge/FSM_onehot_rstate_reg[2]/D
-0.458  u_mem/u_bridge/pre_slot_reg[2]/Q → u_mem/u_bridge/r_len_reg[6]/D
-0.454  u_mem2/u_bridge/stat_wm_reg[10]/Q → u_mem2/u_bridge/r_beats_reg[2]/D
路径明细: stat_wm(Q) → LUT4+CARRY8(范围比较) → LUT 链(槽选择) → len_tab 256:1 树(LUT3+LUT6+LUT6) → r_len/D
数据路径 ≈3.60ns vs 预算 3.333ns（route 占 ~70%）
~~~

即：**还差 0.49ns**，卡在「范围比较 + 槽选择 + 256:1 查表」三段仍挤在同一拍。

## 四、cut-2：再拆一拍 —— 触发 Vivado 2023.1 综合崩溃

### 4.1 做了什么

把 `R_PRE` 拆成两拍：`R_PRE` 只做范围比较 + 槽选择并把结果寄存（`pre2_eff`/`pre2_in_rng`），新状态 `R_PRE2` 用**纯寄存器索引**做三张表的查表与判决——理论上把 3.60ns 拆成 ~1.0ns + ~2.2ns 两段。

### 4.2 崩溃现象（3 次可复现）

~~~
build_w5_fix2.log / fix3.log / fix4.log  三次独立运行，同一位置失败：
  vivado/prj_loop.runs/synth_1/runme.log 尾部：
    Finished RTL Optimization Phase 2 / Start Mimic Skeleton from Reference / Finished ...
    Abnormal program termination (EXCEPTION_ACCESS_VIOLATION)
    Please check 'hs_err_pidNNNN.log' for details
  ERROR: [Vivado 12-13638] Failed runs(s) : 'synth_1'
hs_err_pid*.log: "no stack trace available"（仅 dump）
~~~

### 4.3 判别实验（怎么确认是 cut-2 而非环境）

| 实验 | 结果 | 结论 |
|---|---|---|
| 同文件 **单模块 OOC 综合**（`synth_design -top axi4_master_bridge -mode out_of_context`） | **通过**，0 错误 | 崩溃 ≠ 纯 RTL 语法/结构非法；是它与全工程组合才触发 |
| 清理 `.Xil` 历史会话目录 + 删掉 `synth_1` run 目录后重跑 | 仍崩溃（第 3 次） | 排除“环境脏/残留状态” |
| **回退 cut-2**（保留 cut-1）后同工程重跑综合 | **`SYNTH_STATUS: synth_design Complete!`** 且 dcp 生成 | **cut-2 结构就是触发条件**（唯一变量） |

### 4.4 处置

- **回退 cut-2**，cut-1 保留（当前 RTL 状态）；
- cut-2 的 RTL 原文备份留证：`sim/axi4_master_bridge_cut2_synth_crash_repro.v`；
- 最小复现脚本留证：`sim/mini_synth_check.tcl`（单模块 OOC 综合，用于二分定位）；
- 结论按“**工具级阻塞**”登记：不在这条结构上继续对赌，改从其它角度取那 0.49ns（§七）。

> **教训（建议入坑账本）**：单元仿真 PASS、单模块 OOC 综合 PASS，**都不等于工程级综合能过**；RTL 结构性重排后要**尽早跑一次工程级综合**（本项目里综合 ~1 分钟即可见分晓），不要等到 40 分钟的完整构建末尾才发现。
