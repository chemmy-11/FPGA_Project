### 1.3 A6 的一次设计返工（值得记录）

第一版按实操单字面实现「忙等到**绝对**时刻 `t0 + k·周期`」。离线自检立刻暴露问题：Windows 一次抢占（实测 150–828 µs ≈ 12–66 个帧周期）会积欠一屁股时间，追赶时**连续十几帧背靠背发出**——

```
（返工前，绝对时间轴 + 追账）
节拍实测 µs     : min 0.200 / avg 12.500 / p50 12.500 / max 151.800
突发检查        : 最短帧间隔 0.200 µs vs 目标 12.500 µs -> 存在背靠背突发 ✗(会打穿板端零裕量)
```

**0.2 µs 的帧间隔会瞬时打穿板端零裕量通路**（实操单 §三 定论 2-b / §四 R1：泵B 服务 12.21 µs、栈 TX 12.24 µs），足以让 E3 出现"零星整帧丢弃"从而**假失败**。改为**相对节拍**（下一帧目标 = **本帧实际发出时刻** + 周期，落后不追账）：

```
（返工后，相对节拍）
节拍实测 µs     : min 12.500 / avg 12.803 / p50 12.500 / p95 12.600 / max 828.200
突发检查        : 最短帧间隔 12.500 µs vs 目标 12.500 µs -> 无背靠背突发 ✓(帧间隔恒 >= 目标)
结论            : 节拍钉住 ✓ 帧间隔恒 >= 目标(本自检不含 sendto); 平均周期比目标慢 2.43% = OS 抢占耗时(如实计入, 不追赶)
```

**代价与收益**：`帧间隔 ≥ 目标周期` 变成**由构造保证的不变量**（可被自检断言），代价是平均速率比设定值低 1.0–2.8%（抢占时间如实计入），方向是**保守**的——对"100% + SHA"判据只会更安全。这条不变量正是 E3 判据的物理前提。

### 2.3 节奏裁决（**必须显式，否则 E3 会静默退化**）

| 输入 | 行为 | 打印 |
|---|---|---|
| `--pace-us > 0` | **pace 接管**，`--gap-ms` **完全忽略**（`gap_s` 被置 0，L465） | `节奏裁决: pace 接管节奏, --gap-ms=1.0ms 被忽略(R5: sleep 无 µs 精度)` |
| `--pace-us = 0`（默认） | 用 `--gap-ms` 的 `time.sleep` 老语义（向后兼容 09-21 基线） | `节奏裁决: 未启用 pace(--pace-us=0), 用 --gap-ms=1.0ms` |
| `--parallel N` 且 pace>0 | 每进程周期 = `pace-us × N`（聚合帧周期 = `pace-us`） | `pace=12.500µs/帧(每进程 25.000µs)→目标 938.2Mbps @80.00kfps` |

> **为什么这条裁决是本次改造最关键的一处防错**：E3 的命令 `--pace-us 12.5` **没有写** `--gap-ms`，而 `--gap-ms` 默认值是 **1.0 ms**。若不做裁决而是"两者都生效"，E3 会变成 1000 fps ≈ **11.7 Mbps** 的慢速实验——而日志里只会看到一个"很低的速率"，极易被误读成硬件限制。现在运行开头第一行就把这件事说清楚。

### 3.3 节奏器时序自检（★ 核心证据）

命令：`python scripts\json_storm.py --pacer-selfcheck 20000 --pace-us 12.5 --chunk 1466`
（**与真实发送循环共用同一份 `_run_send()` 代码**，只把 `sendto` 置空 → 自检的就是实跑那段）

三次独立运行：

| 次 | min | avg | p50 | p95 | max | 忙等命中 | OS 抢占 | 平均周期比目标 |
|---|---|---|---|---|---|---|---|---|
| 1 | **12.500** | 12.803 | 12.500 | 12.600 | 828.200 | 19981 | 19 | +2.43% |
| 2 | **12.500** | 12.846 | 12.500 | 12.700 | 590.100 | 19970 | 30 | +2.77% |


### 3.4 为什么不能用 `time.sleep`（R5 的实测复现）

新节奏器全程不含 sleep。忙等单次轮询成本 = `perf_counter()` **38.3–40.0 ns**，12.5 µs 周期内约 300+ 次轮询——这些都是"等待"本身，不占额外预算；而 `sleep` 在 Windows 上睡不出 µs（09-21 实测：请求 100 µs 实际 ~561–645 µs/帧，见 `testdata\storm_full.log` 与 `storm_p4.log`）。

## 六、第一性原理四问（Lead 点名）

### 6.1 ① 忙等 pacer 在 12.5 µs 周期下每帧可用 CPU 预算多少？会不会 pacer 形同虚设？

| 项 | 值 | 来源 |
|---|---|---|
| 每帧总预算 | **12.500 µs** | `--pace-us 12.5` |
| 循环体开销（取时刻、dict/list、元组解包、分支） | −0.181 µs | 自检 pace=0，20000 帧 |
| `perf_counter()` 单次 | 38.3 ns | 自检 |
| 忙等轮询本身 | **不占额外预算**（它就是"等待"），但**占满 1 个物理核** | 自检 `CPU 12.500 µs/帧` = 墙钟 |
| `sendto` 至真实网卡 | **未知**（环回下界 4.077 µs） | `--syscall-selfcheck` |
| ⇒ **留给 sendto 的余量** | **≈12.3 µs** | 12.5 − 0.18 |

**算术结论**：
- 真实 `sendto` ≤ 12.3 µs → pacer 有效，帧周期由脚本设定，E3 速率是**设计值**；
- 真实 `sendto` > 12.3 µs → 预算为负，帧间隔被 sendto 顶穿，**pacer 形同虚设**，实测速率 = PC 单进程上限。
- **"解释器单帧开销会不会顶不住"**：解释器自身开销（0.181 µs + 38 ns×轮询）**不到预算的 2%**，真正吃预算的是 `sendto` 这个 syscall。风险不在"忙等太贵"，而在"发送过快导致 syscall 排队"。
- 该失效模式**已由工具自动检测并打印**（`判定: !! pacer 形同虚设`），未上板干跑中已真实触发过一次（§3.7 D6）→ 实验中不会把它误读成硬件上限。
- **CPU 代价**：忙等满核；E2/E3 请用空闲核，与 E4/Wireshark 并行时注意别把核抢光。

### 6.2 ② `--pace-us` 与 `--gap-ms` 同时给定时如何裁决？

**显式规则（已实现并打印）**：`--pace-us > 0` **完全接管**，`--gap-ms` **被忽略**（`gap_s := 0`，L465）；`--pace-us = 0` 时走 `--gap-ms` 的 sleep 老语义。
**理由**：① sleep 无 µs 精度（R5），两者混用语义不可定义；② 防御性——E3 命令行没写 `--gap-ms` 而默认值是 1.0 ms，若"两者都生效"E3 会静默退化成 ~11.7 Mbps。
**可核查**：D1 打印 `节奏裁决: pace 接管节奏, --gap-ms=1.0ms 被忽略`；D2 打印 `未启用 pace(--pace-us=0), 用 --gap-ms=0.0ms`。

### 6.3 ③ A2 预构造包在 10 MB 负载下的内存代价是多少？

**实测（`tracemalloc`，负载 10,293,111 B）**：切片列表 10.09 MiB → 整包列表 **10.77 MiB**，**净差 +0.67 MiB（+6.7%）**。
**为什么几乎免费**：A2 不再保留 `chunks` 切片列表，整包**取代**了切片的位置；单包只多 33 B 的 `PyBytesObject` 头。
**总量算术**：单进程 ≈ `data 9.82 + pkts 10.77 + md5s 0.49` = **≈21.1 MiB ≈ 2.1× 负载**；
`--parallel 4`：每进程 spawn 各自一份 `data`(9.82) + 自己那段包体(≈2.55) ≈ **12.4 MiB/进程，4 进程合计 ≈49.5 MiB**。
⇒ **不构成任何约束**（<50 MiB）。代价方向：A2 用 ~0.7 MiB 内存换 0.485 µs/帧（≈4% 预算）。

### 6.4 ④ E3 判据「≥900 Mbps 且 100%+SHA」在 PC 侧真的可达吗？

**预判（明确标为"待验证"）**：
- 目标速率 **938.2 Mbps**（12.5 µs/帧 × 1466 B），线速上限 953.2 Mbps，判据线 900 Mbps ⇒ 允许的平均帧间隔 ≤ **13.03 µs**。
- 达标条件是 **`sendto` ≤ ~12.3 µs**。已知环回下界 **4.08 µs**；真实 NIC 值**今天测不到**（未上板干跑的 15.3 µs 是 ARP 未解析的污染值）。
- **我的预判："很可能可达，但不能在 PC 侧定论"**——未上板干跑走的是"ARP 未解析 → 内核邻居子系统排队"路径，与"板卡在线、ARP 已解析"不是一回事，用它的数字预判会得出**过于悲观**的结论。
- **100% 那一半更有把握**：相对节拍使帧间隔**恒 ≥12.5 µs > 泵B 服务 12.21 µs**（§三 定论 2-a 的裕量条件），且 OS 抢占只会让间隔**变长**（安全方向）⇒ **PC 侧不再向板端注入压缩/突发**；剩余丢失风险只来自板端本身（R1/R3/R4）。
- **验证方法（三步，工具已支持）**：
  1. **E1 定标**：`--gap-ms 0` 打满读 `发送阶段速率`，换算单帧耗时 = `1466×8 / rate(Mbps)` µs。<11 µs → E3 大概率过；12.3–20 µs → E3 会被顶穿。
  2. **E3 自证**：读 `节拍实测 avg`——≈12.5 µs 说明节拍在起作用；>13.1 µs 说明被顶穿；`判定` 行必须显示 `节拍有效`。
  3. **交叉对比（最硬）**：`E3 速率 ≈ E1 速率` → pacing 没起作用（顶穿，PC 限速）；`E3 速率 ≈ 930 > E1 速率` → pacing 生效。这条对比本身就是三问①的完整证据链（19.3 → E1 → E3 三层）。

**Lead 独立复核补充（已采信）**：Lead 独立跑同一自检得 p50 = **12.500 µs**、avg = 12.810、p95 = 12.700、min = 12.500、无背靠背突发 → 等效 **915.6 Mbps**（比目标 938.2 慢 2.48%）；`--syscall-selfcheck` 得 sendto **4.553 µs/帧**（p50 3.9 / p95 6.4）。与本记录 §3.5 的 4.077 µs（p50 3.6 / p95 5.1）、§3.3 的 12.668–12.846 µs **互相印证**（两次独立测量，量级一致）。

**E3 达标裕量的算术（关键）**：

| 项 | 值 | 说明 |
|---|---|---|
| 判据线 / 目标 | 900 / 938.2 Mbps | 判据线 ÷ 目标 ⇒ **允许总损耗 ≤ 4.07%** |
| 已测 OS 抢占税（离线，不含 sendto） | **1.34–2.77%**（本文 3 次）；**2.48%**（Lead 1 次） | 唯一已量化的损耗项 |
| 扣掉后的期望速率 | 938.2 × (1−0.0248) = **914.9 Mbps** | **≥900 ✓** |

⇒ **光 OS 抢占税不会让 E3 掉出 900**，但它**吃掉一半以上预算**（4.07% 中的 2.48%），留给"真实 sendto 抖动 + NIC 背压"的只有 ~1.6%。**E3 的瓶颈预计就是这 ~2.5% 的 OS 抢占损失叠加未知的 sendto 成本**；若上板实测 <900，第一嫌疑即这两项之和。

**备选动作（若不达标，按此顺序试）**：
