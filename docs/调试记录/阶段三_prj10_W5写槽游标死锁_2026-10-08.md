# prj10 W5 · 写槽游标死锁（RND 模式，2026-10-08）

> **一句话**：写槽号取自「提交计数」，而拒收时提交计数不动 ⇒ 游标停在满槽上再也推不动，RND 模式下无人能解锁。

---

## 一、现象：命令通了、写也「成功」，却读回 0 帧

runt 修复后重烧，单条命令立即得到应答（PROBE: RESPONSE_OK），J3 主轮一度 **PASS**（16/16 逐帧一致、逆序对 52）。但随后出现**间歇失败**，且每次重跑的**第一轮必失败**。失败样本的形态极其特定：

~~~
复核: u_wr_frame 283 → 299（增量 16，期望 16）  u_buf_drop=0   <- 写侧「全成功」
命令应答 16/16（命令通道完全正常）
读回帧 0/16 —— 16 条 READ_SLOT 全部超时无数据帧
~~~

**写侧报 16/16 成功、读侧却是 0** —— 这个矛盾就是突破口：u_wr_frame 数的是「**接受**」，不是「**提交**」。

---

## 二、定位：ILA 实测两个计数器发散

四域 ILA 快照（scripts/dbg_snap.tcl + parse_chk2.py）：

| 信号 | 域 | 含义 | 值 |
|---|---|---|---|
| dbg_mem_u_wr | user_clk | **接受**帧数（u_wr_frame_cnt） | **334** |
| dbg_mem_wm | ui_clk | **提交**帧数 / 写槽游标（stat_wm） | **278** |
| dbg_mem_wr_frm | ui_clk | 提交帧数 | 278 |
| dbg_mem_rd_frm | ui_clk | 已读出（退休）帧数 | 257 |
| dbg_mem_ost | ui_clk | 在途未读 | 21 |
| dbg_mem_u_drop | user_clk | user 域丢弃 | **0** |

**发散 = 334 − 278 = 56 帧：被接受、却从未提交**，且 u_buf_drop=0 说明不是 user 域丢弃 ⇒ 全部卡在「写被拒」这条路径上。

---

## 三、根因：游标停在满槽上，RND 模式无人解锁

RTL 事实（修改前）：

~~~verilog
wire [7:0] w_slot_next = stat_wm[7:0];        // 写槽号 = 提交计数 mod 256
wire       w_no_room   = full_bit_q[w_slot_next];
// 提交成功（B 响应）时：
stat_wm <= stat_wm + 16'd1;                    // 只有这一处推进！
// 被拒时（W_IDLE -> W_DRAIN）：
if (w_slotfull) stat_wr_stall <= stat_wr_stall + 16'd1;   // 计数，但游标不动
~~~

推导：

1. RND 模式下桥① **不再自动读**（W5 的设计前提），槽只在 PC 发 READ_SLOT 时退休；
2. 于是未读槽会长期保持 FULL；
3. 写游标一旦推进到某个「仍未读走」的满槽，w_no_room=1 ⇒ 该帧走 W_DRAIN 被整帧拒收；
4. **游标不动** ⇒ 下一帧仍指向同一个满槽 ⇒ 又被拒 ⇒ **永久卡死**；
5. 与此同时 u_wr_frame（user 域接受计数）继续 +1 ⇒ 与 stat_wm 发散；
6. 上位机按契约「写槽 = 帧计数 mod 256」用 u_wr_frame 推算槽号 ⇒ **全错** ⇒ 读的是空槽/陈旧槽；
7. 由于不知道真正的卡住槽号，PC **无法**通过读一次来解锁 ⇒ **不可恢复**。

> **为什么 W2/W4 没暴露**：SEQ 模式有自动读——被拒的那个满槽迟早被自动读出并退休，游标随即恢复推进。**只有 RND 模式会卡死**，而 RND 正是 W5 引入的新模式。

> **为什么会「第一轮必失败」**：第一轮失败（PC 侧 ARP 老化导致帧没到板卡）留下若干未读满槽；后续轮次写入正常，直到游标撞上那些满槽 → 卡死。这也解释了「每次重跑第一轮失败、之后通过，直到某次彻底卡死」的诡异规律。

## 四、修法：槽游标与提交计数解耦

~~~verilog
reg  [15:0] wr_slot_ptr;                       // 新增：槽游标
wire [7:0]  w_slot_next = wr_slot_ptr[7:0];    // 槽号分配用它

// 提交成功时：
wr_slot_ptr <= wr_slot_ptr + 16'd1;            // 与 stat_wm 同步推进
// 被拒时：
wr_slot_ptr <= wr_slot_ptr + 16'd1;            // ★关键：也推进，否则死锁

// 槽域判断（RND 量程 / clamp / 目标检查）一并改用槽游标：
wire [7:0] c_clamp  = (wr_slot_ptr == 0) ? 0 : wr_slot_ptr[7:0] - 1;
wire       c_in_rng = (wr_slot_ptr >= 256) || (cmd_slot < wr_slot_ptr[7:0]);
wire       p_target_ok = (wr_slot_ptr != 0) && full_bit[pre_eff];
~~~

**为什么这样是对的**：

- wr_slot_ptr 对**每一帧**（提交或被拒）都 +1 ⇒ wr_slot_ptr ≡ u_wr_frame（接受计数）⇒ 契约「写槽 = 帧计数 mod 256」**重新成立**；
- 被拒帧仍按契约**整帧丢弃**（stat_wr_stall 计数、不覆盖未读槽，原槽字节仍可被读出）；
- 游标永不停止 ⇒ **死锁消除**：即使 256 个槽全满，游标绕环前进，PC 始终能用 u_wr_frame 推出正确槽号并读取解锁；
- stat_wm / stat_wr_frame 语义**不变**（仍是「已提交帧数」）⇒ W2 判据不受影响。

**回归证据**：

~~~
W2 六用例 : PASS (0 errors)
  wm=585 wr_frame=585 rd_frame=585 wr_stall=1 ill_rd=3 noframe=0 bresp_err=0   <- 逐字不变
  服务 wr=933 / rd=921 ui-cycles/frame  hold_cycles=24098                     <- 与基线同
W4 联合   : 负向 FAIL(deadlock) + 正向 PASS (0 errors)
~~~

## 五、另一个独立缺陷：PC 侧 ARP 老化（测试工具伪故障）

排查过程中先撞上的是**假故障**：清掉 PC 的 ARP 条目后立即发 16 帧（间隔 1.5ms，共 24ms），板内只收到 **2 帧**，而 u_buf_drop=0（帧根本没到板卡）。

机制（准确版，2026-10-08 深夜修正）：**RND 模式下板子根本无法应答 ARP** —— RND 下桥① 不自动读，板子要发的任何帧（含 ARP 应答）都得走「栈 → 泵A → 内存 → …」这条路，而 RND 不自动读 ⇒ 应答帧出不来 ⇒ PC 邻居表老化成 `Unreachable`（`Get-NetNeighbor 192.168.1.10` 实测 MAC 全 0）⇒ 单播数据帧被直接丢弃；广播命令不需要 ARP，故通道一直正常。
先前的「Windows 在 ARP 解析窗口丢帧」只是表象。**修法**：引擎每轮开测前先切 `SEQ`（板子能应答 ARP）→ UDP 探测刷新邻居表 → 再切 `RND`；收尾恢复 `SEQ`。实测 WLAN 全程连接下连续 4 轮全 PASS。

**修法（测试工具侧）**：j3_random_read.py 增加 warmup_link() —— 数据阶段前用 **UDP 单播探测**预热 ARP。

> ⚠️ **不能用 ping 预热**：RND 模式下桥① 不自动读，ICMP 回包会被写进内存取不出来 ⇒ ping 必然无应答，无法完成 ARP 解析。实测 ping 预热无效，UDP 探测有效。

## 六、定案

| 项 | 结论 |
|---|---|
| 命令通道（runt 修复后） | ✅ 通：单条命令 0.169ms 得到 P10R 应答 |
| 随机读功能 | ✅ 通：16/16 逐帧一致、逆序对 52、u_rd Δ16 |
| **写槽游标死锁** | ❌ **设计缺陷，已修**（wr_slot_ptr 解耦），待重建重验 |
| PC 侧 ARP 老化 | ⚠️ 测试工具伪故障，已在引擎加 UDP 预热 |
| 教训 | ①「接受计数」≠「提交计数」，跨域计数器暴露给上位机时必须明确语义与其差值来源；②任何「拒收后不推进指针」的流控在无自动排空的模式下都会死锁；③排查假故障（ARP）与真缺陷（死锁）必须分开定性，否则会把工具问题误判成硬件问题（或反之） |
