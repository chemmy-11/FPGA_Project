# prj10 W5 · 命令通道上板缺陷：以太网 runt 帧（2026-10-08）

> **一句话**：板内一切正常、帧完全正确、FCS 经独立参考校验——**但帧太短**。58 字节 < 以太网最小帧 64 字节，**网卡在硬件层丢弃、不计错误、不可观测**。加 6 字节填充即愈。

---

## 一、现象

J5 上板（WNS +0.001 位流，19:31 版）后按验证单执行：

| 步骤 | 结果 |
|---|---|
| 位流版本闸门 | ✅ SHA256 与预期一致 |
| 烧录 + 体检 | ✅ `PROGRAM_OK` · 4 ILA + 1 MIG · 四域时钟在跑 |
| J6 数据面回归（ping / 四档） | ✅ ping 20/20 · `DDR_VERIFY: PASS`（基础 12/12、槽深 12/12、稳定 300/300） |
| **第 4 步 命令通道冒烟** | ❌ **`SET_MODE` 3 次重试全部超时无应答** |

脚本日志里的 `len=8` 杂包经裸探测器（`cmd_probe.py`）判定为 **PC 自有广播回环副本**（+0.012ms 立即到达）——不是板子回应。

---

## 二、定位（五步，每步都排除了一个假设）

### 2.1 差分 ILA 快照 → 解析/CDC/执行 全部正常

`scripts/dbg_snap.tcl`（带 tag 的四域立即快照）+ `scripts/parse_snap.py` 比对：

| 探针 | before | after | 判读 |
|---|---|---|---|
| `dbg_cmd_rx`（eth 域收命令计数） | 3 | **5** | 命令**收到了** |
| `dbg_cmd_err` | 0 | 0 | 解析无错 |
| `dbg_cmd_exec`（**user 域**执行计数） | 3 | **5** | 跨时钟域 mailbox **通了**、执行了 |
| `dbg_cmd_mode` | 1 | 1 | **SET_MODE 真的生效**（桥已切 RND） |

> 注意：烟雾测试那 3 次重试同样被收到并执行（`cmd_rx=3`），说明**接收侧从头到尾都是好的**。

### 2.2 纠正一个方法论错误

`dbg_cmd_respbsy` 在快照里恒为 0，一度被误读为「应答从未发出」。**但它是电平信号**，而快照是在命令发出 1-2 分钟后抓的——只能证明"那一刻"为 0。计数器才是累积量。**不能用电平快照推断一次性事件是否发生过。**

### 2.3 触发式捕获 → 应答帧确实完整发出了

`scripts/dbg_trig_resp.tcl`（触发条件 `dbg_cmd_respbsy == 1`，`wait_on_hw_ila -timeout` + 文件标志同步）：

~~~
TRIG_RESULT: TRIGGERED
resp_busy=1 连续 68 拍（样本 1024..1091，触发点居中）
cmd_rx 在触发点 0x0f -> 0x10      cmd_err = 0
~~~

**68 = E_TXPRE(1) + 66 字节 + E_TXE(1)** —— 应答 FSM 完整走完，66 字节全部以 `resp_tx_en=1` 送出。

### 2.4 网卡统计 → 帧根本没到 PC

~~~
发 15 条命令前后:
  ReceivedUnicastPackets : 34672 -> 34672   (零增量!)
  ReceivedPacketErrors   : 0
  ReceivedDiscardedPackets: 0
~~~

板内发了 15 个应答帧，PC 网卡**一个都没收到、也没有任何错误计数**。

### 2.5 实现网表核对 → 排除「接管 mux 没生效」

打开构建成功后的 `post_route.dcp`（`scripts/inspect_mux.tcl`）：

~~~
CELL cmd_takeover_reg  REF=FDCE      (锁存真实存在, 未被优化掉)
CELL cmd_takeover_i_1  REF=LUT3      I0=cmd_tx_idle  I1=dbg_cmd_respbsy  I2=Q
PIN  u_gmii_to_rgmii/gmii_tx_en  NET=rgmii_tx_en_o      (mux 输出确实接到转换器)
PIN  u_gmii_to_rgmii/gmii_txd[0] NET=rgmii_txd_o[0]
PIN  u_cmd/tx_idle               NET=cmd_tx_idle  <- tx_idle_cnt_reg[6]/Q
~~~

接管逻辑 D = resp_busy & (tx_idle | Q) — **与 RTL 意图逐位一致**，硬件里没有任何丢失。

## 三、根因：以太网最小帧

算术闭合（这是决定性的一步）：

~~~
应答帧 = 6 dst MAC + 6 src MAC + 2 ethertype + 20 IP + 8 UDP + 12 payload + 4 FCS
       = 58 字节（不含前导码）
以太网最小帧 = 64 字节（不含前导码）
58 < 64  ->  RUNT  ->  网卡硬件层静默丢弃
~~~

**为什么之前所有验证都没抓到**：

| 验证层 | 为什么没抓到 |
|---|---|
| 单元 TB | 校验了前导码、MAC、IP、UDP、载荷、**FCS（独立参考 CRC + 残差）**——唯独**没有校验最小帧长** |
| 仿真波形 | 帧"完整发出"在仿真里就是成功，SIM 没有网卡 |
| 板内 ILA | resp_busy 68 拍、字节流完整——板内视角一切正常 |
| 网卡统计 | runt 在硬件层丢弃，**不计入 Windows 可见的错误计数** |

> 这是典型的**跨层不可观测缺陷**：每一层单独看都正确，缺陷只在"网卡硬件"这一层显现，且不留痕迹。

---

## 四、修复

按 **RFC 894**：以太网填充**不计入** IP total length / UDP length，仅参与 FCS 计算。

~~~verilog
// 布局 (72 字节):
//  [0..7]   前导码 55*7 D5
//  [8..21]  以太头 14B
//  [22..41] IP 头 20B  (IP_TOTAL_LEN 保持 40, 不含填充)
//  [42..49] UDP 头 8B  (UDP_LEN 保持 20)
//  [50..61] 载荷 12B
//  [62..67] ★新增 6B 填充 (00)
//  [68..71] FCS (覆盖 8..67)

localparam [6:0] FRM_BODY_END = 7'd67;   // 原 61
localparam [6:0] FRM_LAST     = 7'd71;   // 原 65
// ti_next_b 的 FCS 字节位置 62/63/64 -> 68/69/70
~~~

线路长度 = 8(前导) + 64 = 72 字节 ✓

### 补测（防止回归）

单元 TB 新增**最小帧长护栏** + 填充字节全零校验：

~~~systemverilog
if ((frame_len[fi] - 8) < 64)
    fail("... on-wire length %0d < 64 -> RUNT (NIC drops silently)");
for (int i = 62; i <= 67; i++)
    if (cap[fi][i] !== 8'h00) fail("... padding[%0d]=%02x", ...);
~~~

**负向对照（护栏自证有牙）**：用 git 里修复前的 `cmd_channel.v` 跑新 TB →

~~~
=== prj10 W5 CMD SIM: FAIL (45 errors) ===
[FAIL] C8/reply#0: length 66 (expected 72)
~~~

修复后正向：`=== prj10 W5 CMD SIM: PASS (0 errors) ===`

## 六、教训

1. **"板内正确"与"对端收到"之间有一层不可见的物理约束**——以太网最小帧只是其中之一；同类还有 IFG、前导码、CRC。协议层的"常识约束"必须写进测试。
2. **电平快照不能推断一次性事件**——计数器才是累积证据（本次差点被 `respbsy=0` 误导）。
3. **触发式捕获 > 立即快照**：一次性事件的定位必须用触发条件捕获，且等待 API 要选对（`wait_on_hw_ila -timeout`，2023.1 无 `-trigger`）。
4. **实现网表核对是排除"RTL 写了但硬件没有"的最后手段**：`post_route.dcp` 里查 LUT INIT 与引脚连接，比反复推测有效得多。
