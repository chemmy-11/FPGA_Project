# prj10 · 速率瓶颈诊断与 L2 写路径流水化（2026-10-09）

> **一句话**：速率不是被带宽卡住的，是被**桥写 FSM 每帧等一次 DDR 写响应**卡住的 —— 20.3 µs/帧的纯延迟，与 MIG 带宽无关（占用仅 3–5%）。

> ⚠️ **模型更正（2026-10-09 晚，读者必读）**：上句中 20.3 µs/帧固定开销 是**测量方法的假象**，不是设计属性。
> 拟合用的三个点里，128 B 那一档的 pace=20 µs 意味着 PC 最多只能报 **50k 帧/秒** —— 板卡对 128 B 的真实上限
> （≥117k fps）被 PC 限速**遮住**了，于是线性拟合把 PC 的节拍当成了板卡的固定开销。
> 用 pace=5 µs（200k fps 报价）重测后，正确模型是 **T = 7.0 µs + 11.6 ns/字节**（拟合误差 <5%）：
> 固定项只有 ~7 µs，**字节项 11.6 ns/B = 线速到达 8.0 + 泵排出 3.33（被握手串行）才是主要矛盾**。
> ⇒ 教训：**测上限必须让报价显著高于被测上限**，否则拟出来的参数是测试台的，不是被测件的。

## 一、起点：零丢包速率只有 58–117 Mbps，预算是 957 Mbps

2026-10-09 板卡实测（PRJ9 同款 `json_storm.py` 速率扫描）：

| pace | 发送速率 | 到达率 |
|---|---|---|
| 1 ms | 11.7 Mbps | **100%** |
| 200 µs | 58.5 Mbps | 99.99% |
| 100 µs | 116.5 Mbps | 99.79% |
| 60 µs | 184.8 Mbps | 96.80% |
| 35 µs | 261.4 Mbps | 81.26% |
| 13 µs | 399.1 Mbps | 51.45% |

而设计预算（实施单 §九）是**全链路节拍 ≈957–959 Mbps、两级桥 2.09–2.39× 余量**。落差 8–10×。

## 二、诊断链（每一步都是实验，不靠推测）

### ① 丢在哪：入口泵A 闸门，不是内存桥

新写 `scripts/rate_probe.py`（不依赖 ILA，用命令通道读板内 `u_wr_frame`）：

| pace | 发出 | 到达内存桥 | **入口丢** | **出口丢** | 桥内拒收 |
|---|---|---|---|---|---|
| 200 µs | 1000 | 1000 | **0%** | **0%** | 0 |
| 60 µs | 1000 | 976 | **2.40%** | 0% | 0 |
| 20 µs | 1000 | 538 | **46.20%** | 0.40% | 0 |

**两级内存桥一帧没丢。**

### ② 闸门服务率存在硬上限

| pace | 发出帧率 | 到达帧率 | 入口丢 |
|---|---|---|---|
| 60 µs | 16,666 | 16,267 | 2.4% |
| 40 µs | 24,999 | 22,063 | 11.8% |
| 30 µs | 33,332 | 22,650 | 32.1% |
| 25 µs | 39,996 | **26,400** | 34.0% |
| 20 µs | 49,994 | **26,900** | 46.2% |

**⇒ 饱和在 ≈25,000–27,000 帧/秒。**

### ③ 拆解：固定项 + 字节项

改 `rate_probe.py` 支持 `--len`，三种帧长测上限：

| 帧长 | 到达帧率 | 每帧时间 |
|---|---|---|
| 128 B | 45,925 | 21.8 µs |
| 512 B | 38,150 | 26.2 µs |
| 1466 B | 26,500 | 37.7 µs |

线性拟合 **T = 20.3 µs + 11.9 ns/字节**（三点全部吻合，误差 <1%）。

字节项分解：线速到达 **8.0** ns/B + 泵排出 **3.33** ns/B（1 字节/拍 @300MHz）= 11.33 ≈ 11.9 ✓

**⇒ 剩下 20.3 µs 是纯固定开销**（≈6000 拍 @300MHz）。

### ④ 关键判别：是延迟还是带宽？

**RND 模式**下桥① **不自动读** ⇒ 读路径与二级桥全部空闲。此时：

| 场景 | 速率 |
|---|---|
| 全环路（SEQ，桥①边写边读 + 二级桥全忙） | 26,500 帧/秒 |
| **RND（只留桥①写路径）** | **26,365 帧/秒** |

**⇒ 速率一点没变 ⇒ 纯延迟受限，与带宽无关。** 与 MIG 占用仅 3–5% 相互印证。

### ⑤ 根因：桥写 FSM 每帧串行等 BVALID

~~~verilog
W_IDLE → W_WAIT → W_AW → W_FILL → W_PUSH → W_B(等 bvalid) → 提交 → W_IDLE
~~~

**一帧写完必须等 DDR 写响应回来才处理下一帧** ⇒ 每帧白串行一个 Lw。

## 三、L2 修复：写路径流水化

**原理**：AXI 允许**同一 ID 多笔 outstanding 且响应保序** ⇒ 把「出队提交」与「取下一帧」解耦即可把 Lw 藏进流水线。

**改动**（`rtl/axi4_master_bridge.v`，prj10 独有文件，不动 prj9 共享代码）：

| # | 改动 |
|---|---|
| 1 | 新增 **4 深提交队列** `cqs0-3/cql0-3/cq_cnt`（显式寄存器移位，无 RAM 读延迟） |
| 2 | `W_PUSH` 最后一拍：压 `{w_slot, w_len}` 入队后**立即回 W_IDLE**，不再进 W_B |
| 3 | B 响应由**同一 always 块顶部**的独立逻辑出队提交（`wr_commit/out_inc/stat_wm/stat_wr_frame`） |
| 4 | `m_axi_bready = (cq_cnt != 0)`，由出队逻辑统一驱动（原 W_IDLE/W_B 的清零已移除） |
| 5 | **槽游标 `wr_slot_ptr` 推进点从「提交时」移到「接收时」** —— 流水化后提交滞后，否则连续多帧抢同一槽号 |
| 6 | 队列满（4 笔在途）时**握停最后一拍**，保证「拍一旦发出必有地方记录」，不会重复发拍 |
| 7 | `W_B` 停用（保留状态编码缩小改动面） |

**两条设计红线（都是坑账本里的真实教训）**：

> ① **`wr_commit/out_inc/stat_wm` 必须留在同一个 always 块** —— 拆成第二个块就是多驱动（**坑账本 #25**：多驱动 reg 仿真能过、DRC 直接挂）。
> ② **`m_axi_bready` 只能有一个驱动源** —— 原 W_IDLE/W_B 都有赋值，本次统一到出队逻辑。

## 三·补、L2 上板实测结论（2026-10-09 晚，诚实记录）

L2 没有改善速率 —— 这正是先实测再决定 L1 的原因：

| 档位 | L2 前 | L2 后 |
|---|---|---|
| 1466B 帧率上限 | 26,500 fps | 25,900 fps（噪声内） |
| 512B 帧率上限 | 38,150 fps | 44,075 fps（+16%，来自固定项缩小） |

为什么：正确模型下固定项只占 1466B 每帧耗时的 ~30%（7/24 µs），L2 只动固定项，动不了占 70% 的字节项。
保留 L2 的理由：①语义正确（W2 计数逐字不变）；②时序正贡献 +0.157 ns（−0.235 → −0.078），
是把游标修复吃掉的余量挣回来的关键；③是 L1 流水化的前置（泵排出要快，桥提交就不能逐帧卡死）。

## 五、顺带解决：W6 完整探针构建的时序失败

加回 W5 命令通道探针（7 项/74 bit）后构建 **WNS = −0.235**（闸门正确拦住位流）。

失败路径：`u_mem/u_bridge/full_bit_q_reg[132] → w_beats_reg[4]/CE`，
**Data Path Delay 3.004 ns 中 route 占 2.339 ns（77.9%）** ⇒ **布线拥塞**，不是逻辑深度（logic 仅 0.665 ns）。

**修法**：4 个 ILA 全加 `C_INPUT_PIPE_STAGES 1`（探针输入加 1 级流水，解 ILA 布线拥塞的常规手段），
**两条构建脚本同步改**（`build_debug.tcl` / `build_debug_resume.tcl`），一致性校验 `BUILD_PATH_CONSISTENCY: PASS`。

## 六、L1 实施：乒乓双 bank 泵（含一次 off-by-one 失败与修复）

验收 TB（prj9 的 pump_tb_stress 改造 + 加强为逐字节校验）：200 帧 × 86 B，帧间 10 拍（≈背靠背）。

| | prj9 原版 | L1 第一版 | **L1 修复版** |
|---|---|---|---|
| 收帧 / 发出 | 100 / 200 | 200 / 200 | **200 / 200** |
| 丢帧 | **100（50%）** | 0 | **0** |
| 读出字节 | 8600 = 100×86 ✓ | 17000 = 200×**85** ✗ | **17200 = 200×86** ✓ |
| 逐字节校验 | （旧 TB 不查） | 不适用 | **byte_errs = 0** ✓ |

off-by-one 根因：accept 置位 wr_active 到下一拍才生效，首字节那拍 wr_active=0 → 未写入 RAM →
每帧丢首字节、后续字节整体左移一位。第一版 TB 只查帧数与字节总数，没查内容，放行了它。
修法：写使能改为 byte_we = wr_en & (wr_active | accept) & ~ovf（首拍同拍写入），并把帧首清计数
移到帧尾（帧首清会与首字节写入同拍冲突，是第二处吞字节来源）。

### 6.1 两条方法论教训（进坑账本 #31/#32）

| # | 教训 |
|---|---|
| 31 | 测上限必须让报价显著高于被测上限：pace=20µs 时 PC 只能报 50k fps，把 128B 档的板卡真实上限（≥117k）遮住，线性拟合于是把 PC 节拍拟成了板卡固定开销（20.3µs 假象）。换 pace=5µs 重测后固定项修正为 ~7µs，主要矛盾从固定项变成字节项，修复方向随之从 L2 转向 L1 |
| 32 | 数据通路 TB 必须逐字节校验内容，不能只数帧数/字节数：L1 第一版每帧丢首字节（86→85）且整体左移，帧数与字节总数=帧数×常数 的检查全部通过，只有逐字节比对才抓得住。配套：xvlog 报 ERROR 后 xelab 仍会用旧快照 Built 并跑出结果 —— 仿真脚本必须把 xvlog 非零退出当硬失败，否则会拿旧产物骗自己 |

### 6.2 L1 的预期收益（待上板实测）

字节项 11.6 → 8.0 ns/B（排出与下一帧到达重叠）⇒ 1466B 帧上限 41.7k fps → ~81k fps（957 Mbps，线速）。
