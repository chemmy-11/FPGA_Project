## §1 三分钟看懂我们在做什么

### 1.1 一句话

**让数据从一台电脑出发，穿过 FPGA 和高速光链路，到达另一处再原样回来——并且要求"快、稳、可验证"。**

### 1.2 为什么要用 FPGA 做这件事

普通电脑网卡做转发，靠操作系统协议栈，时延是"尽力而为"的（几十微秒到毫秒级抖动，还不确定）。FPGA（Field-Programmable Gate Array，**现场可编程门阵列**——一块出厂后还能被"重新接线"的芯片）的价值在于：

- **确定性**：硬件电路一拍一拍地跑，时延可算、可复现，不受操作系统调度干扰；
- **线速处理**：数据来的多快就处理多快，不"排队等 CPU"；
- **可定制**：协议栈可以只保留我们需要的部分（比如只做 UDP 不做 TCP），砍掉的都是时延。

### 1.3 课题定位

- **大背景**：实验室在做 AI Infra（人工智能基础设施）——让多台机器协作跑大模型推理。机器之间要频繁交换数据，"网络好不好"直接决定整体性能。
- **我们的角色**：**互连层**。不去做 AI 算法，而是造一张**低时延、高吞吐、行为可预测**的板间网络。
- **本期范围（已与导师定案）**：**先做单板闭环**，把"内存读写"塞进数据环路里（详见 §6）；板间组网作为并行线推进。

### 1.4 数据是怎么流的（记住这张图就懂一半）

```
   PC(上位机)                 FPGA 板卡                        光/对端
 ┌──────────┐   千兆网口   ┌──────────────────────┐   10G 光   ┌────────┐
 │ 发送脚本 │ ──────────► │ 以太网栈(收/UDP解析)  │            │        │
 │ udp_verify│            │        ↓             │            │ 另一块 │
 │ json_storm│            │  帧泵(跨时钟域搬运)   │ ────────► │ 板卡或 │
 └──────────┘            │        ↓             │   光纤      │ 光回环 │
       ▲                 │  打包 8→64 位         │            │        │
       │                 │        ↓             │            └────────┘
       └──── 回程原路返回 ─┤  Aurora 64b/66b 链路 │
                         └──────────────────────┘
```

一句话：**网口进 → 板内搬运 → 光口出 → 对端原样送回 → 光口回 → 板内搬运 → 网口出**。我们所有的工作，都是在把这条链上的每一段**做通、做稳、测准**。

## §2 硬件平台：我们手里的这块板

### 2.1 板卡与核心器件

| 项 | 值 | 说明 |
|---|---|---|
| 板卡 | 正点原子 **KU060** 开发板 | 教学/开发板，资料齐全 |
| 主芯片 | Xilinx Kintex UltraScale **XCKU060** | FPGA 本体 |
| 器件型号（part）| `xcku060-ffva1156-2-i` | **务必记牢**：不是 `xcku060_CIV`（早期踩过坑，见 §4.1） |
| 硬核处理器 | **无**（该系列不带 ARM） | 所以需要"软核"MicroBlaze 顶替（见 §3） |
| 板载 DDR4 | 4 GB（×4 颗 MT40A512M16） | 目前用于"内存进环路"课题 |

### 2.2 时钟与复位（数字电路的"心跳"与"归零"）

- **主时钟**：板上 100 MHz **差分**晶振 → 引脚 `AK17/AK16`（差分 = 用两根线传一个信号，抗干扰强）
- **GT 参考时钟**：156.25 MHz → 引脚 `T6/T5`（给高速收发器用，见 §3 的 GT）
- **复位**：引脚 `AC34`，**低电平有效**（拉低 = 复位，拉高 = 正常工作）

### 2.3 四个光口（"笼位"）——最容易记混的地方

板上有 4 个 SFP+ 光模块笼位，编号不是简单 A/B/C/D，而是绑在 FPGA 内部的 **GT Quad**（4 个高速通道为一组）上：

| 笼位 | FPGA 内部位置 | 本项目用途 |
|---|---|---|
| **A** | X1Y11 | ✅ **主干**：prj9 用它做"去程"光链路 |
| **B** | X1Y9 | ✅ **主干**：prj9 用它做"回程"光链路 |
| C | X1Y10 | 空闲（备用/后续眼图观测） |
| D | X1Y8 | 空闲 |

> prj9 的做法：A 口出一个光模块 → **LC 跳线**（一对光纤，一头一发一头一收）→ 回到 B 口。
> 数据因此**两次经过光**（出去一次、回来一次），比单口自环更接近真实组网。

### 2.4 双千兆网口

- GE1 / GE2，PHY 芯片 YT8531，接口形式 **RGMII**
- 固定 IP：**板卡 192.168.1.10** ↔ **PC 192.168.1.102**
- 这是"上位机 ↔ 板卡"的唯一数据入口（本期定案：**端点一律走千兆网口**）

### 2.5 调试通道

| 通道 | 用途 |
|---|---|
| **JTAG** | 烧录位流（掉电即失，每次上电要重烧） |
| **串口**（COM7@9600）| 软核打印（如 MicroBlaze 的 Hello World） |
| **LED T23** | **链路指示**：Aurora 链路建立（channel_up）就常亮——这是判据第一层 |
| **LED T22** | 观测用 |
| **ILA** | 片内逻辑分析仪（见 §3），抓内部信号波形 |

## §3 FPGA 术语速查（不常见名词一句话解释）

> 按"你会先碰到哪个"排序。**括号里是"在本项目里指什么"**。

### 3.1 开发流程类

| 术语 | 一句话解释 |
|---|---|
| **RTL** | Register Transfer Level，**寄存器传输级**——用代码描述"每个时钟沿数据怎么在寄存器之间流动"，是 FPGA 设计的源码形式（我们写的是 Verilog） |
| **综合（Synthesis）** | 把你的 RTL 代码"翻译"成芯片里真实存在的逻辑门和触发器 |
| **实现（Implementation）** | 把综合结果**摆到芯片的具体位置**并**连好线**（含 place 布局 + route 布线） |
| **时序收敛** | 布线完成后检查"信号能不能在下一个时钟沿到来前稳定传到"；全部通过叫收敛 |
| **WNS / WHS** | Worst Negative Slack / Worst Hold Slack，**最差建立/保持裕量**。正数=有余量，负数=违例，**0 附近=零余量**（本项目多处处于零余量，属于"贴着线速设计"的代价） |
| **位流（bitstream）** | 最终给 FPGA 的"配置文件"（`.bit`），烧进去芯片才变成你要的电路。**掉电即失** |
| **XDC** | 约束文件：告诉工具"这个信号接哪个引脚""这个时钟多快"。**只能是受限 Tcl**（见 §5 红线） |
| **Tcl** | 一种脚本语言，Vivado 的命令行/批处理都用它（我们的构建脚本就是 `.tcl`） |
| **xsim** | Xilinx 自带的**仿真器**——不接板子，在电脑上跑波形验证逻辑 |
| **testbench（TB）** | 仿真用的"激励 + 检查"程序：给被测模块喂输入，检查输出对不对 |

### 3.2 芯片资源类

| 术语 | 一句话解释 |
|---|---|
| **LUT** | 查找表，FPGA 实现组合逻辑的基本单元（可以理解成"万能小逻辑门"） |
| **FF** | Flip-Flop，**触发器**，存 1 bit 的寄存器 |
| **BRAM** | Block RAM，芯片内的小块存储器（本项目用于帧缓存，几 KB 量级） |
| **DSP** | 芯片内专用的乘法累加单元（本项目基本没用） |
| **资源占用** | 综合报告会告诉你用了百分之几的 LUT/BRAM——用满了就得换芯片或改设计 |

### 3.3 高速接口类

| 术语 | 一句话解释 |
|---|---|
| **GT / GTH / 收发器（Transceiver）** | 芯片里专门跑**超高速串行**的硬核电路，10 Gbps 级别。光通信就靠它 |
| **Quad** | GT 的"宿舍"：4 个 GT 通道为一组，共享一个参考时钟 |
| **refclk** | 参考时钟。GT 必须有一个高质量时钟作基准（本板 T6/T5 = 156.25 MHz） |
| **SFP+ / 光笼** | 插光模块的金属笼子；SFP+ 是模块规格（10G 级） |
| **LC 跳线** | 一对细光纤 + LC 接头，把两个光口连起来 |
| **Aurora 64b/66b** | Xilinx 的**板间链路层协议**：把数据可靠地送上光、并保证对端能正确还原。**64b/66b = 每 64 位数据加 2 位同步头**（编码开销仅 3%，比老的 8b/10b 的 25% 省得多） |
| **channel_up / lane_up** | Aurora 的"链路已建立"标志位：所有通道都同步上才拉高。**我们的数据通路被它硬门控**（链路没起来就对外静默） |
| **IBERT** | Xilinx 的**误码率测试工具**：往链路里灌已知数据，统计错了多少位 |
| **PRBS** | 伪随机比特序列，IBERT 用来灌的测试图案 |
| **眼图** | 把高速信号叠加显示，看"眼睛"张得开不开——张得开代表信号质量好 |

### 3.4 网络协议类

| 术语 | 一句话解释 |
|---|---|
| **MAC / PHY** | 以太网的"协议层芯片（MAC）"与"物理层芯片（PHY）" |
| **RGMII / GMII** | MAC 与 PHY 之间的接口形式。GMII 是 8 位宽 + 125 MHz = 1 Gbps；RGMII 把它压成 4 位宽 + 双沿采样 |
| **ARP** | 由 IP 地址查 MAC 地址的协议（ping 之前都要先 ARP） |
| **ICMP** | ping 用的协议 |
| **UDP** | 无连接传输协议：不握手、不重传，**快但可能丢**。本项目用它做快路径 |
| **MTU / 分片** | 一个以太帧最大能装多少。**超了就要分片，而我们的板端栈不做分片重组 → 分片包会被整包丢弃**（这是踩过的坑，见 §4.7） |

### 3.5 板内数据搬运类（**本项目的技术核心**）

| 术语 | 一句话解释 |
|---|---|
| **时钟域** | 同一时钟驱动的电路区域。板上同时存在 125 MHz（网口）、151.5 MHz（光口恢复钟）、300 MHz（DDR 控制器）等**多个时钟域** |
| **CDC** | Clock Domain Crossing，**跨时钟域**。两域之间直接传数据会出错（亚稳态），必须用专门结构 |
| **异步 FIFO** | 最常用的 CDC 结构：一端按 A 时钟写、另一端按 B 时钟读，靠"读写指针"协调 |
| **格雷码** | 一种相邻数只变 1 位的编码。**用它传指针，跨时钟域采样时最多错 1 个数，不会出现"全错"**——这是异步 FIFO 的标准做法 |
| **帧泵（frame pump）** | 本项目的自研模块：把一整帧数据从 A 时钟域"搬"到 B 时钟域，并保证帧的完整性（不做流式透传，而是整帧中转） |
| **握手（handshake）** | 两个模块之间"我准备好了/我收到了"的协调信号 |
| **FIFO** | First-In-First-Out，先进先出队列（数据排队的地方） |
| **AXI4 / AXI4-Stream** | ARM 系标准**片上总线**协议。AXI4 带地址（读写内存用），AXI4-Stream 不带地址（纯数据流用） |
| **DDR4 / MIG** | 板载内存及其**控制器 IP**（MIG = Memory Interface Generator，Xilinx 生成 DDR 控制器的工具）。**DDR 上电后必须先"校准"（training）成功才能读写** |
| **MicroBlaze** | Xilinx 的**软核 CPU**——用 FPGA 的 LUT 搭出来的处理器（因为这块芯片没有硬 ARM 核）。可以跑 C 代码，用来做控制面 |
| **ILA** | Integrated Logic Analyzer，**片内逻辑分析仪**：把内部信号"引出来"存进 BRAM，再上传到电脑看波形。**调试利器**，但要占用资源且必须标对时钟域 |
| **计数器差分链对账** | 本项目自创的判据方法：在数据通路每一级都放一个计数器，跑一段流量后看"上一级增加数 − 下一级增加数"，**差额就是丢在这一级**（见 §5） |

### 4.1 M1 · 软核最小系统（08-11）

**目标**：把"电脑 → FPGA → 串口打印"这条最小链路打通，同时把工具链流程固化下来。

**关键步骤**：
1. Vivado 新建工程，选对 **part**（`xcku060-ffva1156-2-i`）；
2. 用 **Block Design（图形化连线）** 搭最小系统：MicroBlaze 软核 + 本地存储器（LMB）+ AXI UART Lite + AXI Interconnect + 时钟向导 + 复位模块；
3. 写引脚约束（`xdc`）：时钟 AK17、复位 AC34、串口 AE33/AF34；
4. 综合 → 实现 → **Generate Bitstream** → **Export Hardware（含 bitstream）** 得到 `.xsa`；
5. Hardware Manager 烧录位流（成功标志 `End of startup status: HIGH`）；
6. Vitis 导入 `.xsa` → **Run Configuration 里取消 "Program FPGA"**（保留 "Reset entire system"）→ Run，程序经 JTAG 下载进 BRAM；
7. 串口 9600 应打印 Hello World。

**踩的坑（重要）**：一开始烧录报 `DONE PIN is not HIGH`。排查链是：先怀疑启动模式 → 再怀疑 JTAG 链路（用 LED 冒烟测试排除）→ **最后靠"对照实验 + 位流元数据"定位：MicroBlaze 位流的 part 写成了 `xcku060_CIV`，而实物是非 CIV**。改对 part 后一次通过。
**教训**：**硬件参数以实测为准**，教程/视频只能当参考。

### 4.2 IBERT · 光口物理层验证（08-27）

**目标**：证明"这块板的光口硬件本身是好的"——在跑协议之前先把物理层钉死。

**关键步骤**：
1. 新建工程，添加 **IBERT UltraScale GTH** IP；
2. 配置到我们实际用的 Quad（X1Y2）、参考时钟 156.25 MHz；
3. 用 **Open IP Example Design** 生成官方例程（避免自己写 GT 相关代码）；
4. **补光模块控制脚**（这是唯一需要改代码的地方：模块的 tx_disable / rate_select 等要驱动对）；
5. 写约束（**只约束控制脚**，GT 差分对由 IP 自动放置）；
6. 上板 + 插光模块 + LC 跳线跨两个口；
7. 在 IBERT 界面扫描、灌 PRBS、看误码与眼图。

**判据**：PLL Locked + 误码 **0E0**（指数显示，即 0 个错误）；眼图截图归档。

**意义**：这一层通了，后面 Aurora 出问题是"协议/逻辑问题"而不是"硬件坏了"，**排障范围直接砍半**。

### 4.3 Aurora 64b/66b 链路层（08-31）

**目标**：让板子自己能建立一条 10G 的"光链路"，并能判断链路好不好。

**关键步骤**：
1. 添加 **Aurora 64B/66B** IP，配置：10G 线速率、单通道 duplex、位置 X1Y11；
2. 生成官方例程，核对顶层端口名；
3. 写 XDC：GT refclk（T6/T5）、板载 100 MHz init clock、光模块控制脚；
4. 先做**内部环回**（数据不出芯片，直接回自己），排除光模块变量；
5. 上板，用 **ILA** 抓 `channel_up` / `lane_up` / 误码计数。

**判据**：`channel_up` 与 `lane_up` 均拉高、误码计数为 0。

**教训（写进规范的一条）**：**一个 GT Quad 里只允许出现一个 GT_COMMON**。同 Quad 要放第二个 Aurora 核时，第一个实例把 refclk/QPLL 引出（`_ext`），兄弟实例用"无 common"的版本（`_shared`）——否则综合直接报多驱动错误。这条在 §4.6 做双核时用上了。

### 4.4 以太网 UDP 网口栈（09-04）

**目标**：让上位机（PC）能用最普通的方式——**ping 和 UDP**——和板卡说话。

**关键步骤**：
1. 以官方例程 **39_eth_udp_loop** 为基底（事实源优先级最高的是官方例程）；
2. 整包移植到本项目，保留 ARP / ICMP / UDP 三个协议；
3. **RGMII 接收相位修复**：官方板与我们的板 PHY 时序不同，直接用会采错数据 → 加 `rgmii_rx_fix2.v`（**IDELAY 1250 ps + IDELAYCTRL**）逐通道修相位；
4. 上板验证三层：**T23 灯**（链路）→ **ping**（通路）→ **UDP 回环字节比对**（数据）；
5. Wireshark 抓包佐证。

**为什么这几步是这个顺序**：判据是**逐层收紧**的。灯亮只说明链路建立，ping 通只说明包能走，**只有逐字节比对才能证明数据没错**——这条"三层证明力"后来成了全项目的标准判据写法（§5）。

### 4.5 数据级桥 M2（09-18）

**目标**：让 **PC 发的 UDP 数据，真的穿过 Aurora 光链路，再原样回到 PC**——这是"板子能当中继"的第一个完整证明。

**关键步骤**：
1. 把"以太网栈"和"Aurora 链路"拼在一起；
2. 写两个"翻译模块"：**axis_word_pack / axis_word_unpack**——把网口的 **8 位宽**数据流，打包成 Aurora 要的 **64 位宽**（及其逆过程）；
3. 加**双向帧泵**：跨时钟域搬运整帧数据（网口 125 MHz ↔ 光口 151.5 MHz）；
4. 上板跑判据。

**三个根因（都在这轮暴露并修掉）**：
- **unpack 对"帧中断流"敏感** → 改为**整帧存储转发**（收满一帧再发，不再边收边发）；
- **帧泵 `rd_empty` 判断用错信号**（用了"下一个值"判断当前是否空）→ 帧尾总丢 1 字节、FCS 校验错 → 改用当前值；
- **RGMII RX 采样相位**（同 §4.4）。

**判据**：ping 10/10 + 20/20 全 <1ms；`udp_verify` 12/12；压力测试 36/36 **逐字节一致**。

### 4.6 真光链路 prj9（09-21）——**当前的主力验证平台**

**目标**：不再用芯片内部环回，而是**真的插两个光模块、用 LC 跳线连起来**，数据**两次经过光**。

**关键步骤**：
1. 在 prj8 基础上加**第二个 Aurora 核**（A/B 两个笼位）；
2. 处理同 Quad 双核问题：**一个 Quad 只能有一个 GT_COMMON** → 用 `_shared` 版本（见 §4.3 教训）；
3. B 侧实现**整帧回显**：收到什么就原样发回；
4. 写**判决位流**：在三个时钟域各挂一个 **ILA**，并在数据通路各段埋计数器（为 §4.7 的对账做准备）；
5. 上板：A 口 → 光模块 → LC 跳线 → B 口 → 回来。

**判据**：T23 常亮 + ping 20/20 + `udp_verify` 12/12 + 压力 36/36 + **复测无楔死**；时序收敛（WNS > 0）。

**踩的大坑**：跑着跑着**第 25 帧后链路全灭**。根因是**帧泵的"满"判断**：写时钟域用二进制计数、读时钟域用格雷码，两者在跨 2048 回绕时"混比"→ 永久伪满。修法：标准 Cummings 格雷码满判 + 帧原子性 + 复位对称。
**方法论**：这条走的是 **"板上必现 → 仿真复现 → 修复 → 回归"** 的标准三连，后来沉淀成规范。

### 4.7 传输质量评测 + 0.4% 丢失根因定案（09-21）

**目标**：不只看"通不通"，还要看"**传 10 MB 一个字节都不能错**"。

**关键步骤**：
1. 写评测脚本 `json_storm.py`：把真实会话 JSON（10 MB）切片、加序号头、逐帧发；接收端重组 + **SHA256 校验**；
2. 分三档跑：**质量档**（慢速求正确）、**性能档**（单流求速度）、**容量档**（多进程冲击）；
3. 发现慢节奏下有 **0.4% 的"相邻对丢失"** → 上**判决位流**（三域 ILA + 六段计数器差分链）定位；
4. **差分链对账**（见 §5）指出丢失集中在 pack 输出环节 → 根因 = **pack 的输出队列深度只有 2，溢出时把 `tlast`（帧结束标志）吞掉了，导致两帧被合并成一帧**；
5. 把队列深度 **2 → 16**，重出位流复测。

**结果**：**10 MB 全量 100% + SHA256 一致**（历史首次）；`json_reliable.py`（带选择性重传的真实业务层）交付 100%、0 重传。

**教训**：**"通"和"对"是两件事**。0.4% 的丢失在 ping 测试里完全看不出来。

### 4.8 传输效率归因（09-29）

**背景**：性能档测出来只有 **19.3 Mbps**，离千兆口差 49 倍。大家第一反应是"FPGA 太慢了吧？"

**做法（第一性原理：把每一级"每帧要花多久"都算出来）**：
1. **读 RTL 逐级核算**每帧服务时间：网口 12.3 µs、栈发送 12.24 µs、帧泵 12.21 µs、光口 1.22 µs……；
2. 得出**全链路上限 ≈ 957–959 Mbps**——**恰好压在千兆口净载荷上限 953 Mbps 之上**；
3. 反过来查 PC 侧：脚本每帧调了一次 `time.sleep()`，而 **Windows 的定时器精度只有约 500 µs**，于是每帧被硬生生拖到 561 µs；
4. **结论：19.3 Mbps 是 PC 脚本睡出来的，不是板子慢**。板子实际是"贴着线速设计、几乎没有余量"的结构。

**副产品（很重要）**：
- 明确了**帧长契约**：单帧净载荷 **1466 字节**（写 1472 会触发 IP 分片，而板端不做重组 → **整包丢弃**）；
- 把 PC 侧脚本改造好（忙等节奏器 `--pace-us`、预构造包、扩大发送缓冲），并规划了 **E1–E5 五级实验**去逐层钉死瓶颈归属；
- 定义了**线速工作点**：帧周期 12.5 µs → 目标 938 Mbps，判据 **≥900 Mbps 且 100% + SHA 一致**。

**这就是"答辩要讲得出原理"的典型**：一个数字（19.3）背后，是能逐级拆开、每级都有依据的预算表。

### 4.9 内存进环路 prj10（09-29 起，进行中）

**目标**：把**内存读写**塞进数据环路——"以太网数据先写进内存，再从内存里挑地址读出来，经光回环，再存进内存，最后读出来发回以太网"。

**已完成（W2）**：
1. 设计三层 RTL：`async_fifo`（跨时钟域缓冲）+ `axi4_master_bridge`（**自研 AXI4 主端**，即"主动去读写内存"的那一侧）+ `frame_mem_if`（帧接口）；
2. 写一个**行为级 AXI4 RAM 替身**（先用假内存验证逻辑，不用等真 DDR 控制器）；
3. 写**六个用例的 testbench**，覆盖：校准前零活动 / 逐字节一致 / 乱序读 / 非法读 / 300 帧回绕 / 槽满不覆盖；
4. `xsim` 跑通：**PASS (0 errors)**。

**这一轮的额外收获（两次"仿真 PASS ≠ 硬件成立"）**：
- **多驱动缺陷**：一段逻辑被两个 `always` 块同时驱动，**仿真器完全静默**（`xvlog` 0 警告），但**真综合会保留常量驱动、丢弃逻辑驱动** → 上板计数器恒为 0。**教训：多驱动只能靠真综合判**；
- **替身模型的适用边界**：假内存"立即应答、地址只取低 20 位"，所以 PASS **不覆盖** AXI4 端口合规性和真 DDR 的延迟特性——后续 W3 必须换真 MIG 再验。

**当前（W3）**：补 12 个缺失的 AXI4 端口 → 换真 MIG → 两级插桥 → 上板联调。

## §5 判据体系：我们怎么"证明一件事真的成了"

> 这一节是**方法论**，比任何单个模块都值钱。

### 5.1 三层证明力（数据通路的标配）

```
T23 灯常亮   →  证明"链路建立了"
ping 通      →  证明"数据能走通"
udp_verify   →  证明"数据一个字节都没错"
```

**只报前两层等于没测**。任何"通了"的结论，必须落到**逐字节比对 + 校验和**。

### 5.2 判据无旁路原则

数据通路必须被**链路状态硬门控**（`aurora_rst = ~sys_rst_n | ~channel_up`）：**链路没起来，板子对外就是静默的**。
这样"判据通过"就**等价于**"数据真的穿过了链路"——杜绝了"其实数据在本地绕回来了"这种假通过。

### 5.3 计数器差分链对账（本项目自创）

在数据通路**每一级**埋一个计数器，跑完流量后逐级相减：

```
PC发送 N → 泵A写 → 泵A读 → 打包出 → B回显入 → B回显出 → 解包入 → 泵B写 → PC收到 M
            (+泵A丢)                          (+B溢出)              (+泵B丢)
闭合条件: N = Σ各级计数 + Σ各级丢弃 = M + 总丢弃
```

**差额落在哪一级，问题就在哪一级**——比"盯着波形猜"高效得多。§4.7 的 0.4% 就是这么做出来的。

### 5.4 差分链的前提：产物必须留档

09-21 那次对账的 ILA 快照用的是固定文件名、每次覆盖，导致**配对产物丢失、事后无法重算**。
现已改为**每次快照自动归档到带时间戳的目录**（3 份 CSV + manifest）——**判据的价值取决于证据能不能被复查**。

### 5.5 事实源优先级（一条红线）

**官方例程与官方约束 > 已上板验证的自家工程 > 板卡手册 > AI 生成文档**。
遇到冲突，永远往上找。§4.8 判"GT 参考时钟要不要写 IOSTANDARD"，就是靠翻官方例程定的——工具报的警告也可能是**误报**，动手前先做真伪判定。

### 6.3 已知的两个待修问题（知情，不必慌）

1. **过载时的"硬冻结"**：背靠背猛打时板子可能卡死（重烧恢复）。**第一候选机制已经用仿真复现出来了**——栈发送模块在"正忙"时收到的"新帧开始"信号会被**整帧丢弃**，且因为缓冲区不记录帧边界，下一个开始信号会**用新帧的长度去读旧帧的字节**，造成**字节流永久错位**。修法已设计（忙时挂起请求 / 换成带帧边界的队列），但**故意没动**——因为现在的判据基线都建立在现有位流上，改逻辑就得重出位流、全部重测。
2. **一条约束其实没生效**：某个 XDC 里有一条 `set_false_path` 因为**行尾写了 `#` 注释**而报错失败（Tcl 里 `#` 只在行首才是注释，写在行尾会被当成多余参数）。影响很小（时序仍收敛），但**新工程会继承这个写法，要一并修掉**。
